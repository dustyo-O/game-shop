# Phase 4 · Slice 4 — The currency control, and hover on tiles and cards

> Three of the five graded interactions land in this slice, and the first of them has no JavaScript at all. The «$ / ₸ / ₽» control is three native radio inputs in a `<fieldset role="radiogroup">`: the browser keeps exactly one checked, moves the check with the arrow keys, enters the group on the checked one, and the stylesheet paints what the browser already knows through `:checked + label`. A reviewer who opens `steam-topup.ts` looking for the handler finds a comment telling them why there is none. That is not the interaction done cheaply; it is the strongest version of it, because every property functional spec §2.4 asks for — *exactly one active, clicking another makes it active, clicking the active one changes nothing* — is a property a radio group has by definition, and the JavaScript alternative would have to rebuild each of them by hand and could get each of them wrong. §3.1 lists what it would rebuild.
>
> The other two — tiles that highlight and cards that lift — are CSS transitions, and the spec's word for both is *"fades in rather than switching on instantly"* / *"animates rather than switching instantly"*. "Smooth" is not a thing a test can watch, so it was made into two things a test can read: a static `transition-duration` greater than zero, and the two end states either side of it — never a value in between. R14 wrote that rule down before the slice began; the slice's own finding is that the rule bit anyway. Reading a currency label's colour straight after a click caught its 120 ms fade halfway — `rgb(137, 137, 139)`, a grey neither end of the fade names — and that is the third time this phase a read landed at a moment the test did not control (§5.1).
>
> One rule in the sheet is for a reviewer nobody can see: under `prefers-reduced-motion: reduce` the card's 4-px rise is withdrawn and nothing else is — the shadow still deepens, the tiles still tint, and both still fade. Why the fade survives is the second decision the task names (§3.2). Reading the code and specs for this document found six small things, none in the product's behaviour — reported in §5.4, not fixed.

## 2. The words this document uses

- **Radio group** — inputs of `type="radio"` that share a `name`. The browser treats them as one control with one answer: checking one unchecks the rest; the whole group is a single Tab stop, entered on the checked radio from either direction; Left/Up and Right/Down move focus *and* the check to the neighbour, wrapping at the ends; a click on a `<label for>` is forwarded to the radio it names. `role="radiogroup"` on the containing `<fieldset>` says the same thing to assistive technology in one word, and the `aria-label` is the group's name where the mockup has no room for a `<legend>`.
- **`:checked`, `+`, `:focus-visible`, `:focus-within`** — four pieces of selector. `:checked` matches a radio whose state is on. `+` is the adjacent-sibling combinator: `.currency__input:checked + .currency__option` reads "the label immediately after a checked radio". `:focus-visible` matches a focused element *when the browser judges the focus should be shown* — after a key press, yes; after a mouse click on a radio's label, no. `:focus-within` matches an element that *contains* the focused element — the card, when the «Купить» inside it has focus.
- **Visually hidden** — the clip recipe on `.currency__input`: `position: absolute; width: 1px; height: 1px; margin: -1px; overflow: hidden; clip: rect(0 0 0 0); clip-path: inset(50%); white-space: nowrap`. The element is in the DOM, in the tab order and in the accessibility tree; it has no pixels. `display: none` would remove it from all three, and a radio the keyboard cannot reach is a radio the keyboard cannot use.
- **Transition vs animation** — a transition is the browser interpolating a property from its old value to its new one *when something changes the value*: a hover state coming on, a check moving from one radio to another. It has a duration and an easing and runs only on a change. An animation is keyframes that run of their own accord. Everything in this slice is a transition; nothing on the page animates.
- **Interpolated value** — the in-between value the browser computes on each frame of a transition. `getComputedStyle` returns *that* value, not the target: 60 ms into a 120 ms fade from `#f2f2f4` to `#111113`, a label's background is a grey no rule names. It is a fact about the frame, not about the state.
- **Reduced motion** — an operating-system setting ("Reduce motion" on macOS and iOS; the animation-effects switch on Windows) that reaches CSS as `@media (prefers-reduced-motion: reduce)`. People set it because things *moving* on screen — sliding, zooming, parallax — cause them discomfort or distraction. It is a statement about movement, not about change.
- **Token** — a CSS custom property holding a value used in more than one place: `--sf-ink`, `--sf-ground`, `--sf-shadow-lift`. Seven are declared, on `.storefront` rather than `:root`, so the order and admin pages have none.

## 3. The two decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision — with the markup or CSS fact beside the plain-language reason.

### 3.1 The active state is the browser's own radio group, and no script touches it

**What.** `renderCurrencyControl` builds `<fieldset class="currency" role="radiogroup" aria-label="Валюта">` and fills it by mapping `currencies` through `renderCurrencyOption`, which returns a pair per currency: `<input type="radio" name="currency" id="currency-usd" value="$" class="currency__input">` and `<label for="currency-usd" class="currency__option">$</label>`. Only the «$» input gets `checked` (`steam-topup.ts` lines 65–67). That is the whole of the control's code; the rest is stylesheet. The input is hidden by the clip recipe, not `display: none`. The label is the 36-px square the shopper sees and clicks, and the browser forwards that click to the radio. `.currency__input:checked + .currency__option` paints the checked one `--sf-ink` on `--sf-surface`; the other two rest on `--sf-ground`. `.currency__input:focus-visible + .currency__option` draws `outline: 2px solid var(--sf-ink); outline-offset: 2px` — the keyboard's ring, on the label, because the radio it belongs to has no pixels to draw it on.

There is no listener, no `.checked` read, no `change` handler, no `querySelector` in the file — `grep -n 'addEventListener\|\.checked\|"change"\|querySelector' ui/steam-topup.ts` returns nothing. `grep -rn "currency" ui/*.ts` finds the markup construction in `steam-topup.ts` and, elsewhere, only the glyph name `chip-game-currency` in `icon.ts` and `popular-products.ts`, which is a chip's icon and nothing to do with the group. `storefront-page.ts` neither listens to the group nor reads it.

**The obvious alternative.** Three `<button type="button" role="radio" aria-checked="…">` in a `<div role="radiogroup">`, one `click` listener that sets `aria-checked="true"` on the clicked button and `"false"` on the other two and moves an `is-active` class, and a stylesheet keyed on the class. It is the shape a reviewer expects to find, because "the currency control changes its active state" sounds like a state and a handler — which is why the tech spec surfaces this decision as assumption 4 rather than leaving it to be discovered.

**What goes wrong with the alternative.** The handler is the least of it. To be a correct radio group — not a row of buttons that looks like one — the JavaScript version has to rebuild six things the native group gives by construction, and each is a thing hand-rolled versions get wrong:

1. **Exactly one active.** Native: an invariant the browser enforces; `currencyState` in the spec throws if the count of checked radios is not one, and it never has. Hand-rolled: two copies of one bit — the class and the attribute — that a handler must keep in step; a re-render, a second handler, or an early return leaves them disagreeing, and a sighted user and a screen-reader user are told different states.
2. **One Tab stop for the group — the roving `tabindex`.** Native: the group is one stop. Hand-rolled: `tabindex="0"` on the active button and `-1` on the others, rewritten on every change. Forgotten on first render → three Tab stops for one choice. Forgotten after a change → Tab lands on the button that *was* active.
3. **Arrow keys.** Native: Left/Up and Right/Down move focus and the check together, wrapping at both ends. Hand-rolled: a `keydown` handler that knows four keys, wraps in both directions, moves focus *and* state (in a radio group the arrows select, unlike a tab list where they may only focus), and swaps direction under RTL. The usual omissions are Up/Down and the wrap.
4. **`aria-checked`.** Native: role, name and checked state are properties of the element. Hand-rolled: an attribute string mirroring the state — the third copy of the bit from item 1.
5. **Entering the group on the checked one, from either side.** Native: Tab and Shift+Tab both land on the checked radio — the drive's Shift+Tab back from «Оплатить» landed on ₽, the checked one, with the ring on its label only. Hand-rolled: item 2 again, and Shift+Tab is the direction that gets missed; a naive version lands on the last button.
6. **Form semantics and CSS state.** Native: `name` and `value` (`$`, `₸`, `₽`), a `change` event the browser fires, `:checked` for the stylesheet to key on, a value a form could read. Hand-rolled: none of these; the stylesheet keys on a class the handler owns, and "the state" is wherever the handler last wrote it.

After all that scaffolding, the handler's own logic is "set this one true, the others false" — the sentence the tech spec (§2.2), the source comment and `CLAUDE.md` all use. It is the wrong trade: build six mechanisms to replace one, and arrive at a function with no content. The spec's fourth criterion — *nothing else changes* — is also easier to keep with nothing running: there is no handler to accidentally do something.

Three smaller choices sit inside the big one. **Hidden by clipping, not by `display: none`:** the radio has to stay in the tab order and the accessibility tree for items 2–5 to exist at all; `display: none` keeps the state but discards the keyboard. **An `outline` for the ring, not a `box-shadow`:** `outline` is what the browser's own ring is, so it behaves as a ring everywhere a ring is expected — including forced-colours modes that discard shadows — and it is *not* one of the two properties the label transitions, so the ring appears at once rather than fading in over 120 ms. **The label fades, the check does not:** `.currency__option` transitions `background-color` and `color` over 120 ms, so the dark square slides its colour from one label to the next; `:checked` itself flips instantly. That difference — a discrete state beside an interpolated paint — is what the spec reads for each (§4) and what §5.1 is about.

On "isn't that cheating": the assignment grades that the control *changes active state*, and it does — by click, by keyboard, with a visible active square. It was never asked to recalculate; §2.4 waives that and keeps the mockup's «$» active beside a sum in roubles as drawn. A radio group is not a way around the interaction; it is the interaction, named by its standard name.

### 3.2 Reduced motion drops the transform and keeps the fade

**What.** The last block of the sheet:

```css
@media (prefers-reduced-motion: reduce) {
  .product-card:hover,
  .product-card:focus-within {
    transform: none;
  }
}
```

It sets one declaration on the same two selectors as the lift rule, and nothing else. It does *not* touch `transition` — the card's `transform 180ms ease, box-shadow 180ms ease` stays declared — so under the setting a hovered card still gains `--sf-shadow-lift`, and the shadow still fades in over 180 ms; there is simply no transform change for the first half of the transition to interpolate. The tiles' `background-color, box-shadow 160ms` and every 120 ms fade are untouched. The block is last in the file on purpose: a media query adds no specificity, so `.product-card:hover` inside it ties with `.product-card:hover` outside it and source order decides — the lesson Slice 1's §6.1 recorded about the cascade, applied. `hover.spec.ts`'s last test sets `emulateMedia({ reducedMotion: "reduce" })`, hovers a card and reads `transform: none` with `box-shadow: rgba(0, 0, 0, 0.18) 0px 16px 40px 0px`, then hovers a tile and reads the tint and a shadow.

**The obvious alternative.** Two, opposite in direction. The first is the boilerplate: `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { transition: none !important; animation: none !important } }`. The second is nothing at all — a 4-px rise is small.

**What goes wrong with each.** The boilerplate is a `*` rule, the one selector R4 forbids: this sheet is in the bundle on `/order/:id` and `/admin/recovery`, and a `*` rule would reach both. It also removes the thing §2.5 crit 1 grades — for the reviewer with the setting on, the highlight would "switch on instantly", which is R11 word for word. And it is the wrong reading of the setting. Reduced motion is a preference about *movement* — an element changing position or size across frames — because that is what makes some people ill or pulls their attention. A colour going from transparent to grey, or a shadow deepening, moves nothing: no edge travels, nothing grows. The usual advice for what to do under the setting is to replace a movement with a fade, not to remove the fade. Doing nothing goes wrong the other way: the rise is movement, it happens on every card the pointer crosses, and a shopper who asked the system for less of it would watch this page ignore the request.

Why the criteria still hold with the transform gone: §2.6 crit 2 says the card "visibly lifts — *a raised shadow, an outline, or a rise*", so the shadow alone is one of the three answers the spec itself lists, and "animates rather than switching instantly" still holds because the shadow fades. §2.5 is not touched at all — the tiles never moved. The audit behind "only the card": on hover, tiles change background and shadow; chips, pills and buttons change background; the currency label changes background and colour; the card changes transform and shadow. One `transform` on the page, so one declaration in the block. The banner's auto-advance is deliberately outside the query — a slide change is a `hidden` swap with no transition, the spec mandates the advance, and the pointer pause is its stop mechanism.

## 4. What each test layer proves, and how each was shown able to fail

**No unit layer, and why.** Tech spec §4.1: *"The currency control has no unit test — native radios, nothing to compute."* Slices 2, 3 and 5 each had a fact the page *derives* — wrap arithmetic, a timer policy, a menu rule, a row selection — and that is the trigger architecture §7 names for a test without a browser. Slice 4 derives nothing. The markup is `currencies` mapped through a function; the state is the browser's; the hover is a stylesheet. A unit test here would be testing `createElement` and the browser's radio implementation, and the second of those is what the browser layer is for. So this slice's first layer is Playwright.

**Browser — `currency.spec.ts`, 5 tests, no clock.** Every assertion reads through one helper, `currencyState`, which fetches two facts in one round trip: which radio is `.checked` (and throws if zero or more than one is — a throw there means the markup drifted, not that an assertion was strict), and each label's computed `backgroundColor`. The first fact is discrete and read at once; the second is a painted colour with a 120 ms fade behind it, so it is read only after `CURRENCY_SETTLE_MS = 200`. `sumText` reads `.steam-topup__sum-value` immediately — text is not interpolated.

**R14 as a method, not a sentence.** The rule has two halves and both files apply both. *A static read* — `transition-duration` — proves the fade exists without watching it. *An end-state read after the duration* proves what the fade arrives at. That under reduced motion the shadow still has a duration: the media block sets only `transform: none` and leaves `transition` alone, but that is read from the CSS, not asserted — the reduced-motion test reads end states only. The ring's look beyond `outlineStyle !== "none"`. Any browser but Chromium: `:focus-visible`'s heuristics differ per engine, and the suite runs one project.

## 5. Findings

### 5.1 The settle-time trap, third appearance

Crit 2 of `currency.spec.ts` first read each label's `backgroundColor` immediately after the click, and failed: `rgb(137, 137, 139)` and `rgb(122, 122, 124)` — greys about halfway between `--sf-ground` (242) and `--sf-ink` (17), values no rule in the sheet names. The radio had flipped; the label's 120 ms fade was in flight; the read landed on a frame. The fix is `CURRENCY_SETTLE_MS = 200`, and the file's header records the two mid-values so the next reader does not "tighten" the wait away.

It is the third time this phase a read arrived at a moment the test did not control, and the three are worth lining up because the fix was the same shape each time — make the moment explicit:

| Where | What moved between the action and the read | The fix |
| --- | --- | --- |
| Slice 2 §5.2 — `install()` does not freeze time | the faked clock kept pace with the wall through `goto` and the catalogue fetch, so `runFor(4999)` was already past 5 000 | pause the clock *before* navigating, at an epoch the file owns |
| Slice 2 §5.3 — `waitForTimeout` in the relay | the page's renderer was unscheduled while the relay waited, so a real timer that should have fired had not | wait *inside* `page.evaluate`, with the call held open |
| Slice 4 — this one | a 120 ms colour fade between the click and the `getComputedStyle` | wait past the duration, then read the end state |

R14 predicted the third before it happened; it still happened, in the one file that was not about hover, because the currency label fades too. The general form is the one the tech spec's own words give: a computed style mid-transition is the classic false negative, and *every* painted property with a `transition` on it is mid-transition for a while after any change.

### 5.2 `:focus-visible` is about how focus arrived, and the mouse does not qualify

Two facts from the drive that look like the ring being flaky and are not. A mouse click on a currency label focuses its radio — `document.activeElement` is the input — and draws no ring, because Chromium does not match `:focus-visible` for focus that arrived by pointer on this kind of control. A Shift+Tab into the group draws the ring, on the checked radio's label only. That is the pseudo-class doing what it is for: the browser's own ring has always been keyboard-only for buttons and radios, and `:focus-visible + label` inherits the judgement rather than re-deciding it.

The consequence for tests is a rule both spec files follow: reach a state by the gesture the criterion names. `hover.spec.ts` presses real `Tab`s to reach a tile because crit 4 says "with the keyboard"; `currency.spec.ts` uses `.focus()` on «$» only to *start* the arrow-key sequence without the side effect a click would have (checking the radio), and asserts the ring after a real Shift+Tab. Slice 3's `.focus()` on the search field was the same principle from the other side — reaching a state without a click's side effect — and its header told the next reader not to "fix" it; both files here say the same in their comments.

### 5.3 Hover shades as literals — a judgement call to name

Two colours appear only in hover rules and appear as hex, not tokens: `#3a3a3f` (ink, a step lighter — already the Каталог pill's pressed colour) for the black controls, and `#e4e4e8` (ground, a step darker) for the grey ones, including the unchecked currency squares. The MOTION header says why: they are hover-only, and keeping them out of the token list keeps "seven tokens" a true count rather than nine. The cost is real and worth saying aloud: a later change to `--sf-ink` or `--sf-ground` would leave both hover shades where they are, one step off a colour that has moved. The alternative — `--sf-ink-hover` and `--sf-ground-hover` — is two lines. The call was made for the smaller list; it is the kind of thing a reviewer may reasonably prefer the other way, and either answer is defensible as long as it is stated.

### 5.4 Read while writing this document — reported, not fixed

- **`hover.spec.ts` attributes a sentence to R14 that R14 does not contain.** Lines 41–42 quote R14 as saying `waitForTimeout(250)` after the hover "is acceptable here". R14 in `technical-considerations.md` says "wait for `transitionend` where a final value is needed"; the phrase in quotation marks appears nowhere in the repository except the spec file itself. The fixed wait is defensible (§4 says why), but the justification should be the file's own, not a quotation.
- **`.currency__option:hover` is the one `:hover` rule without a `:focus-visible` twin.** The MOTION header ("`:focus-visible` shares every `:hover` rule") and `CLAUDE.md` ("`:focus-visible` shares each `:hover` rule") are one degree too strong. The keyboard user loses nothing — the ring rule is the keyboard's equivalent, and the checked square is ink regardless — but of 15 hover rules, 14 are paired and this one is not, and the sentences say 15.

## 6. Interview questions this answers

**"There is no JavaScript on the currency toggle. Isn't that cheating on a graded interaction?"**
It is the interaction, done by the mechanism that defines it. §2.4's contract is *exactly one active; clicking another makes it active; clicking the active one changes nothing; nothing else changes* — and that is the definition of a radio group, which is why the markup is `<input type="radio" name="currency">` ×3 in a `<fieldset role="radiogroup">`. The browser enforces the one-active invariant, moves the check with the arrow keys, enters the group on the checked one from either side, fires `change`, and exposes role, name and state to a screen reader; the stylesheet paints `:checked + label`. A JavaScript version has to rebuild all six of those to arrive at a handler whose logic is "set this one true, the others false" — and every one of the six is a thing hand-rolled versions get wrong. The tech spec surfaces this as assumption 4 precisely so a reviewer expecting to see a handler reads the reason instead: `grep addEventListener ui/steam-topup.ts` returns nothing, and that is the design.

**"Why doesn't picking ₸ change the sum?"**
Because the assignment waives it and the mockup contradicts it. Functional spec §2.4: recalculating amounts is explicitly waived, and the mockup's own pairing — an active «$» beside «Сумма 500 ₽» and a button reading «Оплатить 500$» — is reproduced as drawn. There is no exchange rate in the shop and nothing to compute from; a control that pretended to convert would be inventing prices, which the product definition forbids for the same reason it forbids the struck-through "old price". «Сумма» is a `<span>` of static text, not an input, so nothing about it invites typing or promises a result. `currency.spec.ts` crit 4 reads it before and after every click: `"500 ₽"` every time.

**"Why `:focus-within` on the card, when everything else uses `:focus-visible`?"**
Because the card is never focused; the «Купить» inside it is. `:focus-visible` on `.product-card` would never match. `:focus-within` matches the element that *contains* the focused one, so a keyboard user who Tabs onto Купить lifts the card they are about to press — the same 4 px and the same shadow the pointer gets. A card without Купить has nothing focusable and lifts on hover only, which is correct: there is nothing on it to reach. The test focuses the first `.product-card__buy` and reads the lift matrix on its own `<li>`. The reduced-motion block repeats both selectors so the keyboard user's lift is withdrawn there too.

**"The search box and «Оплатить» do nothing. Why do they still have hover states?"**
Because the functional spec's scope line for them is *"visibly present and quietly inert"* (§3), and §2.8's last criterion is that nothing about them may promise a result they do not deliver — and a button with no hover reads as broken, which is a promise of the wrong kind. Slice 1 made them inert by construction (no `<a>`, no `<form>`, no handler); this slice gives them `cursor: pointer` and a 120 ms hover shade so they look like what they are, buttons. The line the spec draws is between *feedback* and *result*: a pressed look is fine, a spinner or a message is not. `inert-controls.spec.ts` still proves the result half — no navigation, no `POST`, no error, no text like «скоро» — and this slice did not touch it.

**"How do you test that a highlight is 'smooth'? You can't screenshot a fade."**
You do not test the fade; you test the two facts that make one. First, a static read: `transition-duration` on the tile and the card is greater than zero — a CSS property that does not change while the transition it describes runs, so it is safe to read at any time. Second, end states: at rest the tile is `rgba(0, 0, 0, 0)` with no shadow; after `hover()` plus 250 ms it is `rgb(242, 242, 244)` with a shadow; after moving away plus 250 ms it is back. Never a value in between — that is R14, and §5.1 is what happens when it is forgotten: a read at 0 ms found `rgb(137, 137, 139)`, a grey no rule names. The one thing no layer proves is the fade *as seen*; the verifier's by-eye of the three screenshots is the closest, and the spec says so in its "does not prove" paragraph.

**"Why keep the fade under reduced motion? Isn't a fade an animation?"**
It is a transition, and it is not motion. `prefers-reduced-motion` is a request about *movement* — position or size changing across frames — because that is what makes some people ill. A colour going from transparent to grey, or a shadow deepening, moves nothing; the usual guidance is to replace a movement with a fade, not to remove fades. So the block withdraws the one thing on the page that moves on hover, the card's `translateY(-4px)`, and nothing else: `transform: none` on the lift's two selectors, and `transition` untouched, so the shadow still fades over 180 ms. The criteria still hold — §2.6 crit 2 accepts "a raised shadow, an outline, or a rise", so the shadow is one of the spec's own three answers — and the boilerplate alternative, `* { transition: none !important }`, is a `*` rule R4 forbids that would also make the tiles switch on instantly for exactly the reviewer R11 worries about.

**"What does R4 — CSS leaking into the order page — have to do with hover rules?"**
This slice added thirty-odd hover and focus selectors to a sheet that is in the bundle on every route, because `router.ts` imports every page statically and Vite emits one CSS file. What keeps them off `/order/:id` and `/admin/recovery` is that each starts with a storefront-owned class — `.service-tile:hover`, `.product-card:focus-within`, `.currency__input:checked + …` — and none is a bare `button:hover` or `*`. So the slice re-ran the check Slice 1 established: on `/order/:id`, `leakCount: 0`, `bodyMinWidth: "0px"`, the payment buttons' `transition-duration` `0s` — the order page's buttons do not fade, because no rule reaches them — and the page pixel-identical to the 003 screenshot by eye; on `/admin/recovery`, the sheet present and `hoverRulesMatchingAnythingHere: []`. The audit of the parsed sheet: 133 selectors, 0 element-level. The reduced-motion block is the case where this mattered most, because the obvious way to write it is the one `*` rule that would have broken it.

**"You're reading colours with `getComputedStyle`. Doesn't the verify-ui skill say not to?"**
It says not to for shape and position, where `getBoundingClientRect` is the right tool, and to use computed style for visibility and opacity. A hover highlight *is* a paint — background, shadow, transform — and there is no geometry to read: a hovered tile is the same 76 px wide as an unhovered one. The discipline is elsewhere: read discrete state (`:checked`, `hidden`, `aria-current`) at once, read painted state only after the duration, and read the duration itself statically. And the pixel judgement — "visibly highlights" — is left to the one layer that can make it, a person looking at the screenshot.
