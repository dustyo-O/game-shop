# Phase 5 · Slice 1 — The codes and the counter

> Nothing in this slice can be redeemed. A shopper who types `LIMIT3` today reaches no endpoint, and no transaction increments anything. What exists after it is the storage the fifth adversarial scenario will be proven on — two tables, eight named CHECKs, one primary key that is stronger than the architecture asked for — plus the four codes loaded by a seed that is safe to re-run, the discount arithmetic as a pure function with the brief's worked examples pinned, and two test harnesses that know the new tables well enough to refuse a dirty database.
>
> Three things carry the slice, and each looks like bookkeeping until the alternative is tried. **The counter and the ledger are two columns that must agree, and only one of them is the mechanism**: `promo_codes.used_count` is the row twenty simultaneous shoppers queue on; `promo_redemptions` is the record of who spent what. A count derived from the ledger has no row to queue on. **The seed writes the definition and never the state**: its `ON CONFLICT (code) DO UPDATE` names `kind`, `value`, `currency`, `max_uses` and stops, so `pnpm dev:stack` — which re-seeds on every start — cannot hand a spent code back. **The cleanup decrements by exactly what it deleted and never recomputes**, because a cleanup that recomputes the counter from the ledger makes the after-run baseline true by construction, and a test that cannot fail is not a test.
>
> Reading the delivered work found four things. drizzle's migrator splits a file on its statement separator as a raw substring, comments included, and the first annotated header quoted the separator in prose — the whole migration rolled back. The seed's `catch` printed the query text and swallowed the constraint name. The new baseline assertion caught another agent's write mid-flight (`sum(used_count) = 2, expected 0`), which is the assertion doing its job on a database it was not told about. And `promo_codes.id` is `serial`, not the `bigint` the older tables use, for a reason that is one sentence long.

## 2. The words this document uses

- **Counter** — `promo_codes.used_count`, one integer per code. The thing I7 guards, and the row every redemption of that code will queue on. Written by exactly one statement in production, the conditional `UPDATE` Slice 2 adds.
- **Ledger** — `promo_redemptions`, one row per order that spent a use: which code, at what list price, for how much off. The thing I8 keys on. In production the counter always equals `count(*)` of the ledger grouped by `promo_id`; they are two columns that must agree, and *agree* is a fact to assert, not a rule to enforce by copying one into the other.
- **Definition vs state** — every column of `promo_codes` except `used_count` is *definition*: the brief wrote it, the fixture transcribes it, a re-seed may rewrite it. `used_count` is *state*: the shop wrote it as codes were redeemed, and a re-seed must not touch it. The distinction decides the seed's `SET` list.
- **Backstop vs mechanism** — the mechanism is the statement that makes a guarantee hold under concurrency (the conditional `UPDATE`); the backstop is the constraint that refuses a row the mechanism should never have produced (`CHECK (used_count <= max_uses)`). A backstop can hold with the mechanism gone, which is why a proof must not assert on the backstop's column alone.
- **Minor units** — kopecks. `promo_codes.value` for an `amount` code is `50000`, not `500`; the fixture keeps the brief's `500` and the seed multiplies once. No money anywhere in the schema is a float.
- **Idempotent seed** — safe to run twice, which is not the same as "changes nothing the second time". The catalogue and the promo *definitions* are rewritten from the fixture on every run (that is how a drifted limit gets corrected); only the state columns are genuinely untouched. The report line says "no new rows", not "nothing changed", on purpose.
- **Drift** — the counter and the ledger disagreeing: a code whose `used_count` is 3 while two ledger rows name it, or the reverse. In production it means a rollback path failed or a write bypassed the transaction. The whole point of §3.3 is that the harness must *see* drift, not repair it.

## 3. The three decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision — with the SQL beside the plain-language reason.

### 3.1 Two columns that must agree, and only one of them is the mechanism

**What.** Two tables. `promo_codes` carries the four definitions and one integer of state, `used_count integer NOT NULL DEFAULT 0`. `promo_redemptions` carries one row per order that spent a use — `order_id text PRIMARY KEY` referencing `orders`, `promo_id integer` referencing `promo_codes`, `list_amount_minor`, `discount_minor` — with `CHECK (discount_minor >= 0 AND discount_minor <= list_amount_minor)` and an index on `promo_id`. In production, `used_count` equals `count(*) FROM promo_redemptions GROUP BY promo_id` at every commit boundary. The counter is what I7's statement, arriving in Slice 2, will read and write in one breath:

```sql
UPDATE promo_codes SET used_count = used_count + 1
WHERE id = $1 AND used_count < max_uses
RETURNING used_count;
-- 1 row  => this transaction holds one of the N uses
-- 0 rows => exhausted; nothing written; 409
```

The ledger is what I8's statement will write immediately after, under the order lock:

```sql
INSERT INTO promo_redemptions (order_id, promo_id, list_amount_minor, discount_minor)
VALUES ($1, $2, $3, $4)
ON CONFLICT (order_id) DO NOTHING
RETURNING order_id;
-- 0 rows => impossible under the order lock; a thrown error that rolls back the increment
```

**The obvious alternative.** One table, not two. Either keep only the ledger and *derive* the count — `SELECT count(*) FROM promo_redemptions WHERE promo_id = $1`, insert if it is below `max_uses` — or keep only the counter and note the applied code on the order row.

**What goes wrong with the alternative.** Ledger-only first, because it is the one that looks cleaner. Under `READ COMMITTED` — this project's isolation level by design — every one of twenty concurrent transactions runs its `count(*)` under its own snapshot, sees `2`, decides it is allowed, and inserts. There is no row for them to queue on: a count is the result of a scan, not a thing with a lock. Making it safe means adding one — a `SELECT … FOR UPDATE` on some `promo_codes` row before counting, which is the counter's row brought back under another name; or `SERIALIZABLE`, which the architecture rejected because it moves the guarantee into an invisible retry loop; or a table lock, which serialises every code behind every other. The counter column is the cheapest possible row to lock, and the conditional `UPDATE` is the read and the write in one statement, so each transaction in the queue re-evaluates `used_count < max_uses` against the row *as the previous one committed it*. The fourth sees `3`, matches nothing, returns nothing.

Counter-only fails the other way. Nothing says which order spent a use, so I8 has nothing to key on — a retried apply on the same order increments twice. The list price and the discount have nowhere to live, and "the record of what was paid does not change after the fact" (functional spec §2.3) is a property of columns, not of arithmetic. And the harness cannot hand back exactly what a test spent, because there is nothing to count.

So both exist, and the discipline is in which one is written by whom. The schema's comment says it in one line: *a test may recompute one from the other; production never does.* The CHECK on the counter — `used_count >= 0 AND used_count <= max_uses` — is the backstop, and §5 of the technical spec's risk table (R2) says what it hides: weaken the guard to an unconditional `used_count + 1` and the fourth increment does not produce `4`, it trips `23514 check_violation`, aborts, and answers 500 with the counter reading `3`. A test that asserts only the counter stays green with the mechanism gone. Every proof of the limit therefore asserts the *shape* of the refusals — exactly N × 200, the rest × 409, **zero 5xx** — and the ledger rows, and the counter only in addition.

One more shape decision sits here. `promo_redemptions` is keyed `PRIMARY KEY (order_id)`, not the architecture's `UNIQUE (promo_id, order_id)`. The original would have admitted two *different* codes on one order — a second discount on an already-discounted price. The functional spec's rule is one code per order, so the key is `(order_id)` alone; the stronger key implies the weaker, so every guarantee I8 was written for still holds, and `architecture.md` carries the amendment inline. The negative proof was the row the old key would have accepted: two redemptions on one order **with different codes** → `promo_redemptions_pkey`. The FK to `orders` is real, by the `deliveries` argument — only code that has already locked and read the order writes this row, so a dangling reference can only be a bug. The table that deliberately carries no such key is `payment_events`; the contrast is the point.

### 3.2 The seed writes the definition and never the state

**What.** The statement Drizzle emits, captured with `.toSQL()` rather than assumed:

```sql
insert into "promo_codes" ("id","code","kind","value","currency","max_uses","used_count")
values (default, $1, $2, $3, $4, $5, default), …
on conflict ("code") do update
  set "kind" = excluded.kind, "value" = excluded.value,
      "currency" = excluded.currency, "max_uses" = excluded.max_uses
returning "code";
```

Two things, read together. Drizzle names every column and writes the `DEFAULT` keyword where it was handed no value — `id` and `used_count` — so a fresh row takes `0`. And the `SET` list names `kind`, `value`, `currency`, `max_uses` and stops; the `0` sitting in `excluded.used_count` is never copied across. An existing row keeps whatever the shop has counted. It is the third `ON CONFLICT` shape in the file, after `products` (pure definition, `DO UPDATE` on everything) and `supplier_keys` / `supplier_behaviour` (pure state, `DO NOTHING`): a definition with one column of state riding on it. The report line says so out loud — `promo_codes — 4 inserted, 0 updated; 4 defined, 0 uses spent (never written by this script)`.

**The obvious alternative.** Any of three. Add `used_count = 0` to the `SET` — a seed is a reset script, after all, and `pnpm db:reset` is how a developer gets a clean slate. Or `DO NOTHING`, the shape the supplier tables use. Or, to avoid the CHECK ever firing on a re-seed, `used_count = least(used_count, excluded.max_uses)`.

**What goes wrong with the alternative.** `used_count = 0` first. `pnpm db:setup` runs migrate-then-seed on every `pnpm dev:stack`, against a database that usually already has live orders. Every restart would zero four counters while the ledger still holds every redemption they counted — drift introduced by the seed itself, and `ONCEONLY` usable again after every reboot of the dev stack. The functional spec's §2.4 is explicit that an abandoned order does not return a use; a seed that returns *all* of them is worse. `DO NOTHING` fails the other way: a corrected limit in the fixture never reaches the row, and the precedent — `products` — is that a transcription of the brief is authoritative and a re-seed must fix a typo. `least(…)` is the quiet one: it makes the seed succeed by forgetting redemptions the ledger still records, which breaks the agreement the harness asserts, from inside the one script that is supposed to be safe to run.

The CHECK is what makes the chosen shape honest rather than merely careful. If the fixture lowers a code's `max_uses` below what the shop has already counted, the updated row violates `promo_codes_used_count_range`, Postgres raises `23514` naming that constraint, and the *whole* seed transaction rolls back — the products upsert included. Proof (b) did exactly that: `used_count = 2` by SQL, fixture `maxUses: 1`, re-seed → `promo_codes_used_count_range`, products still 12. Proof (a) is the ordinary case: `ONCEONLY.used_count = 1` and `LIMIT3.max_uses = 99` set by SQL, re-seed → `0 inserted, 4 updated`, `LIMIT3` back to 3, `ONCEONLY` still 1. Definition rewritten, state untouched, in one run.

The fixture side is where the brief's units live. `GG500` is stored in the fixture as `valueRub: 500`, exactly as the brief prints it, and multiplied by `MINOR_UNITS_PER_ROUBLE` in one expression in `promoCodeRows()` — the same constant and the same place that turns `priceRub` into `price_minor`. The brief's `type` becomes the column `kind` on the same line, because `type` is already a product's category. The definition is a discriminated union on the brief's `type`, so a `percent` row carrying a `currency` does not compile — the same rule `promo_codes_currency_iff_amount` enforces at rest, caught two layers earlier. And the export is `promoCodeDefinitions`, not `promoCodes`: that name is the table, and the barrel exports both.

### 3.3 The cleanup decrements; it never recomputes

**What.** One statement in `cleanupTestOrders`, after `payment_events` and before `orders` because `promo_redemptions.order_id` is a real foreign key:

```sql
with gone as (
  delete from promo_redemptions where order_id = any($1::text[]) returning promo_id
), per_promo as (
  select promo_id, count(*)::int as n from gone group by promo_id
)
update promo_codes p set used_count = p.used_count - per_promo.n
from per_promo where p.id = per_promo.promo_id
-- 0 rows updated => none of these orders had a code applied; not an error
```

Delete this test's ledger rows, returning which code each named; group; subtract from each code exactly the number removed. One statement rather than a delete followed by an update, so there is no instant at which the ledger has shrunk and the counter has not. Byte-for-byte the same executed string in `apps/web/e2e/support/db.ts`, which duplicates the API harness rather than importing across app boundaries.

**The obvious alternative.** After deleting the rows, recompute: `update promo_codes set used_count = (select count(*) from promo_redemptions where promo_id = promo_codes.id)`. It is shorter, it is "always correct", and it heals whatever it finds. Or simpler still, `update promo_codes set used_count = 0` — the shape the admin reset endpoint will take for the deployed shop.

**What goes wrong with the alternative.** It makes `assertBaseline("after")` true by construction. Suppose the application drifted during the test — an increment committed whose ledger insert did not, which is what a broken rollback path in Slice 2's transaction would look like — leaving the counter at 3 and the ledger at 2. The recompute writes 2, then after the delete writes 0; the after-run check reads `sum(used_count) = 0`, `promo_redemptions = 0`, and passes. The bug is gone from the database and was never seen. The decrement subtracts 2 and leaves 1; the same check reads `sum(used_count) = 1, expected 0` and fails, pointing at a counter that outran its ledger. The harness's comment says it in one sentence: *a cleanup that makes the baseline true is not a cleanup; it is a test that cannot fail.* It is the same discipline as the `supplier_keys` un-claim two statements later, which clears only the request ids the test derived and never `claimed_by_request_id IS NOT NULL` wholesale.

The proofs were run against a live database with rows written by SQL. Two orders, two `LIMIT3` redemptions, counter 2 → CTE → 0 / 0. Three, three, counter 3 → CTE with two of the three ids → 1 / 1, the third row surviving. **Drift preserved**: counter 3 against a ledger of 2 → CTE on both → counter 1, ledger 0, where a recompute would have written 0. And the reverse drift — counter 1 against a ledger of 2 — makes the decrement try to write `−1` and `promo_codes_used_count_range`'s lower bound fires. That lower bound exists for this: an over-decrement raises here, loudly, instead of leaving a negative count for the next baseline to explain.

The baseline reads the counter with `coalesce(sum(used_count), 0)` for a reason that is easy to skip. `sum()` over an empty table is `NULL`, and `NULL::int` is still `NULL` — a `null` arriving in a field the interface types as `number`. Whether it slips past a zero check depends only on how the check is spelled (`null !== 0` is true; `Number(null)` is 0): the type is a lie and the verdict an accident either way. `coalesce` makes an empty table an honest 0 and leaves `promo_codes = 0` to report the emptiness as the problem it is. And `assertBaseline` reports the counter and the ledger as two lines, so a drift is visible as *which one* moved rather than folded into a figure that could be right by coincidence.

## 4. What the tests prove, and how each was shown able to fail

**The unit file — 13 cases, written first.** `computeDiscount` is `Math.round((amount * value) / 100)` for `percent` and `Math.min(value, amount)` for `amount`; `normalisePromoCode` is trim, then upper-case, with the empty result returned as `null`. The expected values are transcribed from the functional spec, not computed in the test, for the reason the harness states — a test that imported the arithmetic it is meant to catch a mistake in cannot catch that mistake. Two REDs. Before the modules existed: `Cannot find module '../../src/promo/promo-code.js'`. With the mutant `discount = 0` in place: **8 failed** — the four seeded examples (`116100 → 129000`, `79000 → 129000`, `96750 → 129000`, `64500 → 129000`), the clamp (`30000 → 0`), R8's non-exact case (`2500 → 0`), and the two remaining rounding cases — while the five normalisation and kind cases stayed green under it, as they should: they do not touch the arithmetic, and a RED that turned them red too would be a RED that proves too much.

Two of the thirteen deserve a sentence. `discountMinor` is the *applied*, clamped discount — a 500 ₽ code on a 300 ₽ order reports 300 — so `list = to_pay + discount` holds on every ledger row including the one where the shopper pays nothing, and the redemptions CHECK `discount_minor <= list_amount_minor` accepts it. And the expression multiplies first and divides last: `amount` is a Postgres `integer` and `value ≤ 100`, so the product is an exact integer below 2⁵³, division by 100 is correctly rounded, and an exact half arrives at `Math.round` as an exact `.5`. Written the other way, `amount * (value / 100)` begins from `0.1`'s inexact representation and hands `Math.round` a value *near* a half rather than *at* one. The 10 % of 5 kopecks → 1 case is the one that separates half-up from banker's rounding and from truncation; the four seeded amounts on 1 290 ₽ cannot tell the three apart.

**The schema — seven negative proofs, each inside a transaction that was rolled back.** A constraint is proven by trying to violate it, not by reading the migration:

| Attempt | Refused by |
| --- | --- |
| `limit3`, lower-case, as a code | `promo_codes_code_normalised` |
| An `amount` code with `currency NULL` | `promo_codes_currency_iff_amount` |
| `used_count 2` against `max_uses 1` | `promo_codes_used_count_range` |
| Two redemptions on one order **with different codes** | `promo_redemptions_pkey` — the row `UNIQUE (promo_id, order_id)` would have admitted |
| A redemption naming an `order_id` that does not exist | the FK to `orders` |
| `discount_minor` greater than `list_amount_minor` | `promo_redemptions_discount_range` |
| Two sessions inserting a redemption for the same order concurrently | session B **blocked 1 472 ms** on A's uncommitted row, then failed on the PK after A committed — exactly one row survived |

The last is the one to hold on to. A unique index does not make the second inserter fail immediately; it makes it *wait* for the first transaction's outcome, and then fail or proceed depending on whether that outcome was a commit or a rollback. That is the same queueing the I7 counter relies on, seen from the ledger's side — and in production the order lock settles the race one statement earlier, so the PK is the proof that the lock discipline held, not the mechanism.

**The harness — the CTE proofs of §3.3**, plus the full suites in R13's order: `pnpm test:e2e` first (58 tests in 49.9 s, with the duplicate cleanup), then `pnpm test` (12 files / 103 tests for the API suites, 5 files / 56 for the web unit suite), green, with the baseline reading 4 / 0 / 0 after. That order is the point: the e2e's buy-throughs create orders the API suites will refuse to run beside, so the API suites' baseline passing after the e2e is what proves the e2e's cleanup restored it.

## 5. Findings

### 5.1 The migrator splits on a substring, comments included

drizzle-orm's pg migrator does not parse SQL. It splits each file on the literal text of its statement separator, wherever that text appears — inside a `--` comment as much as at the end of a statement. The first version of `0006`'s header described the separator by quoting it in a sentence. The migrator cut the file at that word: everything before the quote became one chunk, and the tail of the sentence — no longer behind a `--` — became a second chunk sent to Postgres as SQL. The whole migration transaction rolled back with a syntax error naming the second half of a comment. The header now describes the separator without spelling it, and warns the next annotator in its own first paragraph. Checked while writing this: the separator appears on lines 210, 270, 290 and 291 of the file, where drizzle-kit put it, and nowhere in a prose line.

### 5.2 The seed failed, but not loudly

Proof (b) is what surfaced it. The seed's `catch` printed `error.message`, which for a `DrizzleQueryError` is the *query text and its parameters* — the constraint that refused lives one level down, in `error.cause`, the driver's `DatabaseError` with `code` (`23514`), `constraint` and `detail`. So a seed that lowered `max_uses` below a live count failed, correctly, while saying nothing about which invariant refused — which is the whole reason every constraint in `packages/db/src/schema` has a name. `describeFailure()` now walks the cause chain up to five levels and prints code, constraint and detail beside each message. The one-line `catch` is the diff's one deletion in that region.

### 5.3 The new assertion caught a write it was not told about

While the harness task was running its own proofs, `assertBaseline("before")` failed with `promo_codes sum(used_count) = 2, expected 0`. Nothing in the task had written that. Another agent's proof — the schema task's two-session test — was mid-flight against the same local Postgres. The same fact Phase 4 §6.4 recorded from the API suites' side (`orders = 55`) and R13 records from the e2e's side, now seen from the new rows: one database, one baseline, one runner at a time. Two 30-second timeouts followed under a machine load of 25–35 from unrelated processes; an abandoned `finally` stranded one order, which was cleaned with the harness's own statements rather than by hand.

### 5.4 `serial`, not `bigint`

The older shop tables use a `bigint` identity. `promo_codes.id` is `serial` — a plain `integer` — because the technical spec declares the ledger's `promo_id` as `integer`, and a foreign key's two ends must be the same type. Four rows do not need 64 bits, and a mismatch would have been a migration error rather than a design choice. It is recorded in the schema and the migration so nobody "fixes" it toward consistency and breaks the FK.

## 6. Interview questions this answers

**"Why two columns? `count(*)` over the redemptions table *is* the used count."**
Because I7 needs a row to lock, and a count is not a row. Under `READ COMMITTED`, twenty transactions counting the ledger each see their own snapshot — `2` — and all twenty insert. The `promo_codes` row is the thing they queue on: `UPDATE … SET used_count = used_count + 1 WHERE id = $1 AND used_count < max_uses RETURNING` is the read and the write in one statement, and each transaction in the queue re-evaluates the `WHERE` against the row as the previous one committed it. The fourth sees `3` and matches nothing. The ledger is the other half — who spent a use, at what price, for how much — and I8's key. Two columns that must agree, and the agreement is asserted, never enforced by copying.

**"Then why keep the ledger at all? The counter is the mechanism."**
Because the counter cannot say *which* order got through. I8 — one redemption per order — needs something to key on, or a retried apply on the same order increments twice. The list price and the applied discount need columns, because "the record of what was paid does not change after the fact" is a property of storage, not arithmetic. And the harness needs to hand back exactly what a test spent, which requires knowing what it spent. The ledger's `PRIMARY KEY (order_id)` is also the order view's join key, so the `LEFT JOIN` is 1:0..1 by construction.

**"Your seed runs on every `pnpm dev:stack`. Why doesn't it reset the counters?"**
Because it cannot tell a developer's clean slate from a running shop with live orders, and the ledger would still hold every redemption the counter forgot. The emitted `ON CONFLICT ("code") DO UPDATE SET` names `kind`, `value`, `currency`, `max_uses` and stops; `used_count` gets the `DEFAULT` keyword on insert and is never in the `SET`. Proven both ways: set `ONCEONLY.used_count = 1` and `LIMIT3.max_uses = 99` by SQL, re-seed → `0 inserted, 4 updated`, `LIMIT3` back to 3, `ONCEONLY` still 1. And lower a limit below a live count → `promo_codes_used_count_range`, the whole transaction rolled back, products still 12. Loud is correct there; `least(used_count, excluded.max_uses)` would have forgotten redemptions silently.

**"Why does the test cleanup subtract instead of just recomputing the counter from the ledger? Recomputing is always right."**
That is exactly the problem. A recompute makes the after-run baseline true whatever happened during the run. If the application drifted — counter 3, ledger 2, which is what a broken rollback in the redemption transaction looks like — the recompute writes 2, the delete brings it to 0, and `assertBaseline("after")` passes on a bug it just erased. The decrement subtracts the two rows the test removed and leaves 1, and the assertion fails with `sum(used_count) = 1, expected 0`. Run live: counter 3 against ledger 2 → CTE → 1 / 0, where a recompute would have written 0. A cleanup that makes the baseline true is not a cleanup; it is a test that cannot fail. Same discipline as the `supplier_keys` un-claim, which clears only the request ids the test derived.

**"You have `CHECK (used_count <= max_uses)`. Isn't that the limit? Why the conditional UPDATE?"**
The CHECK is a backstop, and it hides a broken guard. Weaken the increment to an unconditional `used_count + 1` and run twenty redemptions of a three-use code across four processes: the fourth does not write `4` — it trips `23514 check_violation`, its transaction aborts, and the API answers 500 with the counter reading `3`. A test that asserts `used_count = 3` stays green with the mechanism gone. That is Phase 2's lesson — a UNIQUE index masking a broken lock — wearing a CHECK constraint. So every proof of the limit asserts the shape of the refusals — exactly N × 200, the rest × 409 exhausted, zero 5xx — and the ledger rows, and the counter only in addition. The CHECK still earns its place: it holds when TypeScript is bypassed, and its lower bound is what turns an over-decrementing cleanup into an error instead of a negative count.

**"The architecture said `UNIQUE (promo_id, order_id)`. Why did you change it to `PRIMARY KEY (order_id)`?"**
Because the original admitted a row the functional spec forbids: two *different* codes on one order, a second discount on an already-discounted price. One code per order means the key is `(order_id)` alone. The stronger key implies the weaker — a table with at most one row per `order_id` has at most one row per `(promo_id, order_id)` — so everything I8 was written to guarantee still holds, and `architecture.md` carries the amendment inline in three places. The negative proof was the row the old key would have accepted: two redemptions on one order with different codes → `promo_redemptions_pkey`.

**"Why round half up? Why not banker's rounding, or truncate?"**
Half up is what a price tag says — 967,50 ₽, never 967,4999 — and what a shopper checking the figure on paper reproduces. `Math.round` does it for non-negative input. The brief is silent (R8), so the unit test pins the cases that can tell the modes apart: 25 % of 9 999 kopecks → 2 500 (2 499,75 up), and 10 % of 5 kopecks → 1 (0,5 up — banker's and truncation both give 0). The four seeded amounts on 1 290 ₽ are exact and cannot distinguish anything. And the expression multiplies before it divides, so the product is an exact integer below 2⁵³ and an exact half reaches `Math.round` as an exact `.5` rather than something near it.

**"Why `coalesce(sum(used_count), 0)`? The table always has four rows."**
It does today. `sum()` over zero rows is `NULL`, and `NULL::int` is still `NULL` arriving in a field typed `number` — whether that passes a zero check depends on how the check happens to be spelled. `coalesce` makes an empty table an honest 0 and leaves `promo_codes = 0` to report the emptiness as the actual problem. The same reason the baseline reads counter and ledger as two lines: a drift should be visible as which one moved, not folded into a figure that could be right by coincidence.

**"What did you find that wasn't in the plan?"**
Four things. drizzle's migrator splits a migration file on the literal text of its separator, comments included, so a header that quoted the separator in a sentence cut itself in two and the tail was sent to Postgres as SQL — the whole migration rolled back; the header now describes the separator without spelling it. The seed's `catch` printed `error.message`, which for a `DrizzleQueryError` is the query text; the constraint name lives in `error.cause`, and `describeFailure()` now walks the chain. The new baseline assertion caught another agent's proof mid-flight with `sum(used_count) = 2, expected 0` — one database, one baseline. And `promo_codes.id` is `serial` rather than the older tables' `bigint`, because a foreign key's two ends must match and the ledger's `promo_id` is an `integer`.
