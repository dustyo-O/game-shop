## 2. The words this document uses

- **Suite / layer** — one of the runners in §1's table. "Layer" is the `@layer` tag a file carries: `unit`, `integration`, `e2e`, or `script`.
- **Behaviour-level / feature-level** — a behaviour-level spec holds one acceptance criterion per `test()` and was written before, or RED-validated against, the behaviour it checks; a feature-level file walks the assembled path and a failure in it says "something broke", not which criterion. The `@regression` tag follows this line (§3).
- **Disposition** — one of five answers for a criterion in the coverage map: *covered* (an automated test asserts the criterion's own words), *covered with a caveat* (asserted, but not quite in its own words, or not at every layer the words name — the caveat says which), *verified by hand* (a person, a `curl` body or a screenshot, named), *a document*, or *not covered anywhere by name*. The last appears zero times in this table, and §5 says where the row the tech spec predicted for it went.
- **The counter and the ledger** — `promo_codes.used_count` and the rows of `promo_redemptions`. Two columns that must agree; every proof of a use reads both, because a `CHECK` can keep the counter right while the ledger, or the shoppers' responses, are wrong (R2).
- **The shape of the refusals** — exactly N × `200`, the rest × `409 { reason: "exhausted" }`, **zero 5xx**. The assertion R1/R2 require *first*; the counter and the ledger are corroboration, never the whole of the proof.
- **Baseline** — the seeded state `apps/api`'s harness asserts before and after every file, which this phase widened: `products = 12`, `supplier_keys total = 50`, `unclaimed = 50`, `orders = 0`, zero rows in `payment_events`, `deliveries`, `issuance_attempts`, `supplier_requests`, and now `promo_codes = 4`, `coalesce(sum(used_count), 0) = 0`, `promo_redemptions = 0`. R13 is the requirement that the e2e and the race check hand this state back — by *decrementing* each code by exactly the rows they delete, never by recomputing.
- **R6's window** — the one simulated-provider round trip between `PaymentSimulatorService`'s un-locked read of `orders.amount_minor` and the webhook's `markPaid`, inside which a code applied to a still-`created` order is applied to a list-price payment. Documented in `architecture.md` §9 as open by decision; §5 says why nothing tests it.
- **Inversion** — the RED method for an assertion added after the behaviour exists: point it at the wrong state, run, read the failure, restore. Never a change under `src/`. Both tests this slice wrote were proven this way (§6).
- **Load** — the one-minute load average `uptime` prints, recorded beside every run in this document, because two of the day's three failures were load, not code (§7).

## 3. What the suite is for

### Four kinds of evidence, because one claim has four parts

The phase makes two claims — a limit that holds under parallel requests, and a price only the shop decides — and every suite proves a different part of each. This section is the sentence per suite that the brief asked for: what it proves, and what it cannot.

**About the limit.**

- **The unit file proves the arithmetic and nothing about a row.** `promo-discount.test.ts` — 13 cases: the four seeded amounts on 1 290 ₽, `GG500` clamped on a 300 ₽ order, three kopeck-rounding cases, the two kinds the schema's `CHECK` admits, and `normalisePromoCode`'s four. It has no database and no request; it cannot say anything about a use being counted.
- **The acceptance file proves the transaction's refusals and the ledger on one instance, and cannot show the race.** `promo-codes.test.ts` on 5301: the four amounts with `promo` set and `list_amount_minor = 129000`; `nope` → 422; ` limit3 ` stored as `LIMIT3`; the same code twice → 200 and one row; a different code → 409 `another_code_applied`; eight malformed bodies → 400; no such order → 404; a delivered order → 409 `not_awaiting_payment`; the abandoned order's use still counted. Its own header says what it cannot do: a `max: 1` pool serialises every transaction inside one process, so twenty callers from this file would queue in Node before Postgres saw a second I7 statement — "a queue test wearing a race test's clothes" — and **`exhausted` is not exercised here at all**. The budget makes that structural: every test that spends a `LIMIT3` or `ONCEONLY` use returns it in its own `finally`, and the busiest test spends one.
- **The four-process file proves the race, the shape of the refusals and zero 5xx — and, in its third test, the same-order lock.** `promo-limit-race.test.ts` on 5201–5204: `LIMIT3` ×20 across four processes → exactly 3 × `200`, exactly 17 × `409 exhausted`, zero 5xx, `used_count = 3`, the ledger's `order_id` set equal to the winners', the three winners at `96750` and the seventeen at `129000`, more than one backend pid; `ONCEONLY` ×10 → 1; one order, the same code ×4 → four identical `200`s, one row, the counter moved by one. Its header records the three weakenings that turn it red (§4's rows 2.4-3 and 2.5-3), including the one a counter-only test would miss: an unconditional increment produces `3 × 200, 17 × 500, 0 × 409` with `used_count = 3` and three ledger rows — every database-side fact correct, only the shoppers' responses wrong — and it is the "zero 5xx" line that catches it. What it cannot do is stand in for the reviewer's copy, and the reviewer's copy cannot stand in for it: with `FOR UPDATE` removed from `lockOrder`, this file's third test failed (`statuses=[500, 500, 500, 200]`) while **`pnpm race promo` stayed `passed`** — the check races distinct orders only and has no same-order scenario, so a missing order lock is invisible to it. The third test is the only guard for that case.
- **`pnpm race promo` proves the same thing in the reviewer's hands, and that it can be run twice.** `scripts/race/promo.ts` on 4601–4604: the same two scenarios, the same assertion set printed as `PASS`/`FAIL` lines by name, cleanup through the harness's decrementing CTE in `finally`, exit non-zero on any failure. This slice ran it back to back at 21:43–21:46 — `200: 3, 409 exhausted: 17` and `200: 1, 409 exhausted: 9` both times, `passed (600 ms)` then `passed (635 ms)`, and the sentence the deployed-target fallback prints ("counters reset through the admin endpoint") absent from both outputs. Against a shop whose database it cannot reach it falls back to `POST /api/admin/promo-codes/reset` and says so; locally it never does.
- **The browser proves the shopper's sentences and the row, not the limit.** `promo.spec.ts` on 5101 / 5102: the form before the payment controls, `LIMIT3 — скидка 322,50 ₽`, `967,50 ₽ (было 1290 ₽)`, the form gone, the URL and a pre-submit `window` marker intact (T1); «Такого промокода нет» with the field's value kept (T2); zero `POST …/promo` on an empty submit (T3); the same row after reload (T4); «Ключ выдан» with the row (T5); «Промокод больше не действует» on the second `ONCEONLY` order (T6); no field on a delivered order that never carried a code (T7). `used_count` is never read in this file — its header says so and says why: this layer proves the shopper's path, and its budget of three-plus-two uses is handed back after every test by the teardown, so no test can see another's. T6 is the shopper-visible half of scenario 5 (§8) and nothing more: one refusal in one browser, on `ONCEONLY`.

**About the price.**

- **The unit file proves `computeDiscount`**: percent → `Math.round(amount × value / 100)`, amount → `min(value, amount)`, to-pay ≥ 0, the applied discount clamped — `GG500` on 300 ₽ → 0 ₽ to pay and 300 ₽ off, not 500. This is the only place the clamp is observed (row 2.3-2).
- **The acceptance file proves the number reaches the payment row.** Its ninth test pays an order carrying `LIMIT3` through the simulator and reads `payment_events.amount_minor` directly — `96750`, not derived from the view — and then reads the delivered order on a fresh `GET` with `promo` intact. `PaymentSimulatorService.readOrderCharge` sends `orders.amount_minor`, the column the transaction repriced under the lock; the payment path did not change by a line.
- **The browser proves the page shows the server's number.** T1 reads `967,50 ₽` and `(было 1290 ₽)` from a page that computed neither — the form does not paint from its own response, it calls `onOrderMayHaveChanged()` and the poll's repaint shows what `GET /api/orders/:id` returned. T6 asserts `data-amount-minor="129000"` after a refusal: the page did not move the number on its own. The malformed-body test is the API half of the same fact — eight bodies that are not `{ code: string }` are refused `400` before the order is even looked up — and `parseApplyPromoRequest` returns `{ code }` and nothing else, so an extra `amount_minor` in a well-formed body has no path to the arithmetic by construction (row 2.3-1's note, corrected in §7).
- **Nothing tests R6's window.** §5 has the full paragraph; the short version: the window is one round trip inside a single unbroken call in `PaymentSimulatorService`, with no seam a test could use to land a `POST …/promo` between the read and `markPaid` without either mocking internals the shop keeps private or adding a timing hook production code has no reason to carry. The status guard closes every other ordering. It is open by decision, recorded in `architecture.md` §9 beside the admin reset, and the honest fix — compare `payment_events.amount_minor` to `orders.amount_minor` under the lock in the processor — changes the payment path and the fifty-webhook race's staged amounts, which functional spec §3 puts out of this phase.

### One database, one runner at a time — and now three things that must be handed back

All the suites share one Postgres on 5433, one 50-key pool and, since this phase, four promo counters and a ledger. Each asserts or depends on the baseline, so the order is fixed and this slice ran exactly it: `pnpm test:e2e` (65 in 57.8 s), then `pnpm race promo` twice (600 ms, 635 ms), then `pnpm test` (14 / 121 in 52.74 s; 6 / 69 in 234 ms) — with `orders 0 / sum(used_count) 0 / promo_redemptions 0 / unclaimed 50 / supplier_requests 0` read before the first step and after every one. Each later run's baseline is the proof the earlier one cleaned up: had the e2e leaked a `LIMIT3` use, the race test's precondition (`LIMIT3 unused before this test: expected 0`) would have said so; had the race check leaked one, the acceptance file's would have.

The mechanism is R13's pair of harness files moving together. `apps/api/test/concurrency/support/db.ts` and `apps/web/e2e/support/db.ts` both gained the three baseline rows and, before the `orders` delete, the CTE from tech spec §2.5 — delete this run's redemptions, decrement each code by exactly that count. Not a recompute from the ledger: a recompute would silently repair any drift between counter and ledger, and that drift is what `assertBaseline("after")` exists to catch. Slice 3's Shape A run showed the rule firing from the other side — the ledger outran the counter, the decrement tried to take nine from three, and the schema's lower-bound `CHECK` turned a `−6` into an error rather than a clean-looking baseline.

### Why `pnpm test:e2e` and `pnpm race` are separate commands

Unchanged from Phase 4, and this phase adds one reason: `pnpm race` takes a base URL, so the identical `promo.ts` runs against the deployed shop, where the check's fallback to the admin reset is the price of being able to run it twice with no database in hand. `pnpm test` is API then web unit and needs only Postgres; `pnpm test:e2e` builds the API and hands Playwright a config that owns 5101 / 5102 with `reuseExistingServer: false`, `workers: 1`, `retries: 0`.

### The `@regression` line, applied to five new files

The convention Phase 2's slice 8 set and Phase 4's slice 7 restated: the permanent, one-criterion-at-a-time guards carry the tag; the acceptance-level file does not. `promo-discount.test.ts`, `order-api.test.ts`, `promo-limit-race.test.ts` and `promo.spec.ts` carry it — each `it()`/`test()` is one criterion, written before or inverted against the behaviour; `promo-codes.test.ts` does not, for the reason `failure-and-recovery.test.ts` does not: a failure in it says the seam between transaction, controller and view broke, and the file to open is one of the others. `promo.spec.ts`'s header states this once, deferring to `e2e/support/orders.ts`'s directory-wide rule rather than re-arguing it.

**The seven caveats, and where the other half of each was actually verified.**

**R6's window — nowhere, and why.** The tech spec's §4 row for this slice expected a "not covered anywhere by name" row for R6, and the table has none, because R6 is a risk in the technical spec, not one of the functional spec's 31 criteria — it has no row to be uncovered in. It is instead the caveat on 2.3-3, and this paragraph is where it is said plainly. The window: `PaymentSimulatorService` reads `orders.amount_minor` without a lock and then delivers the webhook; a `POST …/promo` that lands on a still-`created` order between that read and the processor's `markPaid` is applied to a payment that carries the list price, and the processor never compares amounts — a Phase 1 decision, "settlement belongs to processing". What is left is one simulated-provider round trip inside a single, unbroken call, with no seam — no delay hook, no interception point, no event between the read and the webhook — that a test could use to land a promo inside it. Reaching it would mean mocking `PaymentSimulatorService`'s internals or adding a timing hook production code has no reason to carry, and either would be testing a system other than the one that ships. So it is documented in `architecture.md` §9 beside the admin reset, as a known trade-off with its honest fix named — compare `payment_events.amount_minor` to `orders.amount_minor` under the order lock in the processor and route a mismatch to `payment_failed` — and the reason that fix is not here: it changes the payment path and the fifty-webhook race's staged amounts, and functional spec §3 keeps the payment path out of this phase.

**§2.6, all three — a document.** `phase-5.md` is Slice 5's; its review against §2.6's criteria in two passes is ticked in `tasks.md`, and another agent is editing the document as this one is written. The browser watches one refusal arrive (T6) the way `buy-through.spec.ts` watches one key arrive; whether the refusal was the *right* one — the fourth and not the third — is the four-process file's, and no browser test can see four processes.

Neither touched `apps/api/src` or `apps/web/src`.

**1. An abandoned order's use still counts** — `promo-codes.test.ts`, the new `describe`:

## 7. Also worth including

**Two failures that were the machine, not the shop — what each was, what would close it, and why neither was closed here.**

*The e2e teardown raced the server's own continuation.* At 20:27 on 2026-09-14, a full `pnpm test:e2e` under a load average of 14–30 failed `buy-through.spec.ts` crits 1–2 on its 15-second `delivered` wait (`KEY_DELIVERY_TIMEOUT_MS = 15_000`): the simulated supplier call timed out under load — `IssuanceService` logged an `UNKNOWN outcome … TimeoutError` — and the order sat in `delivering`. ## Interview questions this answers

**"What does each suite prove about the limit?"**
The unit file proves the arithmetic — thirteen cases, no database — and nothing about a use being counted. The acceptance file proves, on one instance, that the transaction refuses in the right order and writes the ledger and the counter together — and it cannot see the race, because a `max: 1` pool serialises every transaction inside one process; `exhausted` is never exercised there, by construction. The four-process file proves the race: twenty simultaneous `LIMIT3` applications from four processes produce exactly three `200`s, seventeen `409 exhausted` and zero 5xx, with the ledger naming the same three winners the responses did — and its third test proves the same-order lock. `pnpm race promo` is the same proof a reviewer can run by name, twice in a row, from a clean baseline each time. The browser proves the two sentences a shopper sees and the row on the page, and never reads the counter. Each is blind to the others' subject, and the honest sentence is that only one of the five can see overlapping requests.

**"Why does the acceptance file not test the limit? It has the endpoint right there."**
Because twenty callers from one file hit one process with one connection, and the second transaction queues in Node before Postgres has seen a second statement. `architecture.md` §7 measured what that does to a broken guard: twenty distinct keys from one process with no locking at all, nine from four. A test that fires twenty requests at one instance is a queue test in a race test's clothes, and it would pass against a read-then-increment. So the acceptance file keeps its budget under every code's `max_uses` on purpose, says so in its header, and points at the four-process file.

**"Why is 'zero 5xx' an assertion of its own?"**
Because the schema's `CHECK (used_count <= max_uses)` hides a broken guard from any test that reads only the counter. Weaken I7 to an unconditional increment and the fourth transaction does not write `4` — it trips the CHECK, aborts, and the shopper gets a `500`. The counter reads `3`. Three ledger rows exist. Every database-side assertion passes. Slice 3 ran exactly that shape: `3 × 200, 17 × 500, 0 × 409`, and the only lines that went red were "17 × 409 exhausted" and "zero 5xx". A limit that holds by exploding in a shopper's face is not the limit the spec describes, and only the shape of the responses can tell the two apart.

**"What does each suite prove about the price?"**
The unit file proves `computeDiscount` — the four seeded amounts, the kopeck rounding, the clamp to zero. The acceptance file proves the number reaches the payment row: it pays an order carrying `LIMIT3` and reads `payment_events.amount_minor = 96750` directly from the table, then reads the delivered order on a fresh `GET` with the promo intact. The browser proves the page shows the server's number: `967,50 ₽ (было 1290 ₽)` on a page that computed neither, painted by the poll from what `GET /api/orders/:id` returned — and after a refusal the amount is still `129000`. Nothing the page sends but a code reaches the arithmetic: eight malformed bodies are refused before the order is looked up, and the parser returns `{ code }` and nothing else.

**"And nothing tests R6. Why not, and why is that acceptable?"**
The window is one simulated-provider round trip inside a single call: the simulator reads `orders.amount_minor` without a lock and delivers the webhook; a code that lands on the still-`created` order in between is applied to a list-price payment, and the processor never compares amounts. There is no seam a test could use to land a request inside that call without mocking the simulator's internals or adding a timing hook production has no reason to carry — and either would be testing a different system. The status guard closes every other ordering. So it is documented as an open trade-off in `architecture.md` §9 with its honest fix named — compare the two amounts under the lock in the processor — and the reason the fix is not here: it changes the payment path and the fifty-webhook race's staged amounts, which the functional spec keeps out of this phase. The table's caveat on 2.3-3 is where a reader finds it, and this document says it in full rather than letting a "covered" hide it.

**"The reviewer's check passed with the order lock removed. Is the check wrong?"**
It is blind to one case, and it says so. `pnpm race promo` races twenty distinct orders and then ten; the resource under contention is the counter, guarded by I7's row lock on `promo_codes`, and the order lock is not what serialises those. The same-order case — four requests for one order at once — is where `lockOrder`'s `FOR UPDATE` matters, and only the Vitest file's third test sends it: with the lock removed, three of four callers passed step 3 believing no redemption existed, and I8's `ON CONFLICT (order_id)` caught them as a `500` each. Adding the scenario to the script is in §9. A check that is honest about what it cannot see is worth more than one that claims everything.

**"Were the failures you saw today product bugs?"**
No, and each has a mechanism. Under a load average of 14–30 the simulated supplier timed out inside the browser suite's 15-second delivery wait; the shop treated the timeout as unknown, retried the same `request_id`, and refused to record a delivery for an order the test's teardown had meanwhile deleted — three correct behaviours in a row. What was wrong was the harness deleting an order the server was still working on. Under load 12–16, spec 002's race saw the ladder exhaust — 3 probes × 2 s × 2 suppliers — and settle `delivery_failed`, which is the right answer for a supplier that never answers and not the scenario the test was staging; at load ~9 it passed, and the tree's non-promo source changes are comment-only plus one function extraction. Neither fix is "raise the timeout" or "retry": the harness's own header says why the first is wrong, and `retries: 0` says why the second is. The fixes are a settle-wait in the teardown and a load preflight, both named and neither in this phase.

**"Did the exercise find anything?"**
Two criteria asserted by entailment — "an abandoned order's use still counts" and "no field on a paid order" — now asserted in their own words, each with an inversion that failed for the stated reason. A harness ordering gap that a loaded machine exposed and a quiet machine never would have. And a handful of drifts: two file headers one test behind their bodies, one architecture count one behind the tree, a stale caveat, and two rows whose wording claimed more than the test does.

**"What is still not done?"**
The settle-wait in the e2e teardown; a same-order scenario in the reviewer's check; R6, by decision; the clamp on a real order; the load preflight; three headers; and the things every phase has carried — a database per run and the root README.
