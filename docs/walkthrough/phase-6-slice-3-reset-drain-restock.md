# Phase 6 · Slice 3 — The demo can be reset, drained and restocked

> Nothing in this slice is deployed either, and — the standing rule of the phase — nothing about the shop's behaviour changes. What exists after it is the deployed demo's housekeeping: three routes, each behind the admin token, that a reviewer holding a public URL and no `psql` can use to put the shop back where the seed left it and to stage the one scenario that would otherwise cost fifty purchases. `POST /api/admin/demo/reset` removes every order and every row an order ever produced, releases every key claim, zeroes every promo counter and switches every supplier knob off, in one transaction, and answers with what moved. `POST /internal/suppliers/keys/drain` claims every unclaimed key under a run-scoped sentinel so the very next paid order meets an empty pool; `POST /internal/suppliers/keys/restock` releases exactly those sentinel claims and nothing else. `pnpm demo:reset` is the operator's spelling of the first; `pnpm race recover-out-of-stock` is the standing caller of the other two — on every run, locally too. All of it was proven against `pnpm dev`, a hand-spawned instance on port 5402, and a `psql` session holding locks on purpose.
>
> Three things carry the slice, and each is a decision about *where a guarantee lives*. **The reset is one transaction that takes every order's row lock before it deletes anything** — the same `FOR UPDATE` every writer of an order takes first — under a `lock_timeout` of five seconds, so work in flight on another instance either finishes first or arrives to find no row, and neither of the two half-states the spec forbids is ever visible to anyone. **Drain and restock live on the supplier's side of the boundary and mark what they take with a sentinel** — `drain_<token>_<id>`, released by `LIKE 'drain\_' || $1 || '\_%'` with the underscore escaped — because `supplier_keys` is the supplier's inventory, no shop module may import it, and a real claim begins `req_` and therefore can never match. **The out-of-stock check speaks HTTP everywhere**, with or without a database of its own, because a path exercised only against the live shop is a path local RED never sees.
>
> Reading the delivered work found three things and confirmed a fourth. The very first drain against the local stack answered `500 Connection terminated due to connection timeout` — Postgres had logged a 19.9 s checkpoint that minute; it is R14's shape, a socket dying under the 10 s connection timeout, reached from a Docker I/O stall rather than a frozen instance. The reset's `duration_ms` read 2.7–3.3 s while the verify task's suites ran at load 14, against 308 ms for a no-op and 1.16 ms of execution for the slowest statement under `EXPLAIN ANALYZE` — the number is the machine's, not the transaction's, and is to be re-timed. A `_` in a token would be a single-character wildcard *inside* the restock pattern, so the token's shape refuses it rather than escaping it. And the harness's cleanup still says, in two places, that nothing in `apps/api` ever clears a claim — which was true until this slice.

## 2. The words this document uses

- **Baseline** — the state the seed leaves: 12 products, 50 keys of which 50 unclaimed, 0 orders, 0 payment events, 0 deliveries, 0 issuance attempts, 0 supplier requests, 4 promo codes with 0 uses and 0 redemptions, 2 supplier behaviour rows with every knob off. The harness's `assertBaseline` reads eleven of those numbers; the reset's `now` reads the same eleven plus `supplier_behaviour_baseline`.
- **Reset** — the one transaction that returns a shop to baseline and reports what it removed and what it put back. It restores the fixture's *state*, not the fixture: `products` and the fifty `supplier_keys` rows are never touched, only the claims on the keys.
- **Half-state** — a shop that is neither reset nor whole, visible between two statements that were not in one transaction. Two of them are forbidden by the spec, and §4.1 names them.
- **The order lock** — `SELECT … FROM orders WHERE id = $1 FOR UPDATE`, the first half of invariant I4, which every writer of an order takes first inside its transaction (`order-lock.service.ts`). The reset takes it on every order at once.
- **`lock_timeout`** — the longest a statement will wait for a lock before Postgres cancels it with SQLSTATE `55P03`. Set `LOCAL`, it lives and dies with the transaction. The reset's is five seconds.
- **Demo affordance** — a route that changes what the shop will do next and exists for the deployed demo, never for the shop: the behaviour knobs, the promo reset, and now the demo reset, drain and restock. Each is behind the admin token, `POST`, `200`, logged at `warn`, and never called by a shopper's request.
- **The boundary** — the rule that shop modules never import `packages/db/src/schema/supplier.ts`, so the shop learns what its supplier holds only across HTTP. The four files that import a supplier table all live in `apps/api/src/suppliers/`; the reset writes those tables by the spec's own SQL text and imports nothing.
- **Sentinel** — the value `drain` writes into `claimed_by_request_id`: `drain_<token>_<id>`, distinct per row because the row's own `id` is appended and the column is UNIQUE.
- **Token** — the run's name inside the sentinel, minted as a `randomUUID()` when the caller sends none; `^[A-Za-z0-9-]{1,64}$`, so it can never carry a `LIKE` wildcard.
- **Real claim** — `req_{order_id}_{provider}_{attempt}`, the request id a supplier writes when it hands a key to an order. It begins `req_`; a sentinel begins `drain_`; no `LIKE 'drain\_…'` can reach it.
- **`\_`** — inside a `LIKE` pattern, `_` matches any one character and `\` is the default escape, so `\_` matches one literal underscore. `'drain\_'` matches the six characters `drain_` and nothing else.
- **Command tag** — the `DELETE 2` / `UPDATE 1` Postgres sends after every statement; `pg` exposes its number as `rowCount`. Every count in `removed` and `reset` is one of these.
- **`changed`** — `true` if any count in `removed` or `reset` is non-zero. Arithmetic over the tags, not a comparison of two snapshots, which is what lets a second run say `false` without reading anything twice.
- **SKIP by name** — the check's line for an assertion it could not make without `DATABASE_URL`: `SKIP <label> — needs DATABASE_URL`, with the same label the PASS or FAIL would carry, never counted as a pass.

## 3. Three routes, and who calls them

**The reset, from the operator's shell.** `RACE_BASE_URLS=http://localhost:3000 pnpm demo:reset` runs `scripts/demo-reset.ts` through `with-env.ts`, takes the first origin from `RACE_BASE_URLS` by the same `parseRaceBaseUrls` the race checks use, reads `ADMIN_TOKEN`, and sends one `POST /api/admin/demo/reset` with the bearer and no body. `AdminTokenGuard` answers `503` if the target has no `ADMIN_TOKEN` configured and `401` if the bearer is missing or wrong; both are printed with `describeMissingAdminAffordance`'s words and exit `1`. On `200` the script prints `removed.<table>` and `reset.<table>` one per line, or `already at baseline — nothing removed, nothing reset` when `changed` is `false`, and then one `now:` line with the twelve numbers. The controller's part is the guard, the status code and one `warn` line with every count; the transaction is the service's, and §4.1–§4.3 are about it.

The smoke, from the task's transcript against `pnpm dev`: order 1 with `LIMIT3` applied, paid, `delivered` with key `LFXC-TNCS-BPCD`; order 2 left `created`. The first reset answered `removed { orders 2, deliveries 1, issuance_attempts 1, promo_redemptions 1, payment_events 1, supplier_requests 1 }`, `reset { promo_codes 1, supplier_keys 1, supplier_behaviour 0 }`, `changed true`, and `now` at baseline — 12 / 50 / 50 / 0 … / 4 / 0 / 0 / 2. The second reset answered every count `0` and `changed false`. After `PUT /internal/suppliers/a/behaviour {"fail_next":1}`, a reset reported `supplier_behaviour 1` — the one armed row, and only that one.

**Drain and restock, from the check.** `pnpm race recover-out-of-stock` mints `race-recover-oos-<uuid>` as its token, sends `POST /internal/suppliers/keys/drain { token }` to its first target and reads back `{ token, claimed }`; pays an order and watches `GET /api/orders/:id` settle `out_of_stock`; sends `POST /internal/suppliers/keys/restock { token }` to its *second* target and reads `{ released }`; presses the operator's retry and watches the order reach `delivered`. Drain on one instance and restock on another is deliberate: the sentinel lives in `supplier_keys`, so any process can undo what any other did, and the check says so by doing it. Its `finally` restocks by token once more whenever the drain answered `200`, so an interrupted run never leaves the pool empty — the route answers `released: 0` to a second restock, which its header says is never an error.

The smoke, from the task's transcript: a real claim made first, so the pool read 49 unclaimed; drain → `claimed 49`; a paid order settled `out_of_stock`; restock → `released 49`, and the real claim `req_ord_…_a_1` was still there. Bodies of `{"token":"a_b"}`, `{"token":"a%b"}` and one with an unknown field each answered `400` naming the rule.

**The reviewer, against the live shop.** The same three requests by `curl` with the demo token from the README, which is the only way to stage the empty pool, or to start over, on a database they cannot reach. Slice 5 records that run; this slice makes it possible.

## 4. The five decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision.

### 4.1 The reset is one transaction

**What.** `database.transaction(async (tx) => …)` — `BEGIN`, twelve statements, `COMMIT`, or `ROLLBACK` if any of them throws; isolation `READ COMMITTED`, the server default, because the argument needs row locks and a single commit and nothing more. The five deletes go dependents first, so no statement trips a foreign key: `deliveries`, `issuance_attempts`, `promo_redemptions` each reference `orders.id`, and `promo_redemptions` also references `promo_codes.id`, which survives; then `payment_events`, which has no FK by design; then `orders`. Then the three resets, each with a `WHERE` that matches only rows not already at baseline, so their counts mean *rows that had moved*. Then the baseline read, last, so it sees every row the transaction removed and nothing anyone commits afterwards.

**The obvious alternative.** Twelve autocommitted statements in a row, which is what the same SQL does when pasted into `psql` without `BEGIN`. Or, faster and shorter, `TRUNCATE orders, deliveries, issuance_attempts, promo_redemptions, payment_events, supplier_requests` in one statement.

**What goes wrong with the alternative.** Between any two autocommits a request on another instance sees a shop that is neither reset nor whole, and two of those shops are the ones the spec forbids in as many words. *Orders gone, keys still claimed*: `DELETE FROM orders` committed and `UPDATE supplier_keys` not yet run leaves keys held by `req_<order>_…` for orders that no longer exist, and since no production path ever releases a claim, the demo has lost that stock permanently with no row left to explain why. *Keys released, deliveries still standing*: the other order, `UPDATE supplier_keys` committed and `DELETE FROM deliveries` not yet run, and a shopper reloading `/order/<id>` sees a key that is at that instant back in the pool and claimable by the next paid order — the exact thing invariant I6 exists to make impossible, made true for a moment by the tool meant to restore it. Inside one transaction neither shop is visible to anyone: every other transaction sees the rows as they were before `BEGIN` or as they are after `COMMIT`, and a lock timeout or an FK refusal anywhere rolls the whole thing back to the former. The response is then "it happened" or "it did not", never "some of it did".

`TRUNCATE` fails on three counts the header lists. It takes `ACCESS EXCLUSIVE`, which blocks even plain `SELECT`s on those tables for the transaction's life — every shopper's status poll and every webhook's insert on every instance would queue behind it, where row locks stall only writers of the rows being removed. It reports no counts, and the whole body of the response is counts. And it cannot be scoped: it would not wait on an in-flight order's row lock the way `FOR UPDATE` does, it would queue behind every reader and demand `CASCADE` to follow the FKs it was not told about.

The FK is also the reset's own backstop. An order created *and* redeemed on another instance in the gap between `DELETE FROM promo_redemptions` and `DELETE FROM orders` makes the latter refuse on `promo_redemptions_order_id_orders_id_fk`, which rolls the whole transaction back rather than leaving an order with no ledger row. That is the database refusing the inconsistent ordering; a re-run is the answer.

### 4.2 It takes every order's lock first

**What.** The second statement, before a single row is deleted:

```sql
SET LOCAL lock_timeout = '5s';
SELECT id FROM orders ORDER BY id FOR UPDATE;
```

`FOR UPDATE` on an order row is the lock the application takes first — `order-lock.service.ts`, the first half of I4: a payment continuation, the inbox drain, the promo redemption, the operator's retry, each opens its transaction with `select … from "orders" where "orders"."id" = $1 for update` and does every write after it. Taking every one of those locks here, before anything is deleted, turns a race into a queue.

**The obvious alternative.** Skip the lock. Every write in the shop is already guarded — `UPDATE … WHERE status = 'paid'` — and a `DELETE` is a write like any other, so let the deletes take their row locks as they go, the way a `DELETE` does anyway.

**What goes wrong with the alternative.** The reset becomes consistent but not decisive. Take a worker inside its second transaction on order X — it has locked X, is inserting X's `deliveries` row and writing `delivered`, and has not yet committed. The reset's `DELETE FROM deliveries` runs first and cannot see the uncommitted row; its `DELETE FROM orders` then reaches X, queues on the worker's lock, and when the worker commits finds a `deliveries` row referencing X — the FK refuses, and the whole reset rolls back with a `500`. The database has kept the shop consistent, which is what the FK is for, but the operator has been told nothing except "try again", and the counts the reset would have reported described a set of orders that was never fixed at any one moment. Taking every order's lock first turns that refusal into a wait: the reset blocks at its second statement until the worker commits, then sees every committed row and deletes it cleanly — the set of orders it acts on is fixed before the first delete, and everything below the lock is about rows nobody else can be writing. A worker that arrives *after* the reset holds the row queues behind it, and when it gets the row the row is gone — its own `FOR UPDATE` matches nothing, its guarded `UPDATE` matches nothing, and it reports `order_not_found`, exactly as it would for a webhook naming an order that was never created. That path already exists because `payment_events.order_id` has no FK — it is the webhook-before-order scenario — and the reset borrows it rather than inventing a failure mode. On another instance a promo redemption is the same story: it locks the order first, so it either finishes and is deleted, or finds no row and answers as if the order had never existed.

Two details are load-bearing. `ORDER BY id` is deadlock hygiene — every application transaction holds at most one order lock, so it can never be waiting on the reset while the reset waits on it, and sweeping in primary-key order keeps that true even if a future path locks two. `SET LOCAL` is pooler hygiene — it is the only `SET` under `apps/api/src` and `packages/db/src`, and `LOCAL` means it dies with the transaction, before PgBouncer can lend the backend to anyone else; a session-level `SET` would leak a five-second lock timeout onto whichever request borrowed that backend next.

**The bound, measured.** `lock_timeout` is what keeps "the reset waits" from meaning "the reset waits forever" behind a transaction somebody left open. Every application transaction that holds an order lock is short by construction — the two-transaction bracket around the supplier call exists so that no lock is ever held across HTTP — so five seconds is generous for a healthy shop and a firm ceiling for a sick one. From the task's transcript, with `psql` holding `SELECT id FROM orders FOR UPDATE` in an open transaction for 8 s: the reset answered `500` after 5.20 s with `canceling statement due to lock timeout` (SQLSTATE `55P03`), the transaction rolled back, and nothing had changed. With the same lock held for 3 s: the reset queued, proceeded the moment the `COMMIT` landed, and answered `removed.orders 1`. That is the whole contract — wait, bounded; then either everything or nothing.

**The straggler R9 names.** A worker between its two transactions, awaiting the supplier, holds no lock at all; the reset runs, releases every claim, commits; the supplier then answers and the worker's second transaction claims a key as `req_<deleted order>_…` and fails on the missing order. The key stays claimed by nobody's order. A second `POST …/reset` releases it — the documented remedy: second run non-zero, third `changed: false`. Every guard is in the database, so either ordering is consistent; the reset does not try to be cleverer than that.

### 4.3 Deleting the promo ledger is honest here, and not in the promo reset

**What.** `DELETE FROM promo_redemptions` is the third statement, in the same transaction as `DELETE FROM orders` and `UPDATE promo_codes SET used_count = 0 WHERE used_count <> 0`.

**The obvious alternative.** Do what `POST /api/admin/promo-codes/reset` does and argues for at length: zero the counter, leave the ledger. Its header is explicit that the ledger is not test residue — a delivered order that paid 967,50 ₽ for a 1 290 ₽ item has its `promo` row, its «было …» price and its discount *only* there, and deleting it would leave a shopper's page showing a discount with no code beside it. "The counter is state; the ledger is history. Reset the one, never the other."

**What goes wrong with the alternative.** That argument is about a shop whose orders remain, and here they do not. The orders whose history the ledger was are deleted in the same transaction, so at `COMMIT` there is no delivered order left for a ledger row to describe, no `/order/<id>` page left to show `promo: null` on, and no books left to be short an entry. A ledger row that survived would reference an order that does not exist — which the FK on `promo_redemptions.order_id` would refuse in any case, so the alternative is not even expressible without dropping the constraint. Counter and ledger then agree at `0 = 0` by construction, which is the invariant `schema/promo.ts` states everywhere else in the shop, restored rather than broken. The promo reset cannot delete the ledger *because* it keeps the orders; the demo reset must delete it *because* it does not. Each argument is right for its scope, both controllers say so, and neither licenses the other: a future "clear the ledger but keep the orders" would be wrong in both files.

This is also why the two resets are two routes in two modules rather than one with a flag. `AdminModule`'s header argues it "still cannot write `orders.status` by any route" and touches storage for one `SELECT` and one one-column `UPDATE`; a six-table delete is what that argument excludes. `DemoModule`'s header says the opposite thing honestly — this module can write every shop table and both supplier tables, and that is the whole of what it is for — and a reviewer who wants to know what the admin token can destroy reads that file, which is short.

### 4.4 Drain and restock live on the supplier's side, and use a sentinel

**What.** Two routes under `/internal/suppliers/keys`, in `SupplierBehaviourModule` beside `PUT /internal/suppliers/:provider/behaviour`, behind the same `AdminTokenGuard`. Each is one auto-committed `UPDATE … RETURNING id`, read back from Drizzle's `.toSQL()` and quoted beside the call:

```sql
-- drain: $1 = the run token
update "supplier_keys"
set "claimed_by_request_id" = 'drain_' || $1 || '_' || "supplier_keys"."id"::text, "claimed_at" = now()
where "supplier_keys"."claimed_by_request_id" is null
returning "id"

-- restock, with a token; without one the predicate is  like 'drain\_%'
update "supplier_keys"
set "claimed_by_request_id" = null, "claimed_at" = null
where "supplier_keys"."claimed_by_request_id" like 'drain\_' || $1 || '\_%'
returning "id"
```

The count each route reports is the size of the `RETURNING` set of the statement that did the work. `0` is never an error on either: a drain of an empty pool and a restock of a token that held nothing both answer `200`, so a script's `finally` can always restock without asking first.

**The obvious alternative.** File them under `/api/admin/demo/` next to the reset — one prefix, one register, one module for everything that is "for the demo". And mark the drained rows with a fixed value, `claimed_by_request_id = 'drained'`, since all that matters is that they are not `NULL`.

**What goes wrong with the alternative.** The prefix is the boundary. `supplier_keys` is the supplier's inventory — "treat them as if they were in the supplier's own datacentre" — and the rule that makes every Phase 3 demonstration honest is that no shop module imports that schema: the shop discovers an empty pool by being *told* `out_of_stock` across HTTP, never by looking. A drain filed under `/api/admin` would have the shop holding a switch for its supplier's stock, the confusion the behaviour route already refused for the behaviour knobs, and the four files that import a supplier table would become five, one of them on the shop's side. The reset is the exception that proves it: it writes both sides *without importing the schema at all* — the spec's SQL text, under the seed's licence, in a module that exports nothing.

The fixed value fails on the first row. `claimed_by_request_id` is UNIQUE (I6), so `'drained'` on forty-nine rows violates it on the second; the row's own `id` has to be in the value, and `drain_<token>_<id>` is the shape that makes every sentinel distinct by construction. The token is what makes a restock *this run's*: two checks in a row, or an interrupted one followed by a fresh one, must never release each other's rows, and a UUID minted per drain is what keeps them apart. And the same UNIQUE index is the backstop under the concurrency argument below — the task's transcript shows it firing: a reused request id hit `supplier_keys_claimed_by_request_id_key` rather than succeeding quietly.

**Why a real claim can never match.** The whole of R15 is one escape. `'drain_'` as a `LIKE` pattern would match `drainX…` too, because `_` is the single-character wildcard; `'drain\_'` matches only the six characters `drain_`, because `\` is `LIKE`'s default escape. A real claim is `req_{order}_{provider}_{attempt}` and begins `req_`; no value of `$1` can make a pattern that begins with a fixed, escaped `drain\_` reach it, because the token is appended *after* the prefix. Under the default `standard_conforming_strings = on` the backslash inside a single-quoted literal is an ordinary character, so `LIKE` receives the five characters `drain\_` and does the escaping itself; the TypeScript spells it `\\_` because a template literal would otherwise swallow the backslash before Drizzle saw it. The task's transcript confirmed the negative directly: the real claim `req_ord_…_a_1` made before the drain was still there after the restock, by token and by the token-less sweep.

**The token's shape — the finding.** The prefix is escaped, but the token is not, and a `_` inside it would still be a wildcard *within* the sentinel namespace: a restock for `a_c` would also release a drain made as `abc`. Two runs' sentinels crossing is not a resold key — the fixed prefix still holds — but it is a token that means less than it says. The controller therefore refuses any token outside `^[A-Za-z0-9-]{1,64}$` with a `400` that names the rule, rather than escaping it on the way in: a silently rewritten token is one the caller no longer holds. A minted token is a `randomUUID()`, 36 characters of `[0-9a-f-]`, well inside the shape; the check's own is `race-recover-oos-<uuid>`, hyphens and never underscores. From the transcript: `a_b` → `400`, `a%b` → `400`, an unknown field → `400` naming it. One more spelling detail of the same kind: `null` in the restock's `SET` is written `sql\`null\`` rather than the JavaScript `null`, because Drizzle binds a JavaScript `null` as a parameter and the token would shift to `$3`, and the text a reader compares against `log_statement = 'all'` would no longer be the text the spec quotes.

**Concurrent with a real claim.** A real claim (`supplier-key-claim.service.ts`) locks one unclaimed row with `… order by "supplier_keys"."id" limit $2 for update skip locked` inside its transaction and then updates it. The two statements can overlap in either order and neither side double-claims. *Drain first*: the drain's `UPDATE` holds a row lock on every row it has written until its own commit; the claim's subquery *skips* locked rows — that is what `SKIP LOCKED` is for — so it never waits on the drain and never picks a row the drain holds; if the drain took every row, the subquery finds nothing and the supplier answers `out_of_stock`, which is the state the route exists to produce. From the transcript: with the drain's transaction held open, the claim's `SKIP LOCKED` subquery found nothing and the outer statement reported `UPDATE 0`. *Claim first*: the drain's scan arrives at the row the claim's transaction has locked and **waits** — a plain `UPDATE` queues, it has no `SKIP LOCKED` — and when the claim commits, `READ COMMITTED` re-evaluates the drain's `WHERE` against the row's new version: `claimed_by_request_id` is now `req_…`, `IS NULL` is false, and the drain leaves it alone. From the transcript: with a claim's transaction held open on its row, the drain blocked for 14.31 s until that transaction committed, then answered `claimed 47`, having re-checked `IS NULL` after the commit and left the claimed row where it was. The two writers partition the pool between them; the UNIQUE index stands underneath in case they somehow did not.

Restock has nothing to race: a real claim's subquery reads only rows `WHERE claimed_by_request_id IS NULL`, every row restock touches holds a `drain_…` value, so no claim can be looking at one; once restock commits, the rows are `NULL` and the next claim takes them in `id` order, as the seed intended.

### 4.5 The out-of-stock check speaks HTTP everywhere

**What.** `scripts/race/recover-out-of-stock.ts` drains and restocks through the two routes on every run, with or without `DATABASE_URL`. The database gates only its assertions: each is a `{ label, read }` pair kept as data, and without a database `assertViaDatabase` prints `SKIP <label> — needs DATABASE_URL` for each, with the same label the PASS or FAIL would carry, and never counts it. The spine — drain answers `claimed > 0`, the order settles `out_of_stock` and later `delivered` as `GET /api/orders/:id` reports it, restock answers `released === claimed`, the retry answers `delivered: true`, a second retry `409` — is a real PASS or FAIL against any target.

**The obvious alternative.** What the file did until this slice: direct SQL locally, copying the Vitest suite's fixture, and HTTP only when `DATABASE_URL` was absent — which is to say only in front of the reviewer.

**What goes wrong with the alternative.** A path exercised only against the live shop is a path local RED never sees. The README's RED table is the project's evidence that each check can fail for the reason it claims to guard; if drain, restock or the sentinel's shape broke, a check that fell back to SQL locally would keep passing here and fail only at the live address, with nothing in the tree to point at. One path, exercised by every run, is the only shape under which "this check passed locally" says anything about the deployed run. The cost is the SKIP lines: locally with a database the check makes 29 assertions; without one it prints 15 PASS and 15 SKIP by name, and the transcript without `DATABASE_URL` lists exactly the assertions the one with it would have made. The Vitest concurrency suites keep their SQL fixtures — they are single-database by design and own their rows; the check is the thing that has to work at a URL.

One observation from the transcript belongs here because it is R15 seen in the wild rather than in a test. A no-database run leaves its order on the target — the check says so in one INFO line rather than calling the whole-shop reset for one order — and that order is `delivered`, holding a real `req_…` claim. The next run, with the database present, drained `claimed 49` and restocked `released 49` around it: the sentinel took every unclaimed key, the pattern gave back every sentinel, and the one real claim on the pool was untouched by either.

## 6. Findings

### 6.1 The first drain died on a connection timeout, and it was the disk

The very first `POST /internal/suppliers/keys/drain` against the local stack answered `500 Connection terminated due to connection timeout`. The Postgres log for that minute has a checkpoint that took 19.9 s with `write=9.061 s` — the Docker volume stalling under the verify task's suites — and the pool's `connectionTimeoutMillis` is 10 s. Nothing in the route is at fault and every later call answered; the drain is one statement on an idle connection. It is recorded because it is R14's shape — a checkout racing a socket that cannot answer in time — reached from an I/O stall rather than from a frozen instance, and R14's mitigation ("keep 10 s and `pool.on("error")`; a one-shot retry only if observed on the first live runs") stands. A reviewer who sees this once against the live shop should read it as the environment, retry, and expect the second call to answer.

### 6.2 `duration_ms` was the machine's number, not the transaction's

The reset's `warn` line carries `duration_ms`, and during the smoke it read 2.7–3.3 s for a reset that removed two orders, against 308 ms for a no-op — while the verify task's suites were running and the load average was 14. `EXPLAIN ANALYZE` on the slowest statement, the behaviour update, showed 1.16 ms of execution and 42 ms of planning. The technical spec says "sub-second on a demo-sized database", and nothing measured here contradicts that; nothing measured here confirms it either, because the number was taken on a saturated host. §9 lists the re-timing.

### 6.3 An underscore in a token is a wildcard

Described in §4.4. The spec's escape covers the prefix and the sentinel's second underscore; the token between them was unescaped, so a `_` inside it would have been a single-character wildcard within the sentinel namespace. The fix is the token shape, `^[A-Za-z0-9-]{1,64}$`, refused with a `400` rather than escaped, and the check's own token is `race-recover-oos-<uuid>` for that reason. Not a resold key under any input — the fixed prefix holds regardless — but a token that could mean more rows than the caller drained.

## 7. What a reviewer might challenge

- **The schema says restocking a live pool is adding rows. Why unclaim at all?** Because the fixture is the fifty supplied keys and a demo that keeps adding rows is a demo whose baseline drifts: `assertBaseline` reads `keys_total 50`, the README will say fifty, and a reviewer's second run would find fifty-one. Adding rows is right for a *live* pool — a supplier restocks by receiving stock, not by forgetting who it sold to — and the schema still says so for every production path. The three exceptions are outside those paths and each is scoped so a delivered key can never be resold: the harness releases only the request ids the test derived, `restock` releases only `drain_…` sentinels, and the reset releases every claim only inside the transaction that has already deleted every `deliveries` row. The paragraph in `schema/supplier.ts` was amended to say exactly that rather than left to quietly stop being true.
- **Why not `TRUNCATE`?** §4.1. `ACCESS EXCLUSIVE` blocks every reader on every instance for the transaction's life; it reports no counts, and the response is counts; it cannot wait on an order's row lock and would need `CASCADE` to follow FKs it was not told about. Row-level deletes stall only writers of the rows being removed, and the table is tens of rows.
- **Why a whole-shop reset and not a per-order delete the reviewer can aim?** Because a partial reset is the half-state the service's header forbids, only smaller: an order removed while its promo use is still counted, or its key still claimed. The only consistent unit is "everything an order touched", and once that is the unit, "every order" is one lock statement and one predicate away, while "this order" needs the reviewer to know what the order touched — which is what the guarantees exist to spare them. The harness's per-order cleanup exists for the local suites, where the point is precisely to leave the application's residue visible.
- **Why the token? A drain could just mark rows and a restock could release every mark.** The token-less restock exists and does that. The token is for the case that actually happens — two runs of the same check in a row, or an interrupted run followed by a fresh one — where a restock that released *every* sentinel would undo the other run's drain mid-scenario. The token makes "this run's rows" a predicate rather than a hope, and the check's `finally` can restock exactly what it took whether or not anything else was drained meanwhile.
- **Why not fold the promo reset into this one?** Because they mean different things and one of them is already in use. The promo reset arms one check's re-run on a shop whose orders stay, and its whole argument is that the ledger survives; the demo reset arms a fresh start on a shop whose orders go, and its whole argument is that the ledger must not. Folding them would mean either a flag that turns a whole-shop delete into a one-column update — the `AdminModule` header's blast-radius argument, breached by a parameter — or a promo reset that deletes the ledger, which §4.3 says is wrong for its scope. Same token, same prefix, two modules, because the prefix says who may call and the module says what may be touched.
- **A whole-shop `DELETE` on a production URL, behind a published token — really?** Yes, and by decision (R16): the shop has no real shoppers, the reset is the remedy for any mischief, the README labels the token as the demo's, and it differs from the local default. The mischief a reader should actually worry about — a key resold, a counter drifting from its ledger — is the thing every one of these routes is scoped against; emptying the demo is the thing they are for.
- **Drain has no transaction. Isn't that a read-then-write?** No — it is one `UPDATE … WHERE … IS NULL RETURNING id`, atomic on its own, and the count is the size of its `RETURNING` set, not a `count(*)` taken beforehand. There is no window between a read and a write because there is no read. A transaction would add nothing but a second round trip on the instance's only connection.
- **`READ COMMITTED` for a twelve-statement transaction?** The header says why that is enough: consistency comes from the row locks and the single commit, not from the isolation level. `DELETE FROM orders` sees rows committed before it started, and a row inserted in the gap with a dependent already in place makes the FK refuse and the whole transaction roll back. Raising the level would paper over nothing that is missing.

## 8. Interview questions this answers

**"What does the reset do, in one breath?"**
One transaction: set a five-second lock timeout, lock every order row with `FOR UPDATE` in id order, delete `deliveries`, `issuance_attempts`, `promo_redemptions`, `payment_events`, `orders` in that order, zero every non-zero promo counter, release every key claim, delete the supplier's request ledger, switch every armed behaviour knob off, read the baseline, commit. Report each statement's command tag as `removed` and `reset`, `changed` as "any of them non-zero", and the baseline as `now`. A second run reports every count `0`, `changed: false`, and the same twelve numbers.

**"Why one transaction rather than twelve statements?"**
Because between any two autocommits another instance sees a shop that is neither reset nor whole, and two of those shops are forbidden: orders gone with keys still claimed by nobody — stock lost forever, since no production path ever releases a claim — and keys back in stock while a shopper's page still shows one, which is the thing I6 exists to make impossible. In one transaction neither is visible; a failure anywhere is a rollback to the shop as it was.

**"Why lock every order first? The deletes take their own locks."**
They do, but then the reset relies on the FK to refuse the interleavings it cannot see: a worker mid-transaction on one order makes `DELETE FROM orders` wait and then fail on the `deliveries` row the worker just committed, the whole reset rolls back with a `500`, and the operator is told nothing but "try again". `FOR UPDATE` on every row first — the lock every writer of an order already takes first — turns that refusal into a wait: the set of orders is fixed before the first delete, a worker inside its transaction finishes and is then deleted, and a worker arriving afterwards finds no row and reports `order_not_found`, the path that already exists because `payment_events.order_id` has no FK. `lock_timeout` bounds the wait: measured, a lock held 8 s made the reset fail after 5.20 s with `55P03` and change nothing; held 3 s, the reset queued and proceeded after the commit.

**"Why does this reset delete `promo_redemptions` when the promo reset refuses to?"**
The promo reset keeps the orders, so the ledger is still the record of what those orders paid — delete it and a delivered order shows a discount with no code beside it. The demo reset deletes the orders in the same transaction, so at commit there is no order left for a ledger row to describe, and counter and ledger agree at `0 = 0` by construction. Each is right for its scope and neither licenses the other.

**"Why are drain and restock under `/internal/suppliers` and not `/api/admin/demo`?"**
Because `supplier_keys` is the supplier's inventory, and the rule that makes every Phase 3 demonstration honest is that no shop module imports that schema — the shop learns the pool is empty by being told `out_of_stock` across HTTP. A drain under `/api/admin` would be the shop holding a switch for its supplier's stock. The reset does write both sides, without importing the schema, under the seed's licence as "the loader, not a participant"; a route that stages one supplier scenario has no such licence and needs none.

**"How can `restock` be sure it never releases a delivered key?"**
The predicate is `LIKE 'drain\_' || $1 || '\_%'`. `\_` is a literal underscore under `LIKE`'s default escape, so the pattern begins with the fixed six characters `drain_`; a real claim begins `req_` and no token appended after the prefix can reach it. The token itself is restricted to `[A-Za-z0-9-]` so it cannot carry a wildcard either. The acceptance test's RED is exactly the widening — `WHERE claimed_by_request_id IS NOT NULL` — and the line that goes red is the real claim's count: `expected 1 to be +0`.

**"What happens if a real claim and a drain run at the same instant?"**
They partition the pool. If the drain reached a row first, the claim's `FOR UPDATE SKIP LOCKED` subquery skips it and, with the pool empty, answers `out_of_stock` — measured as `UPDATE 0` against a drain held open. If the claim reached its row first, the drain's plain `UPDATE` waits on that row, and when the claim commits `READ COMMITTED` re-checks `IS NULL` against the new version and leaves it alone — measured as a 14.31 s wait followed by `claimed 47`. The UNIQUE index on `claimed_by_request_id` stands under both cases; a reused request id in the transcript hit `supplier_keys_claimed_by_request_id_key`.

**"Why does the out-of-stock check use HTTP locally when it has the database right there?"**
Because a path exercised only against the live shop is a path local RED never sees. If drain, restock or the sentinel's shape broke, a check that used SQL locally would keep passing here and fail only in front of the reviewer. So it uses the endpoints on every run and lets `DATABASE_URL` gate only its assertions — 29 with a database, 15 PASS and 15 SKIP by name without — and its RED row was re-run after the switch: 9 of 29, every one after the restock, with the staging untouched.

**"What did you find that wasn't in the plan?"**
That the first drain died on a 10 s connection timeout because Postgres was in a 19.9 s checkpoint — R14's shape from a disk stall rather than a frozen instance. That `duration_ms` at load 14 says nothing about the transaction, whose slowest statement executes in 1.16 ms. That an underscore in a token is a wildcard inside the sentinel namespace, hence the token's shape. And that the harness's cleanup still says nothing in `apps/api` ever clears a claim.
