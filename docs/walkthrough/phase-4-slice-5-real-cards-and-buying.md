# Phase 4 · Slice 5 — Real goods on real cards, and buying from the new page

> This is the slice where the face joins the engine, and the whole point of how it joins is that it joins by *not changing anything*. Купить on a card in the «Популярные товары» row is the same `<button type="button" data-sku>` the plain page carried, inside the same region the same delegated listener watches, and pressing it sends the same `POST /api/orders` with the same `Idempotency-Key` header minted by the same file. The order page, the payment simulator, the poll, the delivery, the operator's recovery screen, `apps/api`, `packages/contracts`, `packages/db` — none of them moved. The functional spec's scope line for this phase is *"where the shopper starts, not what happens after"*, and §3.1 takes that sentence literally: it lists what did not change and why the proofs of Phases 1–3 still stand as the proofs of this page. The live drive did the whole road once — Купить → `ord_01M2FR6QK83N46JVKE6STQJA6M`, «Ожидает оплаты», the success control, «Ключ выдан» about 2.4 s later — and the two screenshots in `docs/screenshots/` are the order page looking exactly as it did in Phase 3, because it is the Phase 3 order page.
>
> The second story is a field that spent three phases deliberately missing. `GET /api/products` has always sent `image`; the web parser dropped it at one line since Phase 1, with a comment saying why — the files did not exist, and constructing an `<img>` for a path that 404s would have put `net::ERR` lines in a console the reviewer was meant to find clean. This slice ships ten pictures at the very paths the seed already holds, reinstates the field as `readonly image: string | null`, and resolves it where it is shown rather than where it is parsed: `new URL(image, window.location.origin).href`. §3.2 explains why the two obvious one-liners — a leading-slash template and a plain relative `src` — are each a bug on a different route, and why a *missing* key on the wire is rejected rather than read as "no picture".
>
> The third is the phase's one edit to `features/buy-product`: 68 lines added, none removed, one file. `buy()` disables Купить and leaves it disabled while the navigation runs, and that is right for a page that is leaving — unless the browser's back/forward cache keeps the page and hands it back later, dead button included. On a persisted `pageshow` the feature re-enables its own buttons, and a second press is then a **second order, correctly**: the key that named the first purchase was forgotten the moment the first order existed, so the second press mints a new name for a new decision. §3.3 walks the sequence click by click and contrasts it with the two fixes that look simpler and are wrong. What no automated layer can reach — the cached restore itself — is still the one thing this slice cannot claim, for the third time this phase (§5.4).

## 2. The words this document uses

- **Idempotency key, purchase intent** — the `Idempotency-Key` header on `POST /api/orders`, stored as `orders.client_request_id` behind a UNIQUE index: the first request wearing a key creates the order, every later one wearing the same key is handed that order back (spec 002, architecture §3 I1). The value of the mechanism is decided by *what the key names*. In this shop it names an **intent** — "this shopper wants one copy of this SKU" — minted once per SKU in `features/buy-product/lib/purchase-intent.ts`, kept in `localStorage`, reused by a second click, a second tab and a retry after a failure, and **forgotten only when an order for it exists**. A key that named the click instead would let a double-click buy two copies while every server-side test stayed green (`phase-2-slice-1-one-order-per-intent.md` §3).
- **Origin, and a protocol-relative URL** — an origin is scheme + host + port: `http://localhost:5101`. A URL that starts with two slashes, `//assets/cs2.png`, is *protocol-relative*: it borrows only the scheme from the page and treats what follows the slashes as a **host** — here a machine named `assets`. It is a valid URL and the browser will try to reach it. This is the trap in §3.2.
- **Back/forward cache restore vs reload** — two ways the Back button can bring a page back. A **reload** builds a new document: scripts run from the top, `mountApp` runs, every button starts enabled, and `pageshow` fires with `persisted: false`. A **restore** (the "bfcache") hands back the *same* document the shopper left — same DOM, same JavaScript heap, same listeners, same `disabled` attributes — frozen at the moment of leaving, and `pageshow` fires with `persisted: true`. The navigation-timing entry's `navigationType: "back_forward"` says only how the shopper got there, not which of the two happened. Any attached debugging session — which every Playwright page has — makes a page ineligible for the cache, so automation only ever sees the reload.
- **Route interception** — Playwright's `page.route(pattern, handler)`: the test process sits between the page and the network for matching requests. The handler can `route.fetch()` the real response itself, read its body, and only then `route.fulfill()` it to the page — so the test has the order id in hand *before* the page's own `fetch()` resolves and `location.assign` can tear the document down. `e2e/support/orders.ts` does exactly this for `POST /api/orders`; a plain `page.on("response")` listener lost that race and left one orphan row (`phase-4-slice-1-the-structure.md` §6.2).
- **Stable partition** — splitting a list into two by a yes/no question and keeping each half in its original order, then joining the halves. It differs from a sort in two ways that matter here: it never reorders items within a half, and it does not touch the input. `Array.prototype.sort` with a comparator on `purchasable` would give the same five today, sorts in place, and reads as "sort by something" to the next editor.
- **The seed as the brief's fixture** — `packages/db/src/fixtures/catalog.ts` is the assignment's twelve-row catalogue transcribed verbatim, in the brief's order and units, so a reviewer can diff it against the brief line by line; its header calls it "a fixed input, not a design decision". Its `image` column already says `assets/steam.png`, `assets/cs2.png`, … — strings that were set before any file existed. Everything this slice ships was made to fit those strings; the strings were never edited to fit the art.
- **SPA fallback** — the dev server's rule that an unknown path is answered with `index.html` and status `200`, so that a client-side route like `/order/ord_…` loads on a refresh. Vite applies it when the request's `Accept` header admits `text/html` or `*/*`. §5.1 is about what that does to a missing image.

## 3. The three decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision — with the code fact beside the plain-language reason.

### 3.1 The storefront changes where the shopper starts, and nothing after

**What.** The connection between the new page and the engine is one line in `popular-products.ts`: `enableBuyControls(region)`, called once when the section is built, before the catalogue has arrived. Everything else is the card keeping a contract. `renderProductCard` puts the buy control on a purchasable card as `<button class="product-card__buy" type="button" data-sku="KEY-CS2-PRIME">Купить</button>`, directly inside `__body`, as the only element inside the card carrying `data-sku` on a `button` — and that is precisely what the feature's delegated listener matches (`button[data-sku]`), disables, and, on failure, inserts a `<p>` after and finds again through `button.parentElement`. The card's own `<li>` also carries `data-sku`, and the feature never matches it, because its selector names the tag.

From the click onward the path is Phase 1–3's, byte for byte. `buy()` clears any old message, sets `disabled`, calls `createOrder(sku, purchaseIntentKey(sku))` — the key read from `lib/purchase-intent.ts`, not minted in the handler — and on success forgets the key and `location.assign`s to `/order/<id>`. The order page reads the order, offers the two payment buttons, polls through `pages/order/model/poll.ts` until the status is terminal, and shows the key. The recovery screen, the supplier stubs, the webhook inbox, the issuance ladder: untouched.

What did **not** change, enumerated, because the claim is only worth making if it can be checked:

- `POST /api/orders` — same endpoint, same body, same `Idempotency-Key` header. `apps/api` has no diff.
- The key's minting and forgetting — `lib/purchase-intent.ts` has no diff; the feature's diff is 68 insertions and 0 deletions, all of them the `pageshow` section §3.3 is about.
- The order page — `pages/order` has no diff; the two screenshots in §1 are visibly the Phase 3 page.
- Payment and delivery — `features/simulate-payment`, the poll, the API's webhook and issuance code: no diff.
- `packages/contracts` and `packages/db` — no diff; the seed's `image` strings are as the brief wrote them.
- The API suites — `apps/api/test/**` has no diff, and `pnpm test` ran green immediately after the e2e (§4).

**The obvious alternative.** Several, all of the same family: give the storefront its own click handler on the card (it is right there, and the card is a new component anyway); or navigate to the order page with the SKU in the URL and let *that* page create the order, so the storefront never talks to the API; or send the product's name and price along so the order page need not fetch them. Each is a few lines and each reads as "the new page owns its own buying".

**What goes wrong with the alternative.** The first one puts a second place in the code that decides what an `Idempotency-Key` is. Phase 2's whole argument (`phase-2-slice-1` §3) is that the minting site *is* the mechanism: a key minted where the click is handled names the click, a double-click sends two names, and the server folds nothing while every `curl` test stays green. Two minting sites are two chances to get that wrong, and the second one would be in a file whose author was thinking about pictures. The second alternative moves order creation to a page the shopper can refresh, bookmark and open twice — the request would fire on every load of `/order?sku=…`, and the intent key that makes a refresh safe today would have to be reinvented there. The third makes the order page trust the address bar for a price. All three also do something quieter: they make the Phase 1–3 test suites stop being the proof of this page. Spec 002's races and spec 003's timeouts are proven at the API boundary against the request the plain page sent; if the storefront sent a different request, or from a different place, the concurrency proofs would apply to a path no shopper uses any more, and the browser suite — which cannot run fifty concurrent purchases against a supplier that stalls — would be asked to re-prove what it cannot.

That is what the functional spec's scope line means by *"where the shopper starts"*. The engine's guarantees are enforced at one boundary and proven there; the face's job is to start the shopper at the right place and then get out of the way. The reviewer's likely question — "what did you have to change on the purchase path to make the design work?" — has the answer "nothing", and the evidence is three empty diffs and a green `pnpm test` after the browser has bought a real key.

One consequence to say aloud: the double-click criterion (§2.7 crit 3) holds on the new page for the same two reasons it held on the old one, in the same order. First, `button.disabled = true` runs synchronously in the first click's handler, so the second click of a double-click lands on a disabled button and dispatches no event — the e2e counts **one** `POST /api/orders` after `dblclick`. Second, if a second request did get out (two tabs, a reload mid-flight), it would carry the *same* key, and the unique index would hand back the same order. The page provides the first; the database provides the second; the storefront added neither and removed neither.

### 3.2 `image`: dropped for three phases, reinstated, and resolved from any route

**What — the three phases.** `GET /api/products` has always emitted `image` for every row: `CatalogService` writes `image: row.image`, the column is `string | null`, and the seed fills it with `assets/<name>.png`. In Phase 1 the web parser read the row and did not carry the field into `Product`. The comment that stood at that line until this slice said why, and it is worth quoting because the reasoning was right at the time: *"The column holds paths like `assets/steam.png`; those files do not exist in this repository, and this deliberately plain page has no picture to show anyway. Dropping the field here means no `<img>` is ever constructed, so there are no 404s in the network panel and no `net::ERR` lines in the console. Phase 4 builds the real storefront against the Figma design, ships the artwork with it, and reinstates the field then."* Phases 2 and 3 changed nothing on the page and inherited the line. This slice is the "then".

Reinstated as `readonly image: string | null` — nullable because the column is, and a row without artwork is still a row to list. The reader is `readNullableString`: a string or JSON `null`, anything else a `CatalogResponseError` naming the field (`product.image: expected a string or null, got number` for `42`). The decision inside it is that a **missing** key is rejected, not read as `null`. The reasoning is about what `JSON.stringify` can and cannot produce: it omits a property whose value is `undefined` and never one whose value is `null`, and the API always sets the property. So a body without the key is not "a row with no picture"; it is a body that is not the one the endpoint promises — a renamed field, a different handler answering the same path — and it is rejected for the same reason `{"products": []}` is. Read as `null`, it would blank every card silently. `parseCatalogResponse(body: unknown)` is exported so the test can hand it bodies without a server; `fetchProducts` is now one line.

**What — the resolution.** The parser keeps the wire value untouched; turning `assets/cs2.png` into something an `<img>` can load is done in `product-card.ts`, in `imageUrl`:

```ts
function imageUrl(image: string): string {
  return new URL(image, window.location.origin).href;
}
```

`new URL(relative, base)` resolves a relative reference against a base the way the URL standard says to. With the base being the page's *origin* — `http://localhost:5101`, no path — `assets/cs2.png` becomes `http://localhost:5101/assets/cs2.png` whatever page the card is on. If a future row arrived as `/assets/cs2.png`, the same call yields the same address. If one arrived absolute, it is kept. One expression, three shapes of input, one correct output each.

**The obvious alternatives, and the two bugs.** Two one-liners look equivalent and are each wrong on a route the other is right on:

- *A leading-slash template*, `` src = `/${image}` ``. Right today: `/assets/cs2.png`. The day a row arrives already carrying its slash — a CDN path, a normalised seed — the template yields `//assets/cs2.png`, a protocol-relative URL to a host named `assets`. The browser does not treat it as a path; it tries to resolve a machine. Every card on the page loses its picture at once, and the console says `net::ERR_NAME_NOT_RESOLVED`, which is not a message anyone would connect to a string concatenation.
- *A plain relative `src`*, `src = image`. Right on `/`, where `assets/cs2.png` resolves to `/assets/cs2.png`. On `/order/ord_01M2…` it resolves against the document's *path* and becomes `/order/assets/cs2.png` — a 404 waiting for the first page other than the storefront to render a card. The order page does not render cards today; the bug would arrive with the first reuse of the entity, in a file nobody touched.

Resolving against the origin is the only choice of base that ignores the current path *and* survives a leading slash. And it is done in the card, not the parser, for a reason the tests make concrete: `products-api.test.ts` runs under Vitest with `environment: "node"` — there is no `window` there — and a parser that resolved against `window.location` would either need a browser to test or a fake `window` to lie to it. Kept pure, the parser is a statement about the wire; the resolution is presentation, and the entity's `ui/` is where presentation belongs.

**Around the `<img>`.** `alt=""` — the name is the `<h3>` beneath it in the same card, and an `alt` repeating it would read every product twice to a screen reader. `width="228" height="152"` — the box the browser reserves before the bytes arrive, so the row does not jump when they do; the stylesheet's `aspect-ratio` and `object-fit: cover` make the same box fluid inside the grid column (the drive measured it at 227 × 151, the grid's `minmax(227px, …)`). `loading="lazy"` because the row is the last block on the page, `decoding="async"` so a decoded bitmap never blocks the frame the blocks above are painting. A `null` image gives the `--empty` modifier from the start and no `<img>`, so no request. A string that fails to load — a renamed file, a typo in a future seed — fires the `error` listener, attached before `src` is assigned and `{ once: true }`, which adds the same modifier and removes the `img`: both roads end at the same CSS-drawn glyph, never at the browser's broken-image icon. The drive proved the fallback by pointing one card's `src` at a nonexistent path: `--empty` present, `hasImg: false`, box unchanged. It also noticed something about *how* that load failed, which §5.1 takes up.

**The pictures themselves.** Ten placeholders, not the mockup's art: the Figma card art is stock imagery for a game the catalogue does not sell, and putting it on a «CS2 Prime Status» card would mislead a shopper about what they are buying (tech spec §1 item 2, §2.7 "Rejected"). Each source is a 456 × 304 SVG — a flat panel, the brand word at 64 px, the Russian product name beneath at 24 px, `system-ui`, text only, no logos — with the fill keyed by SKU prefix: `STEAM-` navy `#1f2a44` (one file, shared by the three top-ups), `KEY-` slate `#2e3a48` (three), `SUB-` purple `#432b7a` (three), `GIFT-` green `#1d6b45` (three). They are rendered to PNG through the same Chromium the e2e installs, because ImageMagick draws text only with a font it is handed and Cyrillic plus «₽» would be tofu without one pinned into the repository; Chromium resolves `system-ui` through the OS. The script is deterministic on one machine — a re-run was byte-identical — and not across machines, which is why the PNGs are committed and the script exists for reproducibility rather than for every checkout. `magick -strip` at compression level 9 is tried when present and kept only when smaller; it beat Chromium's encoder on 3 of the 10 by 17–98 bytes. The output size is 2× the card's box so a high-DPI screen downscales and never upscales; the ten files weigh 102 011 B together, none of it in the JS bundle.

### 3.3 The one feature edit: re-enable on restore, and why a second press is a second order

**What.** At the end of `enableBuyControls(container)`, after the click listener that has been there since Phase 1:

```ts
window.addEventListener("pageshow", (event) => {
  if (!event.persisted) {
    return;
  }

  for (const button of container.querySelectorAll(`${buyButtonSelector}:disabled`)) {
    if (button instanceof HTMLButtonElement) {
      button.disabled = false;
    }
  }
});
```

The selector narrows to `:disabled`, so an enabled button is not touched; the `instanceof` is the same line the click path uses to turn an `Element` into something with a `disabled` property; the listener is never removed because the app has no unmount and a cached page keeps its listeners along with everything else — which is exactly what lets `pageshow` find it. That is the entire change: 68 lines added, 56 of them comment (the header section and the note above the listener) and 12 of them code, 0 deletions.

**The sequence, click by click.** This is the part to be able to say unaided, because the correctness of the edit is the correctness of the whole chain.

1. The shopper clicks Купить on CS2. The delegated listener finds `button[data-sku]`, reads the SKU, calls `buy(button, "KEY-CS2-PRIME")`.
2. `buy()` clears any old message and sets `button.disabled = true` — **synchronously**, before any `await`. A second click in the next few hundred milliseconds lands on a disabled button and dispatches nothing.
3. `purchaseIntentKey("KEY-CS2-PRIME")` reads `localStorage`; nothing is there; it mints a UUID, stores it under `game-shop:purchase-intent:KEY-CS2-PRIME`, returns it. `createOrder` sends `POST /api/orders` with that UUID as `Idempotency-Key`.
4. The response arrives with an order id. `forgetPurchaseIntent(sku)` removes the stored key — a synchronous storage write, on the line *before* the navigation, at the one moment an order for this intent is known to exist (spec 002's argument for exactly this event and no other: earlier breaks the retry-after-failure criterion, later breaks the buy-again criterion).
5. `window.location.assign("/order/ord_…")`. The button is **still disabled**, deliberately: re-enabling here would put a live Купить in front of a shopper for the duration of the navigation, and a click on it would — because step 4 already ran — mint a new key and buy a second copy. The feature's header has said this since Phase 1. The disabled button is meant to leave with the document.
6. *With the cache:* the browser does not discard the document. It freezes it — DOM, heap, listeners, the `disabled` attribute — and puts it aside. The shopper reads their order page (`intentKeysRemainingInStorage: []`, per the drive: the key is gone). They press Back.
7. `pageshow` fires on the frozen-and-thawed document with `persisted: true`. The handler above finds the one `button[data-sku]:disabled` and clears it. The banner's own `pageshow` handler restarts its clock in the same moment (Slice 2 §3.3); the menu's forces the overlay closed.
8. The shopper clicks Купить on CS2 again. `purchaseIntentKey` reads storage: nothing (step 4). It mints a **new** UUID. `POST /api/orders` goes out wearing a name the database has never seen. A **new** order is created. The shopper arrives at a second order page for a second copy.

Step 8 is the one that has to be defended, because it looks like the thing the whole of Phase 2 exists to prevent. It is not. Phase 2 prevents *one decision* producing two orders; this is *two decisions* producing two orders, which is spec 002 §2.1's fifth criterion in its own words: *"Given a shopper has already bought an item and wants another one, when they start a fresh purchase of the same item from the shop page, then they get a separate second order with its own key."* The criterion imagined the shopper returning by the shop's own link; the back button returns them to the same page, and the page — restored or reloaded — must answer the same way. The key rotation in step 4 is what makes the second press a fresh intent; the re-enable in step 7 is what makes the press possible at all on the cached path. Neither is new logic: step 4 has been there since Phase 2, and step 7 only removes a state the cache preserved past its meaning.

**The obvious alternatives, and what each breaks.**

- *Never disable the button.* Then step 2 does not happen and a double-click's second click reaches the handler. It would send the same key — step 3's storage read finds the first click's UUID — and the database would fold the two into one order, so the shopper is not charged twice. But the page would now be sending two requests for one click as a matter of course, the e2e's "exactly one `POST`" would read `2`, and the failure message from a lost second response could appear on a page that is already navigating away. The disabled button is the UX half of the guarantee, and removing it to fix the cache trades a rare path for the common one.
- *Re-enable on success, before the navigation.* Step 5's problem exactly: a live button during the navigation, after the key has rotated, is a second order from an impatient second click that the shopper did not mean as a second decision. The feature refuses this on purpose and says so.
- *Re-enable on restore but do not rotate the key* — or, the same thing from the other side, rotate the key on restore rather than on success. Then step 8 sends the **old** UUID, the unique index recognises it, and the shopper who wanted a second copy is handed their first order back, complete with the key they already own, with no way to buy again. That is Phase 2's "too late" failure (`phase-2-slice-1` §5) — the shop that can sell each game to each shopper exactly once — reached by the back button. The re-enable is only correct *because* the key is already gone; the two facts are one design, and the header of `buy-controls.ts` states them together so nobody keeps one and loses the other.
- *Re-enable on every `pageshow`, ignoring `persisted`.* Harmless on a reload (there is nothing disabled to enable — `mountApp` built the page from nothing) but acting on an event that does not mean "restored". The guard is there so the handler does exactly one thing on exactly one event, which is what lets the header say "nothing else in the feature changes" and mean it.

**Why it is a feature edit and not a page one.** The `disabled` state was set by the feature; the feature un-sets it. `popular-products.ts` knows about the region and nothing about `disabled` — it could not clear the state without reaching into behaviour it does not own, and the layer rules would have it importing the feature's internals to do so. This is the same reasoning that put `buy()` in `features/buy-product` in the first place: the page says which items exist and how the list is built; the feature says what pressing one does, and what pressing one does now includes "stays pressable after the cache hands the page back".

**What was driven and what was not.** The handler was exercised with synthetic events on the real page: disable a button by hand, dispatch a synthetic `pageshow` with `persisted: true` → enabled; `persisted: false` → unchanged; two disabled of three → both enabled, the third untouched. The real `goBack()` under Playwright is a reload — `navigationType: "back_forward"`, all three buttons enabled because the page was rebuilt — so the e2e's crit 4 test proves the reload path and says in its own comment that it cannot prove the other. The cached path itself, in a real Chrome with no debugger attached, is §5.4 and §7.

## 4. What each test layer proves, and how each was shown able to fail

**Unit — `products-api.test.ts`, 10 cases, no network.** The function takes `unknown` and is fed hand-built rows shaped like the seed. ## 5. Findings

### 5.1 The dev server answers a missing image with `200 text/html`, and what that does to R10

When the drive pointed a card's `src` at a path that does not exist under `public/`, the `img` fell back to `--empty` as designed — but the network panel showed the request answered **`200`, `text/html`**, not `404`. Vite's SPA fallback had served `index.html`: its condition is that the request's `Accept` header admits `text/html` or `*/*`, and a Chromium `<img>` request's `Accept` ends in `*/*;q=0.8`. The image element then failed to *decode* a page of HTML, fired `error`, and the card degraded exactly as if the file had been missing. The behaviour on the page is right either way. The finding is about the tests.

R10 says "e2e network sweep is a required assertion" and `render-card-art.ts`'s header says a renamed or missing source "produces a card whose image 404s — which the e2e's network sweep (tech spec R10) reports". Under the dev server the e2e runs against (§4.2 chose `vite` over `build && preview` for its sub-second start), **neither is true for a static file**: the sweep sees `200`, and `products.spec.ts`'s picture test accepts the `--empty` fallback as a pass. A PNG deleted from `public/assets/` — or an SVG source renamed so the script stops producing one — would pass the 4xx sweep, pass the picture test, and pass the landing's "97 of 97 `200`". What actually proved the pictures load in this slice is the drive's `naturalWidth: 456` on all five `<img>`, which no spec asserts without the `--empty` escape hatch. The fix is one of two small assertions and is reported here, not made: since the seed has no `null` image, assert that *no* card on the seed carries `--empty` (the escape hatch is for a nullable column the seed does not exercise); or assert `content-type` starting `image/` on every `/assets/*.png` response. The same blindness applies to the service-tile icons and every other file under `public/`, so the second form is the more general.

### 5.2 One sentence, two readings, and why the choice is written in three places

Functional spec §2.6 says *"the three items that can be bought first, then the next two items in the shop's own order"*. Read as a partition — purchasable first, the rest after, order kept within each — the next two are the first two non-purchasable rows: Steam 500 and Steam 1000. Read as a cursor — the three keys, then the two rows *after the last key* — they are Discord and YouTube. Both fit the sentence; only one can be on the page. The partition was chosen (tech spec assumption 1) for three reasons the model file lists: it is a walk down one ordering rather than a cursor that must remember where the keys ended; it is stable under reordering of the catalogue, where the cursor reading changes its answer whenever a key moves relative to its neighbours; and it puts the two display-only cards, the Steam top-ups, beneath the Steam block that sits directly above the row. The choice is pinned in the unit test's first case by SKU, computed independently in the e2e's crit 1 from the live endpoint by the same rule, and named in the assumptions list — three places, so that whichever way the function is later rewritten, the row a reviewer sees is the one the spec says they will see. The reading was not confirmed with the user; it is recorded as the assumption it is, and the change to the other reading is a `findIndex` and a `slice`.

### 5.3 The card-art script does not read the seed, and what guards the paths instead

`render-card-art.ts` lists `scripts/card-art/*.svg` and writes `public/assets/<name>.png`; it never imports `packages/db/src/fixtures/catalog.ts` to learn which names the seed expects. The reason is practical: importing the fixture from a script run by `node` through type stripping would need `@game-shop/db` built first, turning "regenerate the art" into "build a package, then regenerate the art", for ten strings that have not changed since the brief. So the agreement between the ten basenames under `card-art/` and the ten distinct `image` values in the seed is by convention, stated in the script's header, and checked — the header says — by the e2e's network sweep. §5.1 has just shown that the sweep cannot check it under the dev server. Until one of §5.1's assertions exists, the guard is a person looking at the row, or the drive's `naturalWidth` reading. The two facts belong side by side: a script that deliberately does not know the seed, and a test that was supposed to notice if they drifted apart and currently would not.

### 5.4 The third `persisted: false`

Slice 2's verify launched Chromium without Playwright's `--disable-back-forward-cache` flag and got `persisted: false` with `notRestoredReasons: [{ reason: "masked" }]`. This slice's `buy-through.spec.ts` crit 4 test, under the normal harness, got a reload (`navigationType: "back_forward"`, all three buttons enabled). This slice's verify ran the bfcache script a third time against the buy flow — `persisted: false`, `masked` again, one `pageshow` entry in the window's log where a restore would have left two. Three attempts, three different framings, one answer: a page with a debugging session attached is not eligible for the cache, and every automated browser has one. The tech spec's R1 now records the measurement rather than the assumption. The consequence for this slice is that the one path its feature edit exists for is the one path no test in the repository can reach, and the document has to say so rather than let a green suite imply otherwise. What settles it is one minute in a real Chrome, and the manual check the user has been asked for covers both halves at once: after Back, the banner advances within 5 s (Slice 2's claim) **and** Купить is enabled and a second press creates a second order (this slice's).

### 5.5 Read while writing this document — reported, not fixed

- **`render-card-art.ts`'s header and R10 overstate what the sweep catches.** §5.1. The sentence "which the e2e's network sweep (tech spec R10) reports" is false under the dev server the e2e uses.

## 6. Interview questions this answers

**"What did you have to change on the purchase path to make the storefront buy? Prove it."**
Nothing, and the proof is three empty diffs and one green run. The new card renders the same `<button type="button" data-sku>` the plain page rendered, inside a region the same delegated listener watches — `enableBuyControls(region)` is the one line of the page's involvement. From the click on it is `buy()` as Phase 1–3 left it: `disabled` set synchronously, `createOrder(sku, purchaseIntentKey(sku))`, `forgetPurchaseIntent` on success, `location.assign`. `apps/api`, `packages/contracts`, `packages/db` and `pages/order` have no diff; `lib/purchase-intent.ts` has no diff; the feature's diff is 68 insertions and 0 deletions, all of them the `pageshow` handler. And `pnpm test` — the API suites that prove one intent is one order and one payment is one key — ran green immediately after the browser suite had bought three real orders and one real key through the new page. The functional spec's scope line is "where the shopper starts, not what happens after", and the diffs are what that sentence looks like.

**"Why is a double-click still one order from the new page? You rebuilt the card."**
Because neither half of the guarantee lives in the card. The first half is `button.disabled = true` on the first click's synchronous path, so the second click of a double-click lands on a disabled element and dispatches no event — the e2e counts one `POST /api/orders` after `dblclick`. The second half is the key: if a second request got out anyway (two tabs, a reload mid-flight), it would carry the same `Idempotency-Key`, because the key names the intent to buy this SKU and is read from storage rather than minted per click, and the unique index on `orders.client_request_id` would hand back the same order. The card's contract with the feature is three things — a `<button type="button">`, the only `data-sku` on a button inside the card, directly inside `__body` so `parentElement` is a box the failure message can live in — and `product-card.ts`'s header names all three so the next rebuild keeps them too.

**"`image` was on the wire since Phase 1. Why did the web app drop it, and why bring it back now?"**
It was dropped because the files did not exist and the plain page had nowhere to show one; constructing an `<img>` for `assets/steam.png` would have put ten 404s in the network panel and `net::ERR` lines in a console the reviewer was meant to find clean. The comment at the line said exactly that and named Phase 4 as the phase that would reinstate it. This slice ships the ten files at the seed's paths, so the field comes back as `readonly image: string | null` — nullable because the column is — read by `readNullableString`, which accepts a string or JSON `null` and rejects everything else including a *missing* key: `JSON.stringify` omits `undefined` and never `null`, and the API always sets the property, so an absent key is a different payload, not a row without a picture. The RED for that reader was the one-line shortcut `row["image"] ?? null`: it passes `null` and the string and lets `42` through to `new URL(42, origin)`, which is a valid `http://host/42`.

**"Why `new URL(image, window.location.origin)` and not a template string?"**
Because the two templates are each wrong on a route the other is right on. `` `/${image}` `` is right today and turns a future `/assets/cs2.png` into `//assets/cs2.png` — protocol-relative, host `assets`, every card blank at once with `ERR_NAME_NOT_RESOLVED`. A plain relative `src` is right on `/` and becomes `/order/assets/cs2.png` on the order route — a 404 that arrives with the first reuse of the entity on another page. Resolving against the *origin* — scheme, host, port, no path — ignores where the page is and survives a leading slash, and it is done in the card rather than the parser so the parser stays a pure statement about the wire that runs under Vitest's `node` environment with no `window` to fake.

**"Why placeholders and not the mockup's own card art?"**
Because the mockup's art is stock imagery for a game the catalogue does not sell, and putting it on a «CS2 Prime Status» card would mislead a shopper about what they are buying — the same product rule that refuses the mockup's struck-through old price and «5 %» badge. The placeholders say only what the row is: brand word, Russian product name, a flat colour keyed by SKU prefix, text and nothing else. They are SVG sources rendered through the e2e's Chromium because the text is Cyrillic plus «₽» and ImageMagick would need a pinned font for either; they are committed as PNG because a reviewer installs nothing and `system-ui` renders differently per OS; and they live at the seed's ten `assets/*.png` paths because the seed is the brief's fixture and its strings are the fixed input the art was made to fit.

**"The API is down. What does the shopper see?"**
Everything but the goods. `createPopularProducts` returns its section synchronously with «Загрузка каталога…» in the region, `storefront-page.ts` never awaits it, and `loadInto` paints the loading, empty and error states into that one `region` element and nowhere else. So the header, banner, tiles and Steam block are on the page and answering the pointer whether the catalogue takes a second or never arrives — the drive killed the API process and watched the banner keep advancing and Каталог keep opening while the row showed the Phase 1 sentence verbatim. The e2e reproduces it with a `503` route and asserts the four blocks visible, zero cards, the exact sentence, slide 2 after `runFor(5000)`, and the overlay opening. Every failure — unreachable, non-2xx, a body that is not the promised array — lands in the same `catch` and the same sentence, because to a shopper they are one event.

**"You re-enable Купить after the shopper comes back. Doesn't that let them buy twice?"**
It lets them buy *again*, which is different, and it is the spec's own requirement. `buy()` leaves the button disabled while `location.assign` runs, on purpose — a live button during the navigation would be a second copy from an impatient click. The back/forward cache preserves that disabled state past its meaning: the shopper who bought, read their order and pressed Back would meet a control that does nothing, the "broken control" the storefront must never show. On a persisted `pageshow` the feature clears `disabled` on its own buttons. A second press then creates a second order, and that is correct, because `forgetPurchaseIntent(sku)` ran on success before the navigation — the drive saw `intentKeysRemainingInStorage: []` on the order page — so the second press mints a new key for a new decision. That is spec 002 §2.1's fifth criterion, "buy, come back, buy again", reached by the back button instead of the shop's link. The wrong fixes are the ones that break one half: never disabling (two requests per double-click), re-enabling before the navigation (a second copy from the same decision), or keeping the old key (the second press returns the *first* order and the shop can sell each game once, forever).

**"Which five, and why those?"**
Purchasable first, catalogue order within each half, first five: CS2, GTA V, Tarkov, Steam 500, Steam 1000. The spec's sentence — "the three items that can be bought first, then the next two items in the shop's own order" — also admits Discord and YouTube, the two rows after the last key. The partition was chosen because it is one walk down one ordering, stays stable if the catalogue is reordered, and puts the two display-only cards beside the Steam block above them; it is assumption 1, pinned by SKU in the unit test and recomputed from the live endpoint in the e2e. The function returns what the catalogue affords — two items in, two out — and "exactly five, Купить on three" is the seed's fact, asserted in the browser against the real `GET /api/products`, not a promise the function pads or throws to fake. It lives in `pages/storefront/model/`, not in the entity, because "popular" is this page's word for the five it puts in one row, and the tie-breaker is a fact about this page's layout.

**"What is still unproven?"**
The cached restore. Every automated Back is a reload: a page with a debugging session attached is not eligible for the back/forward cache, and this phase measured that three times (`persisted: false`, `notRestoredReasons: masked`). So the `pageshow` handler's real-world behaviour — banner restarting, Купить re-enabled — is proven by synthetic events and by reading, not by the browser taking the path. It needs one minute in a real Chrome against `vite preview`: DevTools → Application → Back/forward cache → Test, then buy, press Back, watch the dot advance within 5 s and press Купить again and see a second order. Second, and smaller: under the dev server a missing picture is answered `200 text/html` by the SPA fallback, so the e2e's 4xx sweep cannot see one and the picture test's `--empty` escape hatch would accept it; the drive's `naturalWidth: 456` on all five is the evidence today, and one extra assertion would make it the suite's.
