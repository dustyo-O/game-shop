# Phase 6 · Slice 4 — The runner tells the truth to a live target

> Nothing in this slice is deployed either, and nothing about the shop's behaviour changes — the standing rule of the phase. What exists after it is the reviewer's half of functional spec §2.2: `pnpm race`, pointed at an address it did not start, now says what it can see and what it cannot, instead of quietly asserting against the wrong database or quietly passing on assertions it never made. With `RACE_BASE_URLS` set the runner builds nothing and spawns nothing, prints one line naming the targets and *which database the checks will see*, refuses to hand the checks the laptop's `DATABASE_URL` unless `RACE_DATABASE_URL` puts one back on purpose, hints when `ADMIN_TOKEN` is still `.env.example`'s local default, warms the target with `GET /api/products` until it answers `200`, prints one banner saying every database-side assertion below is a named `SKIP` and the orders will stay, runs the nine checks, and — on `RACE_DEMO_RESET=1` — calls `POST /api/admin/demo/reset` after the last one and prints what moved. The harness gained an HTTP half that counts distinct `x-instance-id` values across eight concurrent `GET /api/health` and turns "one instance answered everything" into a `FAIL` with the reason spelled out; `webhooks`, `same-event` and `promo` print the same count for their own batch as an `INFO` line; and the trap check asks the target how long its supplier deadline is before arming a hang that must outlast it. All of it was proven locally against four hand-spawned `dist/main.js` instances on 4601–4604, the platform's shape minus the platform.
>
> Four things carry the slice, and each is about *what a transcript is allowed to claim*. **External mode must not see the local database**, because `scripts/with-env.ts` merges `.env.example` into every run and would otherwise hand each check `DATABASE_URL=…localhost:5433…` while the target writes to its own — the database half of every check would then fail on `ECONNREFUSED` or, worse, assert against a database the target never touched, and nothing in the check can tell the difference. **A skipped assertion is reported by name and never counted**: 39 `SKIP` lines in the smoke run, each carrying the label the `PASS` or `FAIL` would have carried, and a `9/9` that counts only what ran. **A distinct-instance count proves a distinct process and no more**: `4 distinct instance id(s) across 4 target(s)` is a `PASS` externally, exactly one is a `FAIL` naming Fluid Compute, locally it is `INFO` because an id per port is a tautology and the `pg_stat_activity` pids are the proof — and the two honesty lines are printed with the number, not folded into the verdict. **The trap check learns the target's timeout from the target**, `supplier_timeout_ms` on `GET /api/health`, because `hang_ms = timeout + 1500` derived from the local `2000` against a live `5000` would land on the slow-but-successful side and the check would pass having exercised nothing.
>
> Reading the delivered work found three things and confirmed a fourth. `.env.example`'s `RACE_BASE_URLS` comment still said the runner spawns on `4201-4204` — a port default the runner moved in Phase 2 and the comment did not follow — and was corrected to `4601-4604`. A refused `RACE_DEMO_RESET` (a wrong token, an unconfigured target) exits `2` even when every check passed, because a transcript that was asked to end at baseline and did not must not exit `0`; and `resetDemoAfterRun` throws, rather than returning, if it is ever reached in local mode, so the local harness can never have its residue swept into a reset's `removed`. The demo reset after a no-database run reported `promo_codes 0` beside `promo_redemptions 4`: the promo check had already zeroed its own counters through `POST /api/admin/promo-codes/reset`, leaving the ledger it may not delete, and the demo reset is the one route allowed to delete it. And a comment in `promo.ts` still says that branch is unreachable under `pnpm race` — which was true until this slice.

## 2. The words this document uses

- **Local mode** — `RACE_BASE_URLS` unset. The runner preflights `DATABASE_URL`, rebuilds the packages, spawns `RACE_INSTANCES` (default 4) `dist/main.js` processes from port 4601, runs the checks against them with the runner's own environment plus two markers, and stops them. Unchanged by this slice, and the verify task confirmed it: `9/9`, no banner, no reset.
- **External mode** — `RACE_BASE_URLS` set. Somebody else owns the instances: the deployed shop, or — as in every run of this slice — a stack already running locally. The runner builds nothing, spawns nothing, stops nothing, and takes care that what the checks *see* is the target and not the laptop.
- **The mode line** — the first thing an external run prints: `race: external target(s) <urls> — database: none (assertions SKIP by name)` or `… — database: RACE_DATABASE_URL forwarded`. It answers the R7 question before any check runs.
- **The child environment** — what each check process is spawned with. Local: `process.env` plus `RACE_BASE_URLS` and `RACE_MODE=local`. External: `process.env` **minus `DATABASE_URL`**, plus `DATABASE_URL = RACE_DATABASE_URL` only when that is set, plus the two markers.
- **`RACE_DATABASE_URL`** — the author's knob: the target's own database, forwarded to the checks as `DATABASE_URL`. The only way a database reaches an external run.
- **`RACE_DEMO_RESET`** — the reviewer's knob: non-empty in external mode calls `POST /api/admin/demo/reset` on the first target after the last check and prints the counts. Ignored locally, with one line.
- **`RACE_MODE`** — not a knob. Set by the runner to `local` or `external` for the checks it spawns; the harness reads it to decide whether the distinct-id count is a verdict or information. Unset when a check is run by hand, in which case the external reading applies.
- **Warm-up** — `GET /api/products` on the first target until `200`, at most six attempts five seconds apart. The catalogue and not `/api/health`, because health builds its pool lazily and answers `200` with no database at all.
- **The banner** — five box-drawn lines printed once, only when the run has no database: every database-side assertion below is `SKIP` by name and never counted; the orders stay on the target; `pnpm demo:reset` or `RACE_DEMO_RESET=1`.
- **SKIP by name** — a check's line for an assertion it could not make: `SKIP <label> — needs DATABASE_URL`, with the same label the `PASS` or `FAIL` would carry. Counted as neither. `support/race-database.ts` states the rule; every check applies it.
- **The HTTP spine** — the assertions a check makes from responses alone: status codes, `GET /api/orders/:id`'s status, the delivered key as the shopper sees it, all N responses naming one order, drain's `claimed`, restock's `released`, the retry's `delivered: true`. Real `PASS`/`FAIL` against any target.
- **The witness** — the `x-instance-id` header every response carries, one `randomUUID()` per process (`apps/api/src/instance-identity.ts`, Slice 1). Read off a batch of answers, the distinct count is **K**.
- **K** — the number of distinct instance ids a batch saw. `4` everywhere in the smoke run. K = 1 means that batch was not cross-process evidence, and every line that prints K says so when it happens.
- **The honesty lines** — the two fixed lines the harness prints after its count, verdict or not: *a distinct id proves a distinct process, not that those processes overlapped in time*; *K = 1 on a run means that run was not cross-process evidence, whatever the checks after it say*.
- **The trap check** — `recover-timeout`: a supplier made to hang *after* its key claim commits, for longer than the shop's deadline, so the attempt is `unknown` and the same supplier is re-probed under the same request id. It only stages that scenario if the hang outlasts the deadline.
- **`hang_ms`** — the trap check's armed hang: the resolved supplier timeout plus 1500 ms. 3500 against the local 2000; 6500 against a live 5000.
- **The reviewer's command** — `RACE_BASE_URLS=<alias> ADMIN_TOKEN=<demo token> RACE_DEMO_RESET=1 pnpm race`. No database in hand.
- **The author's command** — the same with `RACE_DATABASE_URL=<the target's database>` in place of `RACE_DEMO_RESET=1`. No SKIPs; every check cleans up its own rows through `cleanupTestOrders`; the harness's database half counts the pids and reports the baseline.
- **Exit codes** — `0` every check passed, `1` at least one failed, `2` the command or the configuration was wrong (a target that never warms up, a refused reset), `3` from a check that could not run here at all (`before-order` against a target without `ALLOW_CLIENT_SUPPLIED_ORDER_ID`).

## 3. One run, from the mode line to the summary

This is the reviewer's command as the verify task ran it — four `dist/main.js` instances spawned by hand on 4601–4604 with the harness's own environment (own-origin supplier and webhook URLs, the local admin token, `ALLOW_CLIENT_SUPPLIED_ORDER_ID=true`), then `RACE_BASE_URLS=http://127.0.0.1:4601,…,4604 ADMIN_TOKEN=<local default> pnpm race`. Each step is the line it printed and the decision behind it.

**1. The mode line.** `race: external target(s) http://127.0.0.1:4601, … — database: none (assertions SKIP by name)`, then `race: nothing built, nothing spawned, nothing stopped; the target's owner supplies the instances.` `RACE_BASE_URLS` being set is what selects external mode; `RACE_DATABASE_URL` being unset is what makes the database `none`. The word `none` is the promise every `SKIP` below is keeping.

**2. The hint.** `race: ADMIN_TOKEN is the local default — export the target's token or the admin-guarded checks will answer 401`. Printed here because the hand-spawned instances *were* configured with the local default, so the hint was a false alarm in this one run — and correct behaviour: the runner compares the token it is about to forward against `.env.example`'s transcribed value and cannot know what the target holds. Against the live shop the same line would be the difference between three checks SKIPping on a `401` with no explanation and the reviewer knowing what to export.

**3. The warm-up.** `race: warm-up — GET http://127.0.0.1:4601/api/products → 200 in 49ms (attempt 1 of 6)`. One attempt because the instances were warm and the database was local; against a Neon branch resuming from autosuspend behind a cold function the same loop has six attempts, five seconds apart, twenty seconds per request, before it gives up with exit `2` and the message *the target never answered 200 … Nothing below could pass*. The catalogue and not `/api/health` — §4 and the reviewer challenges say why.

**4. The banner.** Five lines, once:

```
race: ┌─ no DATABASE_URL for this run ──────────────────────────────────────────
race: │ every database-side assertion below is reported as SKIP by name — never counted as a pass;
race: │ orders these checks create stay on the target. Run `pnpm demo:reset` when the run ends,
race: │ or set RACE_DEMO_RESET=1 to have this runner call POST /api/admin/demo/reset after the last check.
race: └──────────────────────────────────────────────────────────────────────────
```

Not one line per check: each check names its own skipped assertions where they would have run, and the banner is the one place that says what a `SKIP` means and what the run will leave behind.

**5. The nine checks**, in the runner's order — `harness` first, then filename order — each spawned with the child environment of §2. The harness: four `serves /api/health` PASSes, `x-instance-id header equals the body's instance_id on all 8 concurrent health answers — 8 of 8 agree`, then `PASS  the 8 concurrent health answers came from at least two distinct instances — 4 distinct instance id(s) across 4 target(s)`, then the two honesty lines, then four `reaches its database` PASSes through `GET /api/products`, then `SKIP  distinct backend connections — needs DATABASE_URL` and `SKIP  seeded baseline counts — needs DATABASE_URL`. N was eight because max(8, 2 × 4) is eight. The three batch checks each printed `INFO  answers came from 4 distinct instance(s)` — twice in `promo` (once per scenario), once in `same-event` over its 20 redeliveries, once in `webhooks` over its 50 events. Across the nine checks, 39 `SKIP` lines by name: harness 2, `before-order` 6, `create-order` 1, `promo` 2, `recover-out-of-stock` 15, `recover-refusal` 2, `recover-timeout` 2, `same-event` 5, `webhooks` 4 — every one of which is a `console.log("  SKIP …")` site in the file it came from, and the sum is the file count too. `recover-timeout` printed `supplier timeout 2000 ms (from target /api/health)` before arming.

**6. The reset — or not.** This run had no `RACE_DEMO_RESET`, so nothing was posted and the database afterwards read `orders 38, promo_used_count 0, promo_redemptions 4, keys_unclaimed 44, supplier_requests 6`: 38 orders left on the target, the promo counters already zeroed by the promo check's own fallback, the four ledger rows it may not delete still there, six keys claimed. `pnpm demo:reset` then printed `removed orders 38 · deliveries 6 · issuance_attempts 9 · promo_redemptions 4 · payment_events 55 · supplier_requests 6` and, under `reset`, `supplier_keys 6`. With `RACE_DEMO_RESET=1` on the same command the same block appears inside the transcript, after the last check and before the summary, and the reset's `reset` line included `supplier_behaviour 1` — §6.4 says what that row was.

**7. The summary.** Nine `PASS` rows and `race: 9/9 passed against 4 instance(s).` The ratio counts checks that ran; a check that exited `3` would be subtracted from both sides and named after the ratio. The 39 named SKIPs are inside the checks' own output and never reach this line, which is the point: `9/9` is the count of checks whose HTTP spine held, and the transcript above it is where the reader finds what was not asserted.

**The author's command** is the same transcript with `RACE_DATABASE_URL=<the local docker url>` exported: the mode line reads `RACE_DATABASE_URL forwarded`, no banner, zero `SKIP` lines, the harness's database half reads `4 distinct backend pid(s)`, every check's `cleanupTestOrders` runs, and the database reads at the seeded baseline afterwards. The checks themselves are byte-identical between the two runs; only the environment they were spawned with differs, and the first line of the transcript says which.

## 4. The four decisions the task names

Each in the same shape: what was built, the obvious alternative, and what goes wrong with the alternative.

### 4.1 External mode must not see the local database

**What.** `buildChildEnv` in `run-checks.ts`: in local mode the child environment is `process.env` plus the two markers; in external mode it is `process.env` with `DATABASE_URL` destructured away, plus `DATABASE_URL: raceDatabaseUrl` only when `RACE_DATABASE_URL` was set, plus the markers. The mode line names which of the two happened. Nothing else about the checks changes: `openRaceDatabase` returns `undefined` when there is no `DATABASE_URL`, and every check already had the SKIP branch for that.

**The obvious alternative.** Do nothing, and let the reviewer export whatever they like — or print a warning when `DATABASE_URL` looks local and forward it anyway.

**What goes wrong with the alternative.** The trap is in `scripts/with-env.ts`, which every root `pnpm` script goes through: it layers `.env.example`, then `.env`, then the real environment, so a reviewer who exported only `RACE_BASE_URLS` and `ADMIN_TOKEN` still runs every check with `DATABASE_URL=…localhost:5433…` — the committed local default — in its environment. Two things can then happen, and both are worse than a SKIP. If no Docker Postgres is running, `openRaceDatabase` connects, the first query throws `ECONNREFUSED`, and nine checks fail for a reason that has nothing to do with the shop. If one *is* running — the reviewer has followed the README's local section first, which is the likely order — the database half connects fine, reads the local database, and reports what it finds there as facts about the live target: *zero deliveries rows for an order the API just returned as delivered*, or, against a local database that happens to be at baseline, a run of assertions that are true of the wrong shop. `race-database.ts`'s header admits the second case in so many words — *this module cannot verify that `DATABASE_URL` points at the database the target is using* — and that is R7: the check cannot tell, so the runner must not let the situation arise. Stripping, rather than warning, is the only shape under which the mode line is a true statement: `database: none` means none. The cost is one knob, `RACE_DATABASE_URL`, for the one person who legitimately wants a database in an external run and has to say so on purpose — and a footgun the reviewer challenges name: an author who exports `DATABASE_URL=$NEON_DIRECT_URL` instead of `RACE_DATABASE_URL=…` gets a stripped run and 39 SKIPs, with the mode line as the only tell. `ADMIN_TOKEN` is forwarded as-is because the recover checks arm the supplier with it; the hint covers the case where it is still the local default.

### 4.2 SKIP by name over a silent pass

**What.** Nothing new in the checks — `support/race-database.ts` has stated the rule since Phase 2: *a skipped assertion is reported by name, and never counted as a pass* — and one new thing in the runner: the banner that says, once, what the SKIPs below mean and what the run leaves behind. The smoke run's 39 lines are the rule applied across nine files: `SKIP  exactly one deliveries row for the order — needs DATABASE_URL`, `SKIP  exactly one orders row for that client_request_id — needs DATABASE_URL`, `SKIP  the drain took the whole unclaimed pool — claimed equals the unclaimed count read before it — needs DATABASE_URL`, and so on, each with the label its `PASS` would have carried.

**The obvious alternative.** Two of them. Require a database for every run, so there is never anything to skip — which makes the deployed run, the strongest form of the claim, the one the reviewer cannot make at all. Or let the database half silently not run and print `PASS` for the check, since "nothing that ran was wrong".

**What goes wrong with the alternative.** The second is the one `architecture.md` §7 names for a race check that silently serialises: a false statement about the system that grows more convincing every time it runs. A check that quietly drops "exactly one delivery row" when `DATABASE_URL` is missing and still prints `PASS` is *worse* than one that fails, because the reader takes the `PASS` as covering the headline row when it covers only the response. The `9/9` at the end is honest only because the 39 lines above it are not in it — and the distribution tells the reader exactly how much of each check is behind the database: `recover-out-of-stock` has 15 of its assertions there (the attempt rows, `last_error`, the whole-pool reads, the `supplier_requests` ledger — the *how* of the recovery, which `GET /api/orders/:id` cannot show), `create-order` has one (the `orders` row count for the shared `client_request_id`), the harness has two (the pids and the baseline). What is still asserted for real is everything the shopper could see: fifty webhooks all `2xx`, the order `delivered`, the key non-null and identical on every read, N creates naming one order id, the promo's `200`s and `409`s in the right proportion, drain's `claimed`, restock's `released`, the retry's `delivered: true` and the second retry's `409`, and — new — K. The two disagree in both directions (§7: a `500` to nineteen callers over a correct database; a self-consistent `null` over a committed key), so the HTTP spine is not the whole proof; it is the half a reviewer can hold, labelled as that half.

### 4.3 What a distinct-instance count proves, and does not

**What.** Two things, deliberately unequal. The harness fires N = max(8, 2 × targets) concurrent `GET /api/health`, spread round-robin over the targets, checks that every answer's `x-instance-id` header equals its own body's `instance_id`, and counts the distinct values. Externally (`RACE_MODE=external`, or unset when run by hand) that count is a `record`: `PASS` at ≥ 2, `FAIL` at exactly 1 with the detail `all N answers came from one instance — re-run, or check that Fluid Compute is off`. Locally (`RACE_MODE=local`) it is one `INFO` line — `4 targets, 4 distinct instance id(s) across 8 concurrent health answers — locally an id per port is a tautology; the pg_stat_activity pids below are the proof`. Either way the two honesty lines follow. The three batch checks collect the header from their own N responses through `collectInstanceIds` and print `describeInstanceIds`'s one `INFO` line, which flags K = 1 in the line itself.

**The obvious alternative.** Make K a `PASS`/`FAIL` everywhere, with a threshold of "at least as many as targets"; or leave K out and let the pids — the stronger witness — be the only proof of separate processes.

**What goes wrong with the alternative.** The pids are the database's view, and the reviewer has no database: without an HTTP witness the live transcript would carry Phase 6's sentence with no number in it, and R3 — Fluid Compute left on, requests sharing an instance, the `max: 1` pool serialising them in-process — would be invisible from the transcript. The witness exists to make that one reading impossible to miss, and only that one: exactly one id across eight concurrent answers is the run §7 calls worthless, so it is a `FAIL` with the platform setting named. Above one, the number is information. It proves that K processes answered; it does **not** prove they were alive at the same moment — two ids across fifty webhooks are consistent with one instance recycled between the first and the last — which is why the threshold is ≥ 2 and not ≥ targets, and why the line is printed with its limit rather than as a verdict. Locally the count is a tautology: the runner started four processes on four ports and asked each port twice, so `4 distinct` says nothing the runner did not already know, and calling it a `PASS` would be a green line that costs nothing. The pids are the proof there, and the `INFO` line says so. The negative proof in §5 — one target, `FAIL … all 8 answers came from one instance`, `race: 0/1` — is the shape a Fluid-on deployment would produce, staged the only way it can be staged on a laptop. The README will carry the K of the author's live run as a number with the caveat beside it, never as a pass.

### 4.4 The trap check must learn the target's timeout

**What.** `resolveSupplierTimeout` in `recover-timeout.ts`: `GET /api/health` on the first target and read `supplier_timeout_ms` — the value `health.controller.ts` injects from `SUPPLIER_A_CONFIG`, the same token the issuance client hands to `AbortSignal.timeout`, not a second read of the variable; failing that, `SUPPLIER_TIMEOUT_MS` from the check's own environment; failing that, the client's own `2000` default. The line `supplier timeout 2000 ms (from target /api/health)` names which source won, and `hang_ms = timeout + 1500` is derived from it.

**The obvious alternative.** What the file did until this slice: derive `hang_ms` from the check's own `SUPPLIER_TIMEOUT_MS`, which locally is the same value the runner hands the instances.

**What goes wrong with the alternative.** The check proves one specific thing: a supplier that goes quiet *after* its claim commits produces an `unknown` attempt, never `failed`, and the ladder re-probes the same supplier under the same request id inside one invocation. That only happens if the hang outlasts the shop's deadline — `SUPPLIER_TIMEOUT_MS < hang_ms`, R1's inequality. Locally the deadline is 2000 and the hang 3500. The live profile is `SUPPLIER_TIMEOUT_MS=5000` (tech spec §2.7, because each supplier call is a second, possibly cold, invocation). A hang of 3500 against a deadline of 5000 is a supplier that is slow and then *succeeds*: no timeout, no `unknown`, no re-probe, the order delivered on the first attempt — and every HTTP assertion in the check still passes, because the response looks the same. That is R8: the trap check going vacuous live, a green line that exercised nothing, and the assignment's central scenario unproven on the one run that matters. The target is the only authority on its own deadline, so the target is asked, and the environment is demoted to a fallback for an older build that does not publish the field. The verify task's measurement is the one that matters here: with `SUPPLIER_TIMEOUT_MS=9999` exported in the runner's shell, the check still printed `supplier timeout 2000 ms (from target /api/health)` — the shell's number lost to the target's. Against a live 5000 the hang is 6500, inside Vercel's 60 s function ceiling with room for the re-probe.

### 6.3 The promo check resets its own counters, so the demo reset reports `promo_codes 0`

The demo reset is the one route allowed to delete them, because it deletes the orders in the same transaction; it finds nothing to zero in `promo_codes` and four rows to remove in `promo_redemptions`. A reader who expected `promo_codes 4` in the reset would be reading the two affordances as one; they are not, and the numbers show the seam between them.

### 6.4 The reset after a no-database run finds one behaviour row armed

The `RACE_DEMO_RESET=1` transcript's reset block includes `supplier_behaviour 1`. The reset's statement counts rows whose six knobs are `IS DISTINCT FROM (0, 0, 0, 0, 0, false)`, and one supplier had a knob left non-zero. Without a database, A's row is left with `hang_ms = 3500` and `hang_next = 0`: harmless, since nothing fires without a counter or a rate, but not baseline, and the demo reset is what puts it back. The author's run, with the database forwarded, resets the row in the check's own `finally`. This is the same seam as §6.3 seen on the supplier's side: without a database a check can undo what it armed only through an affordance, and the recover checks' affordance for their own row is `PUT /internal/suppliers/a/behaviour` at the *start* of the next run (`provider a reset to the seeded baseline before arming`), not at the end of this one. ## 7. What a reviewer might challenge

- **Why not just require a database for the reviewer? Then there is nothing to skip.** Because the deployed run is the strongest form of the claim — separate processes with nothing in common but Postgres — and it is the one the reviewer cannot make with a database in hand: the live shop's connection string is a secret, and the alternative, a second database the reviewer owns, is a different shop. `race-database.ts`'s header put it this way in Phase 2: *requiring it would mean the deployed run … is the one that cannot be made at all.* So the database half degrades, and the whole design of this slice is making that degradation say exactly what it is. The author's run exists for the assertions that need the rows, and the README will carry both.
- **Why strip `DATABASE_URL` rather than warn and forward it?** Because a warning leaves the transcript's meaning to whether the reader saw the warning, and the two failure modes are not symmetrical. `ECONNREFUSED` is loud and wrong; asserting against a local database that happens to be at baseline is quiet and wrong, and the checks cannot tell — `race-database.ts` says so. The mode line `database: none` is only a true sentence if the runner made it true. The one legitimate database in an external run has a name of its own, `RACE_DATABASE_URL`, so that forwarding is a decision the operator made and not a leftover from `with-env.ts`.
- **That strip is a footgun: an author who exports `DATABASE_URL=$NEON_DIRECT_URL` gets 39 SKIPs.** Yes. The tell is the first line of the transcript — `database: none (assertions SKIP by name)` when the author expected `forwarded` — and the banner right after it. The alternative, honouring an exported `DATABASE_URL` in external mode, reopens R7 for anyone whose shell still carries the local value from an earlier `pnpm dev`, which is the common case. One explicit knob, named in `.env.example`, the README and the runner's usage block, is the cheaper mistake.
- **Why is `RACE_DEMO_RESET` opt-in? A reviewer who forgets it leaves 38 orders on the shop.** Because a reset that runs by default is a reset that runs on a shop the reviewer did not mean to reset — `RACE_BASE_URLS` also names a stack somebody has running locally, and "somebody else owns the instances" is the definition of external mode. The banner names the consequence and both remedies every time the run has no database; the README's recorded command carries the flag; and the residue is bounded — 38 orders and six keys per run, all of them reversible by one `pnpm demo:reset`. The opposite mistake, a whole-shop `DELETE` the operator did not ask for, is not reversible.
- **Why does the warm-up hit `/api/products` and not `/api/health`?** Because `/api/health` is not evidence of a database. `apps/api` builds its pool lazily, so health answers `200` with an `instance_id` on an instance that has never opened a connection — which is right for a boot probe (Slice 1: `200` means the container built and its variables were usable) and useless for "is Neon awake". The catalogue is the cheapest read that actually goes to Postgres, and the harness uses it for the same reason, for `reaches its database` and to open each instance's one connection for the pid count. A cold first check would otherwise fail on timing rather than on an assertion, and the reviewer would be told the shop is wrong when the database was resuming.
- **Why is K `INFO` in three checks and `PASS`/`FAIL` only in the harness?** Because the harness is the check that checks the harness — it asserts nothing about the shop, only that the next check's result will mean something — and "at least two processes answered" is exactly that kind of claim. The three batch checks assert the shop's invariants; folding the process count into their verdict would make `webhooks` fail on a platform setting, and a reviewer who sees red on a correct shop stops trusting the other four. So they print the number for their own batch, so a reader can see whether *these* fifty were spread, and the harness decides once. `describeInstanceIds` still flags K = 1 in the line itself, so a single-process batch is never a silent green.
- **Why ≥ 2 and not ≥ targets, or ≥ 4?** Because the threshold guards one reading — every answer from one process, one `max: 1` pool, §7's worthless run — and only that reading is decidable from ids. Against a deployed alias there is one target and the platform chooses how many instances answer eight concurrent requests; demanding four would make the verdict depend on the platform's scheduler rather than on the shop. Above one, the number is information with its limit printed beside it.
- **The negative proof for K is one local process behind one URL. Is that really Fluid Compute?** It is the shape the witness would see, which is the only thing the witness decides on: eight concurrent health answers, one id. What Fluid Compute additionally does — interleave `waitUntil` contexts, share a pool across requests in one instance — the witness cannot see and does not claim to. The staged negative proves the verdict fires on the observable; that the observable occurs under Fluid on is R3's description of the platform, to be read off the first live run if the toggle is ever wrong.
- **`SUPPLIER_TIMEOUT_MS=9999` proves precedence, not R8. Where is the 5000-against-2000 case?** It cannot be staged without a target whose deadline differs from the runner's shell — which is Slice 5's live shop. What can be staged locally is that the shell's number loses to the target's, and that is the mechanism R8 needs: whatever the live deadline is, the hang is derived from it. The first live transcript will print `supplier timeout 5000 ms (from target /api/health)`, and that line is the R8 evidence proper.
- **Two of the recover checks print one blanket `SKIP every database assertion below` line. Is that "by name"?** At the level of the block, not the assertion — `recover-refusal` and `recover-timeout` each print two lines (`stock accounting before this run` and `every database assertion below`), where `recover-out-of-stock` lists all fifteen of its labels because Slice 3 rewrote its assertions as data. The rule is honoured in the sense that matters — nothing skipped is counted — and under-honoured in the sense that the reader cannot see from the no-database transcript which assertions the author's run would have made for those two checks. §9 lists it.

## 8. Interview questions this answers

**"What does external mode do that local mode does not, in one breath?"**
It builds nothing and spawns nothing; it prints which targets and which database the checks will see; it strips the laptop's `DATABASE_URL` from the checks' environment and puts one back only from `RACE_DATABASE_URL`; it warns when `ADMIN_TOKEN` is still the local default; it warms the target with `GET /api/products` until `200`; it prints one banner saying every database-side assertion is a named `SKIP` and the orders will stay; and on `RACE_DEMO_RESET=1` it calls the demo reset after the last check and prints the counts. The checks are byte-identical between the two modes; the environment and the first line of the transcript are what differ.

**"Why must external mode not see the local database?"**
Because `with-env.ts` merges `.env.example` into every root script, so without care each check inherits `DATABASE_URL=…localhost:5433…` while the target writes somewhere else. The database half then either fails on `ECONNREFUSED` — nine red checks about nothing — or connects to the local Docker database and reports its rows as the live shop's, and `race-database.ts` admits it cannot tell whether a `DATABASE_URL` is the target's. R7. So the runner strips it, the mode line says `none`, and the only database that reaches an external run is one the operator named on purpose.

**"What is a SKIP in the transcript, and why is `9/9` still honest?"**
`SKIP <label> — needs DATABASE_URL`: an assertion the check could not make, printed with the label its `PASS` would have carried, counted as neither. 39 of them in the smoke run — 15 in `recover-out-of-stock` alone, because the *how* of a recovery lives in `issuance_attempts` and `supplier_requests`. `9/9` counts checks whose HTTP spine held; the SKIPs are inside each check's output and never enter the ratio. A check that dropped "exactly one delivery row" and printed `PASS` would be a false statement that gets more convincing every run — §7's trap for a race check that silently serialises, in a different coat.

**"What does K = 4 prove, and what would K = 1 mean?"**
Four distinct `x-instance-id` values across a batch means four distinct processes answered, because the id is a module-scope `randomUUID()` and a module evaluates once per process. It does not prove they were alive at the same moment; the concurrent fan-out and, for the author's run, the `pg_stat_activity` pids argue that. K = 1 means every answer came from one process sharing one `max: 1` pool — the run `architecture.md` §7 measured as indistinguishable from a shop with no locking — so the harness makes it a `FAIL` naming Fluid Compute, and every other K line flags it in the text. Locally K is an `INFO` line because the runner started four processes on four ports itself; there the pids are the proof.

**"Why does the trap check ask the target for its timeout?"**
Because the check only stages the trap if the hang outlasts the shop's deadline. Locally that is 2000, live it is 5000, and a hang derived from the local value — 3500 — against a live 5000 is a slow supplier that succeeds: no `unknown`, no re-probe, every HTTP assertion green, nothing exercised. `GET /api/health` publishes `supplier_timeout_ms` from the same config token the issuance client hands to `AbortSignal.timeout`, so the check reads that first, prints the source, and derives `hang_ms = timeout + 1500` from it. Measured: with `SUPPLIER_TIMEOUT_MS=9999` exported, the line still said `2000 ms (from target /api/health)`.

**"Why is the reset opt-in, external-only, and a hard error locally?"**
Opt-in because external mode also means a stack somebody has running on their laptop, and a default whole-shop `DELETE` is the wrong surprise. External-only because every local check cleans its own rows and the harness asserts the baseline; a reset in their place would sweep a leaking application's residue into `removed` and call it a pass. A thrown error rather than a silent return in local mode because the guard is an assertion about the runner, and an assertion that returns quietly is one nobody would notice failing. And a refused reset exits `2` even at `9/9`, because a transcript asked to end at baseline that did not is not a `0`.

**"Why `/api/products` for the warm-up?"**
`/api/health` builds its pool lazily and answers `200` with no database at all; it is the boot probe, not the database probe. The catalogue is the cheapest read that goes to Postgres, so `200` there means the function is up *and* the database is awake — which against Neon's autosuspend is the thing a cold first check would otherwise fail on, for a reason that is not the shop's.

**"What did you find that wasn't in the plan?"**
That `.env.example` still documented the runner on `4201-4204`, a default that moved in Phase 2. That the demo reset after a no-database run reports `promo_codes 0` beside `promo_redemptions 4`, because the promo check has already zeroed its counters through the promo reset and left the ledger the demo reset alone may delete. That the same run leaves supplier A's row with `hang_ms` non-zero, because the trap check's `finally` can only zero it through a database it did not have — the `supplier_behaviour 1` in the reset's block. And that `promo.ts` still says its no-database branch is unreachable under `pnpm race`.
