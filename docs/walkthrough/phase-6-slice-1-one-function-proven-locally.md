# Phase 6 · Slice 1 — The shop runs as one function, proven locally

> Nothing in this slice is deployed. No account was touched, no `vercel.json` exists, no request has crossed the public internet. What exists after it is the shape the deployment will have, built and driven on a laptop the way the platform will drive it: the API has a second way in, `apps/api/src/vercel.ts`, that answers `(req, res)` from a container built once per process and never listens on anything; every response the shop gives — a `200`, a `404`, a guard's `401`, the entry's own `503` — carries an `x-instance-id` that names the process that wrote it; and the platform's `waitUntil`, a seam Phase 2 left open on purpose, is wired and consulted only when `VERCEL` says there is a platform on the other end. The proof is an acceptance file that imports the compiled handler and hands it to Node's own `http.createServer` on port 5401 — `@vercel/node`'s shape, minus `@vercel/node`.
>
> Three things carry the slice, and each is a decision about *where a fact lives* rather than a mechanism. **The container is one function, `createApp()`, that both entries call and that owns nothing an entry owns** — no port, no shutdown hook, no policy for a boot that fails — so the shop that answers `pnpm dev` and the shop that will answer a Vercel invocation are the same expression, and the two files that differ are each a few lines about what happens *after* a container exists. **The handler caches the promise of the listener, not the listener**, stored on the first line of the module that evaluates once per process, so two invocations that overlap on a cold instance await one container and one `max: 1` pool rather than racing a `let app` across an `await`. **A boot that fails stays failed for the instance's life**: Nest's default answer to a bad variable is `process.exit(1)` from inside `NestFactory.create`, which is exactly right for a process that owns a port and a boot loop inside a function invocation; `vercel.ts` asks for a rejection instead, keeps it, and turns every request into the same `503 { status: "misconfigured", error }` naming the variable.
>
> Reading the delivered work found four things. Nest's `abortOnError` is not a flag that makes `create` throw or not throw — with the default on, the error is logged and the process is ended by an `ExceptionsZone` teardown whose whole body is `process.exit(1)`, so the returned promise never settles at all; the seam `onBootFailure: "exit" | "reject"` exists because the two entries need opposite answers to that one line. The payment simulator's self-call — the shop posting a webhook to itself — had no timeout, which never mattered while the other end was the same process one hop away and matters the moment the other end is a second, possibly cold, invocation. The unit file's header quotes a RED line that says the opposite of what Vitest printed — the inline comment beside the assertion, and the task's transcript, have the right one. And a paragraph of the technical spec assigns this file's assertions, and its port, to a file that belongs to Slice 3.

## 2. The words this document uses

- **Entry** — a file whose only job is to turn a container into something that answers requests. There are two: `main.ts`, which listens on a port and has a lifetime, and `vercel.ts`, which answers `(req, res)` and has neither. Neither builds the container.
- **Container** — what `NestFactory.create(AppModule, …)` returns: every module instantiated, every config provider run, every controller routed. Building it is when a bad variable is discovered, because the config providers validate while it is built.
- **Listener** — Node's `RequestListener`, `(req, res) => void`. An initialised Express application *is* one, which is why `vercel.ts` can take it out of Nest with `getHttpAdapter().getInstance()` and hand requests to it directly.
- **Invocation** — one call of the function's handler by the platform, for one request. It begins when the request arrives and is over when the response ends — plus whatever `waitUntil` was handed.
- **Instance** — the process the platform runs invocations in, reused while warm, frozen between requests, discarded without notice. On Vercel with Fluid Compute off, one instance serves one invocation at a time; a second concurrent request gets a second instance. `INSTANCE_ID` is one value per instance because a module evaluates once per process.
- **Cold boot** — the first invocation an instance receives, which pays for module evaluation and therefore for `createApp()`: the container, the config validation, the pool's first connection. The technical spec's estimate is ≈ 1.5–2.5 s for a self-invocation.
- **Misconfigured** — an instance whose container could not be built because a config provider threw a `ConfigurationError`. Locally that process exits `1` and binds no port; in the function it answers `503 { status: "misconfigured", error }` for its life.
- **Continuation** — the work a webhook schedules after it has acknowledged: processing the event it just stored. Locally `TrackedContinuationScheduler` holds it in an in-flight set drained on shutdown; on the platform `WaitUntilContinuationScheduler` hands it to `waitUntil`.
- **The seam** — `resolveWaitUntil()`. Phase 2 wrote the platform scheduler complete and left exactly one thing absent, the import of `@vercel/functions`, behind a function that returned `undefined`. This slice closed it with the two edits its own comment prescribed.
- **`x-instance-id`** — the response header every answer from a process carries, equal to that process's `INSTANCE_ID`; `GET /api/health` repeats it in the body as `instance_id`. A witness, not a guarantee: it says which process answered and nothing about which processes were alive together.
- **K** — the number of distinct `x-instance-id` values a run of the race checks saw. Slice 4's runner will print it; Slice 5's live run will record it. This slice makes K countable; it does not count.

## 3. One request, from the platform to Nest and back

The path a `POST /api/orders` will take once deployed, with the local driver's version beside it, because the point of this slice is that the two are the same path from the second step on.

**Before any request: the container.** Vercel builds one function from `api/index.js` — the one file under `api/` at the repository root, which it treats as a function regardless of `outputDirectory`. `@vercel/node` loads it as ESM because the root `package.json` is `"type": "module"`, and follows its one line, `export { default } from "../apps/api/dist/vercel.js"`, into build output that `pnpm build` produced under `apps/api/tsconfig.build.json`. Evaluating `dist/vercel.js` evaluates `dist/instance-identity.js` — `INSTANCE_ID = randomUUID()`, once — and then runs the module's first statement:

```ts
const listener: Promise<RequestListener> = createApp({ onBootFailure: "reject" }).then(
  async (app) => {
    await app.init();
    return app.getHttpAdapter().getInstance() as RequestListener;
  },
);
```

`createApp()` is `NestFactory.create(AppModule, new ExpressAdapter(), { abortOnError: false, logger: new ConsoleLogger({ json: true }) })` — the second option only because `VERCEL === "1"` — followed by one `app.use` that sets `x-instance-id` on every response. Building the container runs every config provider, so `SUPPLIER_TIMEOUT_MS=abc` is discovered here, on the instance's first invocation, not on the first paid order. `app.init()` wires Nest's router onto the Express application; `getInstance()` returns that application, which is callable as a Node request listener. The promise now holds the listener, or a rejection, for the life of the process.

Locally the driver is the acceptance file's `driver.mjs`, written to a temp directory at `beforeAll`: `import handler from "…/apps/api/dist/vercel.js"` and `createServer(handler).listen(5401)`. From here on the platform and the driver do the same thing.

**The request.** The platform's rewrite sends `/api/(.*)` and `/internal/(.*)` to `/api/index` after a filesystem miss, with the *original* `req.url` intact — `/api/orders`, not `/api/index` — and calls the default export with Node's own `IncomingMessage` and `ServerResponse`. The handler is:

```ts
export default async function handler(req, res) {
  let serve: RequestListener;
  try {
    serve = await listener;
  } catch (error) {
    // 503 { status: "misconfigured", error } with x-instance-id set by hand — §4.3
    return;
  }
  serve(req, res);
}
```

`await listener` on a warm instance is a resolved promise and costs a microtask; on a cold instance it is the whole boot, and every invocation that arrives during it waits on the same promise. `serve(req, res)` is Express's stack in order: the instance-identity middleware first, because it was registered on the adapter before `init()`; then Nest's body parsers, so a JSON body is parsed exactly as it is behind `app.listen()`; then the router, guards, pipes, the handler and the exception filters. The response ends, and the invocation is over. Nothing in `vercel.ts` parses, routes or logs a request — it decides how a container meets a request that arrives without a listening socket, and that is all.

**What the local entry does with the same container.** `main.ts` is `await createApp()`, `app.enableShutdownHooks()`, `await app.listen(port)`. `listen` initialises as a side effect, so there is no explicit `init()`; the shutdown hooks are there because a process that owns a port receives `SIGINT` and `DatabaseModule`'s pool drain runs on it. A function receives no signal it can act on — the platform freezes and discards instances without telling the process — so `vercel.ts` deliberately has no `enableShutdownHooks()`: it would be a listener that never fires. That asymmetry is the whole of the difference between the two files, and it is why neither of those calls is in `createApp()`.

**What the smoke showed**, quoted from the task's transcript against the driver on 5401: `GET /api/health` → `200` with `instance_id` equal to the `x-instance-id` header, `runtime: "node"`, `supplier_timeout_ms: 2000`; `/api/nope` → Nest's JSON `404` carrying the header; `POST /api/admin/payment-events/sweep` without a token → the guard's `401` carrying the header; `POST /api/orders` with a JSON body → `201`. Booted with `VERCEL=1`, the scheduler's boot line is one JSON object — `{"msg":"continuations delegated to the platform","implementation":"wait_until"}` — where the same line without the flag is pretty-printed with `implementation: 'tracked'`.

## 4. The four decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision.

### 4.1 One function builds the container, and both entries call it

**What.** `createApp()` is the only place in `apps/api/src` that calls `NestFactory.create`. It takes one option, `onBootFailure`, and does three things: builds the container with the adapter, registers the `x-instance-id` middleware, returns an application that has neither been initialised nor told to listen. `main.ts` is the local entry and does what only a port-owning process should — `enableShutdownHooks()`, `listen()`. `vercel.ts` is the deployed entry and does what only a function should — `init()`, take the listener out, cache the promise. `grep NestFactory apps/api/src/main.ts` finds nothing.

**The obvious alternative.** Two entries, each complete. `main.ts` as it was — it already called `NestFactory.create` with the adapter — and a `vercel.ts` that calls it again with its own options. A few lines each, no shared file, no option to thread through.

**What goes wrong with the alternative.** The two containers drift, and the drift is invisible until it is on the live address. The middleware is the first casualty: added to `main.ts` for the harness and forgotten in `vercel.ts`, or the other way round, and the live run's K is counted from a header that half the responses do not carry. The logger option is the second. And the tests are the third, because this slice's acceptance file proves that *the same container* answers the same way through a different door — a `201` with the body parsed, a guard's `401`, Nest's own `404` shape — and that claim is only meaningful if "the same container" is one expression rather than two that happened to agree on the day the test was written. The standing rule for the phase is that nothing about the shop's behaviour changes between local and live; one function that both entries call is what makes that rule a property of the code instead of a discipline for the author. The cost is one option: the entries genuinely disagree about a boot failure, so `createApp()` has to be told which answer to give, and that option is §4.3.

### 4.2 The handler caches a promise, not an app

**What.** `listener` is a `Promise<RequestListener>` created on the first line of `vercel.ts` that runs, during module evaluation, before the platform has called the handler even once. Every invocation does `await listener` and gets the same Express application. There is no `if`, no `let app`, no "is it built yet".

**The obvious alternative.** The lazy shape every tutorial writes:

```ts
let app: RequestListener | undefined;
export default async function handler(req, res) {
  if (app === undefined) app = await buildListener();
  app(req, res);
}
```

Build on first use, keep the result, reuse it. It reads naturally, it defers the cost until a request needs it, and it stores the thing you want rather than a promise of it.

**What goes wrong with the alternative.** It is a check-then-act across an `await`, and this repository refuses that shape everywhere else for the same reason it refuses it here. Two requests arrive at a cold instance. The first sees `app === undefined` and starts `buildListener()`; while it is awaiting, the second arrives, sees `app` still `undefined` — the assignment has not happened yet — and starts a second `buildListener()`. Two containers in one process: two `DatabaseModule`s, two `max: 1` pools, two first connections, and the per-instance connection budget `packages/db/src/client.ts` sized Neon against — `max × live instances` — doubled by an instance that was supposed to hold one. Both builds also run every config provider and log a second `Starting Nest application`, so the symptom in the function log is a doubled boot with no error, which is the kind of thing that gets read as "Vercel is slow".

The promise closes the gap because there is no gap: module evaluation is synchronous and happens once per process, the call to `createApp()` happens inside it, and the platform cannot deliver a request to a module that has not finished evaluating. Two overlapping cold invocations both `await` the same promise and both receive the same listener when it resolves. The header of `vercel.ts` is careful to say this is the one place in the API where a process-level singleton is the right tool: it guards a resource that is *meant* to be per-process — a pool — not a correctness invariant, which stay in Postgres.

One honesty note the header also carries. With Fluid Compute off, the platform itself serves one invocation per instance at a time, so on the deployment as planned the two-overlapping-requests race cannot happen on a single instance. The promise is still the right shape, for two reasons. The local driver *does* overlap requests — it is a `http.createServer` on one process — and the measurement was made there: six concurrent `GET /api/health` fired during a cold boot → **6 × 200, one distinct `instance_id`, one `Starting Nest application` line**. And Fluid off is a dashboard setting nobody can see in the tree; code that is correct only while a setting somebody else can flip is right is the shape the repository refuses on the payment path, and the reason not to accept it here is the same, at lower stakes.

### 4.3 A misconfigured instance answers `503` for its lifetime

**What.** `createApp({ onBootFailure: "reject" })` makes a `ConfigurationError` thrown during `NestFactory.create` reject the cached promise instead of ending the process. The rejection is never retried. Every invocation's `await listener` throws into the handler's `catch`, which answers `503` with `{ status: "misconfigured", error: "<the error's message>" }` — the message names the variable — and sets `x-instance-id` by hand, because Express never ran and the middleware that would have set it never existed. The failure is logged once per instance, from a `.catch` attached to the promise at module scope.

**The finding underneath it.** What Nest does by default is worth reading in the source rather than the documentation, because the documentation says "abort on error" and the source says what abort means. In `@nestjs/core@11.2.3`, `nest-factory.js` line 107 computes `const teardown = this.abortOnError === false ? rethrow : undefined` and passes it to `ExceptionsZone.asyncRun(…)`. In `errors/exceptions-zone.js`, line 6 is `const DEFAULT_TEARDOWN = () => process.exit(1)`, and the zone's `catch` is: log the error through `ExceptionHandler`, flush the logger, call `teardown(e)`. So with the default flag the error is logged and the process exits, from inside `create`, before `create`'s promise can settle — `await NestFactory.create(...)` never returns and never throws; the process is simply gone. Line 123's `process.abort()` in `handleInitializationError` is unreachable belt-and-braces for that branch. With `abortOnError: false`, the teardown is `rethrow`, the error propagates out of the zone into `initialize`'s `catch`, `handleInitializationError` rethrows it, and `create` rejects.

That is exactly what the local entry relies on and has relied on since Phase 1. `dist/main.js` under the harness with a bad variable logs the error, exits `1` and binds no port, so `startApiInstance` reports "never became healthy" and the suite fails loudly before a test runs. The task's transcript confirms it is unchanged: the local entry with `SUPPLIER_TIMEOUT_MS=abc` exits `1` without binding the port. Inside a function invocation the same `process.exit(1)` is a different event: the instance dies mid-request, the platform answers with its own `500` because nothing wrote a response, and the next request cold-boots a fresh instance that reads the same environment and dies the same way. Every request pays a full Nest boot to reach the same throw; the pool connects and is discarded each time; the log fills with `Starting Nest application` and a stack trace, in pairs. A boot loop, wearing the costume of a flapping site. Hence the seam: `onBootFailure` is `"exit"` by default so `main.ts` changes nothing, `"reject"` from `vercel.ts`, and `create-app.ts` translates it into Nest's flag and does nothing else with it.

**The obvious alternative.** Retry the boot per request. A rejected promise is a failed attempt; drop it and try again on the next invocation, so that a transient failure — a database that was resuming, a DNS blip — heals itself without a redeploy.

**What goes wrong with the alternative.** Nothing that throws during `create` is transient. The config providers throw on the *shape* of a variable — unset, not a URL, not a whole number in decimal digits — and the environment cannot change under a running instance; fixing it means a redeploy, and a redeploy creates new instances that read the corrected value on their own first invocation. So a retry per request is the boot loop again with one step removed: every request rebuilds the container to hit the same throw, with the pool and the logs churning underneath, and the operator's `curl` sees a `503` that took two seconds to produce instead of one that took a millisecond. A rejection kept for the instance's life gives the same honest answer at the cost of nothing, and the answer names what to fix. R11's whole point is that a misconfigured deploy must not look like a dead site; `GET /api/health` is the boot probe because `200` with an `instance_id` means the container built and `503` says which variable did not. The task's transcript: `SUPPLIER_TIMEOUT_MS=abc` → `503 {"status":"misconfigured","error":"SUPPLIER_TIMEOUT_MS must be a whole number written in decimal digits, not \"abc\""}`, the second request the same body with the same instance id, the process alive.

**The `.catch` that is not error handling.** `listener.catch(…)` at module scope does two things with one statement, and the second is the one that is easy to miss. It logs the failure once per instance, with `instance_id` and the message, so the function log has exactly one line per dead instance rather than one per request. And it marks the rejection *handled*. Without a handler attached, a promise that rejects before the first request reaches `await listener` — which is every misconfigured instance, because the boot begins at module evaluation and the request arrives later — is an unhandled rejection, and Node's default for those is to end the process. That is the platform's `500` and the boot loop again, reached by a different road. `.catch` returns a new promise and leaves `listener` itself rejected, so every later `await listener` still throws the original error into the handler's `catch` and the `503` still carries the variable's name.

### 4.4 `x-instance-id` is Express middleware, and what it proves

**What.** `INSTANCE_ID` is `randomUUID()` evaluated once when `instance-identity.ts` loads. `createApp()` registers `app.use((_req, res, next) => { res.setHeader("x-instance-id", INSTANCE_ID); next(); })` on the Express adapter before `init()`, so it sits ahead of Nest's body parsers and router in Express's stack. `GET /api/health` repeats the value in the body as `instance_id`. `vercel.ts`'s `503` sets the header by hand. That is the whole mechanism.

**The obvious alternative.** A Nest interceptor — `@Injectable() class InstanceIdInterceptor implements NestInterceptor`, registered globally with `APP_INTERCEPTOR` — which is the idiomatic Nest way to touch every response and lives inside the DI container where everything else does.

**What goes wrong with the alternative.** Three kinds of response never reach an interceptor, and each is one the race runner will count. A guard's refusal short-circuits the request pipeline before any interceptor runs, so the `401` for a missing admin token would carry no header — and the runner authenticates against the admin surface on every run. An unknown route has no handler for an interceptor to wrap, so `/api/nope` would answer Nest's JSON `404` without it. And an exception filter writes its response after the interceptor chain has already unwound, so any error path is bare. Express middleware registered on the adapter runs before Nest's router sees the request at all, which covers all three. The acceptance file proves the two that can be proven without breaking something: `POST /api/admin/payment-events/sweep` without a token → `401` with the header; `GET /api/nope` → `404` with the header. The `503` is the fourth kind — no container, no Express, no middleware — and is the reason the handler sets it by hand.

**What it will prove on Vercel, and what it cannot.** A distinct id is a distinct process: a module evaluates once per process, a function instance is a process, so two responses carrying different ids came from two instances. That rules out the one reading that would make a live run worthless — every answer from a single process sharing a single `max: 1` pool, which is the in-process serialisation `architecture.md` §7 measured as "a claim written with no locking at all behaves identically to the correct one". It does **not** prove that those processes were alive at the same moment: two ids across fifty webhooks are consistent with one instance being recycled between the first response and the last. The overlap is argued elsewhere — the concurrent fan-out and, for the author's run, the database's own view of it — and the id only removes the tautology. Slice 4's runner will print those limits beside the number rather than folding them into a verdict: *a distinct id proves a distinct process, not that those processes overlapped*; against an external target, exactly one distinct id is a FAIL with the detail *all answers came from one instance — re-run, or check that Fluid Compute is off*; locally, where an id per port is a tautology, INFO only. A run where K = 1 is not cross-process evidence, and the README will say so and record the K of the author's run.

Why a random UUID and not something the platform hands out: Vercel exposes no stable per-instance identifier to the function, and any value derived from the environment would be identical across every instance started from one deploy — the opposite of what this is for. A UUID is not a secret and says nothing about the instance beyond "not the other one".

## 5. `waitUntil` — the seam, closed

**What the platform promises.** A function instance is suspended once its response is written; everything still on the event loop at that moment is not cancelled but *paused*, possibly forever, possibly resumed minutes later on an unrelated request. `waitUntil(promise)` is how the function asks for more time: the platform keeps the invocation alive until the promise settles, bounded by the function's `maxDuration` — which the planned `vercel.json` sets to 60 s, the Hobby ceiling with Fluid off. It is best-effort, with no `SIGTERM`, no shutdown hook, no bound the code could impose that the platform would honour, and the scheduler's header says so rather than pretending to a guarantee: a lost continuation leaves its `payment_events` row pending, and the order-creation drain, the status-poll drain and the admin sweep each find it, because none of the four triggers is load-bearing (`architecture.md` §4). The webhook's `200` was never conditional on the continuation.

**The seam's history.** Phase 2 wrote `WaitUntilContinuationScheduler` complete — constructor takes a `WaitUntil`, `schedule` wraps the work in `guardContinuation` and hands the result over — and wrote the deployment path around it, type-checked, with exactly one thing absent: the import. `resolveWaitUntil()` returned `undefined`, its header said so in capitals, and it said why: Phase 6 owned deployment, and a dependency added three phases early is one that gets version-bumped by a bot before anything has ever imported it. Returning `undefined` rather than throwing was what kept the seam honest in both directions — locally the expected answer with no noise; on Vercel a loud boot-time `error` line saying the deployment was running without its continuation guarantee, not a refusal to boot over a feature the drains already cover. The header prescribed its own closing as two edits, and those two edits are what this slice made: `pnpm --filter @game-shop/api add @vercel/functions`, pinned exact at `3.9.7` with the lockfile committed, and `import { waitUntil } from "@vercel/functions"` with `return waitUntil`. Nothing else changed — not the interface, not the module, not a caller — which was the point of a seam over a `TODO`. The header now reads as history, and the return type still admits `undefined` so that the module's loud branch stays meaningful for a build that reopens the seam.

**Why the module consults it only on `VERCEL === "1"`.** `scheduling.module.ts` reads `process.env.VERCEL` and calls `resolveWaitUntil()` only when it is `"1"`; otherwise it builds `TrackedContinuationScheduler` without calling the seam at all. The variable is chosen over `NODE_ENV` because the question is not "is this production" but "is there a platform holding the process's lifetime": a local production build sets `NODE_ENV=production`, has a `SIGTERM`, and wants the tracked implementation with its shutdown drain. `create-app.ts` and `health.controller.ts` read the same variable for the same reason — the JSON logger and `runtime: "vercel"` are facts about the platform, not about the environment's name.

**Why the import is safe everywhere.** The `import` at the top of the scheduler file runs in every process that loads the scheduling module — `pnpm dev`, the harness's four instances, every test — not only on Vercel. It is safe because `@vercel/functions` does no platform work at import time. Its `waitUntil` is `getContext().waitUntil?.(promise)`, and `getContext()` is `globalThis[Symbol.for("@vercel/request-context")]?.get?.() ?? {}` — the request context is looked up on `globalThis` at *call* time, and when there is none the optional call does nothing. So importing it off-platform cannot throw, and even calling it there is a silent no-op rather than an error. The seam did not need to become a dynamic import to close.

**What the unit file pins**, and why it matters here. `resolveWaitUntil()` returns a function — a regression there is the module's boot-time branch silently taking the wrong arm. And `schedule` hands the platform a promise that can only ever fulfil, even when the work it wraps rejects, because `guardContinuation` runs first and `waitUntil` second, never the other way round: the platform attaches no rejection handler of its own, so a raw rejected `work()` promise would be an unhandled rejection inside the instance — precisely the crash `vercel.ts` exists to keep one bad boot from causing, reached instead by one bad continuation. The spy is a closure that records its argument; the RED inverted the assertion to `.rejects` and Vitest reported `promise resolved "undefined" instead of rejecting`.

## 6. The simulator's self-call had no timeout

**What.** `PaymentSimulatorService.deliver` posts the webhook payload to `PAYMENT_WEBHOOK_URL` with `fetch`. Before this slice the call carried no `signal`; `git diff` of the file removes no `signal:` line because none existed. Now: `signal: AbortSignal.timeout(WEBHOOK_SELF_CALL_TIMEOUT_MS)` with the constant at `10_000`, and in the `catch`, a `TimeoutError` or `AbortError` becomes `WebhookDeliveryFailure.Unreachable` with the detail `no answer from <url> within 10000 ms`, where any other rejection keeps `could not reach <url>: <message>`.

**Why it mattered only now.** Locally the webhook is the same process one hop away, or one of four instances on the same machine; a hang there is a local bug that a developer sees. On Vercel the self-call is a *second invocation* of the same function — possibly a cold one, paying module evaluation, `init()`, the first connection and perhaps a Neon resume, ≈ 1.5–2.5 s by the technical spec's estimate. Without a bound, an inner invocation that never answers holds the outer one open to the platform's `maxDuration`, and a hung simulation becomes a 60 s wait that ends in the platform's own error rather than in this class's honest *no answer*. The bound must be comfortably above a cold boot and it must exist; 10 s is generous on purpose. The supplier's `/issue` budget is 5 s per probe in the live profile because a slow supplier must be read as `unknown` promptly so the retry policy can act; nothing here retries, and the only cost of waiting longer is the caller's patience.

**How it maps to the existing outcome.** The bound expiring is the same fact as a dead socket — the shop does not know whether the webhook stored the event — so it maps to the outcome that already carried that meaning, `Unreachable`, whose report says exactly that the event may have been stored. No new outcome, no new branch in the controller; the detail string is the only change a reader of the log sees, and it says "no answer within 10000 ms" rather than "could not reach", which would read as a refused connection. Measured, from the task's transcript: the simulator pointed at a socket that accepts and never answers returned `502 … no answer from … within 10000 ms` at 10.007 s.

## 9. What a reviewer might challenge

- **Why not two Vercel projects — the static site on one, the API on another — with CORS?** Because the shop calls itself. The browser calls relative paths, and the API's three self-call URLs — both suppliers and the payment webhook — point at its own origin; on one project they are the production alias and nothing else. Two origins means a preflight on every `POST` the page makes, a second set of URLs to keep in step, and a `vite.config.ts` proxy that no longer mirrors the deployment. The technical spec's §1 chooses one project at the repository root so that `apps/web` has zero source change and the rewrite is the only routing that exists.
- **Why not `api/[...path].ts` — Vercel's own catch-all convention?** It still needs the `/internal/*` rewrite, because that prefix is not under `/api`, so it buys nothing over `api/index.js` plus two rewrites (technical spec §2.1). And it would be `.ts`, which is the next challenge.
- **Why is the entry `.js` and not `.ts`?** The root is `"type": "module"`, so `@vercel/node` loads it as ESM and follows the re-export into `apps/api/dist/`, already compiled by `pnpm build` under `apps/api/tsconfig.build.json` — the one tsconfig that owns that source. A `.ts` at the root would be compiled a second time by the platform under a tsconfig nobody in this repository wrote, with whatever `emitDecoratorMetadata` it chose, and Nest's DI would be the first thing to notice. `tsc -p tsconfig.scripts.json` includes only `scripts/`, so it would not even be typechecked. A one-line re-export has nothing to typecheck; the import it names is checked where it is written.
- **Why not retry the boot per request?** §4.3. Nothing that throws during `create` is transient; the environment cannot change under a running instance; a retry is the boot loop with one step removed. A rejection kept for the instance's life gives the same answer at no cost and names the variable.
- **Why not an interceptor?** §4.4. A guard's `401`, an unknown route's `404` and a filter's response never reach one, and two of the three are asserted.
- **Isn't a module-scope singleton exactly what this repository forbids?** It forbids a singleton that *holds a guarantee* — a lock, a counter, a "have I seen this event" set — because two requests are two processes and the singleton is per process. `listener` holds a resource that is meant to be per process. The distinction is the one `vercel.ts`'s header draws, and it is the distinction the whole architecture rests on.
- **You measured six overlapping requests locally; with Fluid off that cannot happen on Vercel.** True, and said in §4.2. The promise is correct under either setting; the measurement was made on the shape that can overlap; and code that is right only while a dashboard toggle is right is not the shape this repository accepts.
- **Ten seconds for the self-call is arbitrary.** It is a bound, not a budget: the class does not retry, so the number only has to be above a cold boot and below the ceiling. 5 s would be the supplier's number for the supplier's reason — promptness for a retry policy — and there is no retry here.

## 10. Interview questions this answers

**"Walk me through a request on Vercel."**
The rewrite sends `/api/*` and `/internal/*` to the one function built from `api/index.js`, which re-exports `apps/api/dist/vercel.js`. That module, on its first evaluation in a process, builds the container — `createApp({ onBootFailure: "reject" })`, the same function `main.ts` calls — initialises it, and stores the promise of the Express listener. The handler `await`s that promise and calls the listener with Node's own `req` and `res`; Express runs the instance-id middleware, the body parsers, Nest's router, guards and filters, and ends the response. The invocation is over when the response ends, plus whatever the scheduler handed to `waitUntil`. Locally the identical handler sits behind `http.createServer` on 5401, and seven tests drive it there.

**"Why one `createApp()` and not two entries that each call `NestFactory.create`?"**
Because the claim of the phase is that nothing about the shop's behaviour changes between local and live, and two containers written separately can only agree by discipline. One expression both entries call makes it a property of the code: the same modules, the same config providers refusing the same variables, the same middleware. The entries keep only what they disagree on — a port and shutdown hooks on one side, `init()` and a cached promise on the other — and the one option `createApp()` takes is the one genuine disagreement, what a failed boot should do.

**"Why cache a promise instead of the app?"**
Because `if (!app) app = await build()` is a check-then-act across an `await`. Two requests on a cold instance both see `undefined` and both build: two containers, two `DatabaseModule`s, two `max: 1` pools — the per-instance budget Neon was sized against, doubled, with no error logged. A promise on the module's first line is built once per process during evaluation, before any request can arrive, so every invocation awaits the same one. Measured: six concurrent `/api/health` during a cold boot, six `200`s, one instance id, one `Starting Nest application`.

**"What happens if `SUPPLIER_TIMEOUT_MS` is wrong on Vercel?"**
The config provider throws while the container is built, on the instance's first invocation. Nest's default would `process.exit(1)` from inside `create` — the promise never settles, the platform answers its own `500`, and the next request boots a fresh instance that dies the same way. `vercel.ts` passes `onBootFailure: "reject"`, so the promise rejects instead, a `.catch` logs it once and marks it handled so Node does not end the process over an unhandled rejection, and every request answers `503 { status: "misconfigured", error: "SUPPLIER_TIMEOUT_MS must be a whole number written in decimal digits, not \"abc\"" }` with `x-instance-id` set by hand. It is not retried: the environment cannot change under a running instance, and a redeploy creates new instances. `/api/health` is the boot probe.

**"What does `x-instance-id` prove, and what doesn't it?"**
A distinct id is a distinct process — one UUID per module evaluation, one evaluation per process, one process per instance. So two ids across a run rule out the reading that would make the run worthless: every answer from one process serialising on one `max: 1` pool. It does not prove the processes overlapped; two ids across fifty webhooks are consistent with one instance recycled in the middle. The runner will print the count with that caveat beside it, FAIL on exactly one id externally, INFO locally where an id per port is a tautology.

**"Why middleware rather than an interceptor for the header?"**
Because the responses that matter most for a runner never reach an interceptor: a guard's `401` short-circuits before one, a `404` has no handler for one to wrap, a filter writes after the chain has unwound. Express middleware registered on the adapter before `init()` runs before Nest's router sees the request. The `401` and the `404` are asserted with the header; the `503` has no Express at all and is set by hand.

**"You have three drains. Why does `waitUntil` matter?"**
Promptness, not correctness. Without it the continuation is paused when the instance freezes at the response, and the order settles when the next drain finds the pending row — a status poll, the next order creation, or the admin sweep. With it the platform keeps the invocation alive until the continuation settles, bounded by `maxDuration`. It is best-effort, and the scheduler's header refuses to call it more than that; the system is designed not to need it.

**"The seam returned `undefined` for three phases. Why not just install the package in Phase 2?"**
Because Phase 2 did not deploy, and a dependency installed three phases before anything imports it is one a bot bumps in the meantime. The class was written complete, the module's selection was written complete, and one function returned `undefined` with its own closing instructions in the header. Closing it was two lines and no redesign — which is what a seam is for, as opposed to a `TODO`. And the import is safe everywhere because `@vercel/functions` resolves the request context on `globalThis` at call time; off-platform it is a no-op, not a throw.

**"Why did the simulator's self-call need a timeout now and not before?"**
Because before, the other end was the same process one hop away. On Vercel it is a second invocation, possibly cold, and without a bound a hung inner invocation holds the outer open to the 60 s ceiling and ends in the platform's own error. The bound is 10 s — above a cold boot, below the ceiling, and generous because nothing here retries — and expiring maps to the outcome that already meant "no answer, the event may have been stored". Measured at 10.007 s against a socket that never answers.

**"What did you find that wasn't in the plan?"**
That Nest's `abortOnError` is a `process.exit(1)` inside an `ExceptionsZone` teardown, so `create`'s promise never settles — which is what the local entry relies on and what would be a boot loop in a function, and why `createApp()` takes an `onBootFailure` option instead of one policy. That the simulator's self-call had no bound, which the deployment's shape exposed rather than created. And two sentences in the tree that say the wrong thing: a RED line misquoted in the unit file's header, and a spec paragraph that puts this file's assertions and port under Slice 3's file.
