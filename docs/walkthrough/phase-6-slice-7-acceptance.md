## 2. The words this document uses

- **Suite / layer** — one of the runners in §1's table. "Layer" is the `@layer` tag a file carries: `unit`, `integration`, `e2e`, or `script`.
- **Disposition** — one of six answers for a criterion in the coverage map, two of them with a "with a caveat" variant: *covered* (an automated test asserts the criterion's own words), *covered with a caveat*, *verified live* (proven against the alias, with a transcript, a screenshot or a log line named — new this phase), *verified live with a caveat*, *verified by hand* (a person, a `curl`, a rehearsal, or a reading, named), *verified by hand with a caveat*, *a document*, or *not covered anywhere by name*. The last appears zero times; §5 says where every non-plain-covered criterion was actually verified.
- **The alias** — `https://game-shop-ochre.vercel.app`, the one address that survives every deploy and is public under Deployment Protection's defaults. Every self-call names it.
- **Instance** — the process the platform runs a function in. With Fluid Compute off, one instance serves one request at a time; a second concurrent request gets a second instance.
- **K** — the number of distinct `x-instance-id` values one burst of a check saw: the harness prints it as a verdict (eight concurrent `GET /api/health`, `PASS` at ≥ 2); `webhooks`, `same-event` and `promo` print it as an `INFO` line for their own burst. K = 1 means that burst was not cross-process evidence, whatever the checks after it say.
- **`SKIP` by name** — what a check prints for an assertion it cannot make without a database: the label the `PASS` or `FAIL` would have carried, never counted in the tally. The reviewer's runs have 39 of them inside a `9/9` that counts only what ran.
- **The recorded run** — the fifth of Slice 5's five reviewer attempts and the second of two consecutive `9/9`s, kept as `docs/walkthrough/evidence/phase-6-live-race-run.txt` (285 lines). The README's run.
- **The final run** — this slice's second task: the three local suites and two live attempts at 15:12–15:17 UTC on 2026-09-16, load 5.8–11.3. Every number in the lead blockquote is from it unless another run is named.
- **The author's full run** — Slice 5's, with `RACE_DATABASE_URL` forwarded: the 39 skipped assertions made for real, `26 distinct backend pid(s)`.
- **The rehearsal** — Slice 6's clean clone of the repository, every README command run as written, one README edit made as a result.
- **The reset** — `POST /api/admin/demo/reset`: one transaction, every order's row lock first, six deletes in foreign-key order, promo counters to zero, every key released, every supplier knob to baseline, the baseline read last. `pnpm demo:reset` is the operator's spelling; `RACE_DEMO_RESET=1` is the runner's.
- **Baseline** — locally, the seeded state the harness asserts before and after every file: `products = 12`, `unclaimed = 50`, `orders = 0`, zero rows in the event, delivery, attempt, request and redemption tables, `sum(used_count) = 0`. Live, the reset's `now` line: `products 12 · keys_total 50 · keys_unclaimed 50 · orders 0 … promo_used_count 0 · promo_redemptions 0 · supplier_behaviour_baseline 2`.
- **Inversion** — the RED method for an assertion added after the behaviour exists: point it at the wrong state, run, read the failure, restore byte-identical. Every RED this phase's three files carry is one (§6).
- **Load** — the one-minute load average `uptime` prints, recorded beside every run, because Phase 5's two failures were load and not code, and this phase's one local `500` was a disk (§7).

## 3. What each suite and the live run prove — and cannot prove — about the deployment

### One claim, seven kinds of evidence

The phase makes one claim — *the guarantees live in Postgres, not in a process's memory, and the shop at the alias is the same shop as the one on the laptop* — and no single suite can see all of it. This section is the sentence per suite the brief asked for: what it proves about the deployment, and what it cannot.

- **The unit file proves the seam and the class, and nothing about a platform.** `wait-until-continuation-scheduler.test.ts` — 3 cases, no HTTP, no container: `resolveWaitUntil()` is a function (the seam Phase 2 left open is closed — `@vercel/functions@3.9.7`'s `waitUntil`); `WaitUntilContinuationScheduler.schedule` hands the platform a promise that can only ever fulfil, even when the work rejects — a hand-written spy records what "the platform" received. It cannot say whether the platform honours the promise: `waitUntil` off-platform is a silent no-op, and the file says so. On the alias the boot line read `implementation: "wait_until"` and every check's order settled — that is the platform's half, and it lives in the transcript, not here.
- **`vercel-entry.test.ts` proves the compiled handler over `node:http` — the container, the header, the `503` — and cannot prove Vercel's routing.** Port 5401; a driver script written at `beforeAll` imports `apps/api/dist/vercel.js` and hands its default export to `http.createServer(...).listen(port)` — what `@vercel/node` does, minus the platform. 7 tests: `GET /api/health` → 200 with `instance_id` equal to the `x-instance-id` header and `runtime: "node"`; two requests → the same id; `GET /api/nope` → JSON 404 carrying the header; a guard's 401 carrying the header; `POST /api/orders` with a JSON body → 201 (body parsing through the handler); a second driver spawned with `SUPPLIER_TIMEOUT_MS=abc` → `503 { status: "misconfigured" }` naming the variable, a second request the same body, the process alive. What it cannot see: `vercel.json`'s three rewrites (`/api/*` and `/internal/*` to the function, everything else to the static site), the `maxDuration: 60`, the region, Fluid Compute's state — every one of those is the platform's, and the only evidence for them is the curl ladder on the alias (`/order/anything` → HTML, `/api/nope` → JSON 404, `PUT /internal/suppliers/a/behaviour` → 200) and the deploy log's `λ api/index (1.93MB) [fra1]`.
- **`demo-routes.test.ts` proves the reset, drain and restock contracts on one local instance.** Port 5402; one `dist/main.js`; 13 tests: the guard table (three routes × no token → 401 with `WWW-Authenticate: Bearer`, wrong token → 401, an unconfigured instance → 503 naming `ADMIN_TOKEN`); `drain` → a purchase settles `out_of_stock`; `restock` releases exactly the drained count and leaves a real `req_%` claim alone; `reset` returns counts equal to what the test created and `now` at the seeded baseline; a second `reset` → all zeros, `changed: false`; `assertBaseline` read off Postgres last. It is single-instance by design — `architecture.md` §7's integration layer, "nothing here needs overlapping requests" — so it proves the *contract* of each route and not what the reset does under a live lock (Slice 3's `55P03` measurement, by hand) or what the drain does against a claim another process holds (14.31 s, by hand).
- **The local race proves four processes on Docker.** `pnpm race` on 4601–4604, nine checks, the database in hand: every assertion made, `4 distinct backend pid(s)` from `pg_stat_activity`, the baseline handed back. It proves the mechanism across processes that share a kernel and a Docker-local Postgres at ~5 ms a round trip. It cannot prove anything about a process the author did not start, a database on another continent, or a platform that freezes an instance at the response — which is exactly the gap the next three rows fill.
- **The reviewer's live run proves HTTP-visible verdicts across dozens of instances, with the database half `SKIP`ped by name.** The same nine files against the alias, no database: every check's HTTP assertions made for real — statuses, `stored`/`duplicate`, `delivered`, the response bodies — and 39 database-side assertions printed as `SKIP <label> — needs DATABASE_URL`, never counted. Its witness is `x-instance-id`: in the final run's second attempt, fifty reports of one payment were answered by **30** distinct instances and produced one key; twenty `LIMIT3` applications by **19**; ten `ONCEONLY` by **10**; twenty redeliveries of one `event_id` by **12**. What it cannot prove: that one row exists in `deliveries`, that `used_count = 3`, that the ladder wrote `a/1, b/2, a/3` — those are the 39 lines, and the run says so by name. And K is a count of processes, not of overlap: a distinct id proves a distinct process, not that those processes were alive together — the runner prints that sentence under every `PASS`.
- **The author's full run proves the database half too.** `RACE_DATABASE_URL=<the direct endpoint>` forwarded: the mode line changes, the 39 `SKIP`s become `PASS`es — `used_count = 3 for LIMIT3`, `exactly THREE attempt rows after the retry (a/1, b/2, a/3)`, `a/1 reads status=ok, probe_count=2` — and the harness's database half reads `26 distinct backend pid(s)` where the laptop reads 4. Twenty-six is Neon's count of how many pooler-owned server connections the run needed at once, printed with that limit. It is one run by one person with a secret a reviewer does not have, which is why it is corroboration for the reviewer's run and not a substitute for it.
- **The rehearsal proves the README's commands.** A clean clone, `pnpm install` (the `prepare` hook built `packages/*`), `pnpm db:setup` (7 migrations, the seed), `pnpm dev`, `curl /api/health`, `pnpm race` **9/9**, `pnpm test` **17 / 144** + **6 / 69**, `pnpm test:e2e` **65** — every command as the README prints it, one deviation noted (`POSTGRES_PORT=5434` and a distinct Compose project name, so the running stack was untouched), one README edit made as a result. It proves a reviewer following the text reaches a working shop. It cannot prove the *published* text does, because it ran before the repository URL replaced the README's placeholder (row 2.6-2's caveat, §5).

**What nothing tests, and this document says so rather than pretending a row covers it.** Vercel's rewrite rules — proven by three `curl`s in Slice 5's ladder and by every check that reached `/api/*` and `/internal/*` since, never by an assertion in the tree. R6's apply-vs-pay window — open by decision since Phase 5, unchanged by a phase that changes no behaviour by rule. A real "next day" — 2.1-6's evidence is a six-minute idle past Neon's five-minute suspend, not twenty-four hours. The `503` boot probe and `maxDuration: 60` on the alias — every variable was right the first time, and staging a `503` live means deploying a broken environment on purpose; the acceptance file on `node:http` is the cheaper proof, and the recorded run's longest continuation (~6 s) sits under the classic 10 s default as well. A Playwright *suite* against the live URL — the e2e config starts its own servers and takes no base URL; the manual drive with four screenshots is the cover. §5 has each with its reason.

### One database, one runner at a time — and a live target with its own discipline

Locally, everything shares one Postgres on 5433, one 50-key pool, four promo counters and a ledger; each suite asserts or depends on the baseline, so the order is fixed and this slice ran exactly it: `pnpm test:e2e` (65 in 59.2 s), then `pnpm race` (9/9), then `pnpm test` (17 / 144 in 65.27 s; 6 / 69 in 259 ms) — with `orders 0 / sum(used_count) 0 / promo_redemptions 0 / unclaimed 50 / supplier_requests 0` read after every step. Each later run's baseline is the proof the earlier one cleaned up.

Live, the discipline is different because the reviewer has no database to clean with: the checks leave their orders on the shop, and `RACE_DEMO_RESET=1` calls the reset after the last check and prints what it removed. "Twice in a row" is true because the first run ended with keys back at 50 and counters at 0, not because the checks tolerate residue — `recover-out-of-stock` would meet `keys_unclaimed 44` after one un-reset run and its drain would assert against a pool it expects full. The final run's two reset blocks each read `removed orders 38 · payment_events 55 · deliveries 6`, which is the checks' own arithmetic (Slice 5 §6): 38 orders is `before-order` 1 + `create-order` 2 + `promo` 30 + one each for the five remaining checks; 55 events is the fifty distinct `event_id`s plus `same-event`'s one plus one each for the three recover checks and `before-order`.

### Why the live run is not in `pnpm test`

`pnpm test` needs only Postgres and runs in a minute; the live command needs the alias awake, the demo token, and a network, and leaves orders behind until the reset. A suite that fails because Neon was asleep is a false statement about the shop, so the live run is a command a person runs and reads, and its record is a transcript in `docs/walkthrough/evidence/`, not a green tick. The same reason `pnpm test:e2e` is separate from `pnpm test` (Phase 4), applied to a target the runner did not start.

### The `@regression` line

The convention Phase 2's slice 8 set and every closing document since restated: the permanent, one-criterion-at-a-time guards carry the tag; the acceptance-level files do not. `wait-until-continuation-scheduler.test.ts` carries it — three cases, each one claim of the seam's header, inverted against the behaviour. `vercel-entry.test.ts` and `demo-routes.test.ts` do not, for the reason `promo-codes.test.ts` and `failure-and-recovery.test.ts` do not: a failure in either says the seam between the handler, the container and the routes broke, and the file to open is one of the others.

## Interview questions this answers

**"What does each suite prove about the deployment?"**
The unit file proves the seam is closed — `resolveWaitUntil()` is a function — and that a rejecting continuation reaches the platform as a fulfilled promise; it cannot see whether the platform honours it. `vercel-entry.test.ts` proves the compiled handler builds the container once, stamps `x-instance-id` on a 200, a 404 and a 401, parses a body, and answers `503` for its whole life when a variable is wrong — driven through `node:http` the way `@vercel/node` drives it, minus the platform; it cannot see `vercel.json`'s rewrites, the region or the timeout. `demo-routes.test.ts` proves the reset, drain and restock contracts on one instance, and cannot see a live lock. The local race proves four processes on Docker. The reviewer's live run proves every HTTP-visible verdict across thirty instances and says by name which 39 database assertions it could not make. The author's run makes those 39 and reads 26 backends. The rehearsal proves the README's commands. Each is blind to the others' subject, and the only one that sees the deployment is the one a reviewer can run without a secret.

**"The reviewer's run is 9/9 with 39 SKIPs. Is that an honest pass?"**
Yes, because the 39 are not counted and are named. A pass that hid them would claim `used_count = 3` on the strength of nothing; a fail would punish a reviewer for not holding a database secret. The check prints the label the `PASS` would have carried, with `— needs DATABASE_URL`, and the tally counts only what ran. The author's run with `RACE_DATABASE_URL` is where those 39 become `PASS` lines, and it is recorded beside the reviewer's rather than in its place.

**"The first live attempt was 8/9. Is the deployment broken?"**
No — the one `FAIL` was the harness's own witness on the cheapest endpoint: eight ~1 ms health calls served back to back by the one instance a cold platform had warm, while the work checks of the same run were answered from 15, 10, 9 and 30 instances. The `FAIL` says so and names the remedy; the second attempt read K = 5. Vercel's rewrite rules, except by three `curl`s in the ladder and every check that reached the function since. R6's window, open by decision since Phase 5. All five, by the same name: `pnpm race webhooks`, `same-event`, `before-order`, `recover-out-of-stock`, `promo`, with `RACE_BASE_URLS` pointed at the alias.
