# Phase 6 · Slice 2 — Neon holds the shop's memory, and the local shop runs against it

> Nothing in this slice is deployed, and — the standing rule of the phase — nothing about the shop's behaviour changes. What exists after it is the shop's memory moved off the laptop: a Neon project in Frankfurt (`aws-eu-central-1`, Postgres 16.15, a 0.25 CU compute that scales to zero when idle, `max_connections 112`), carrying the seven migrations and the seed exactly as the Compose container does, reached by the **same** `pg` driver the shop has used since Phase 1, through a pooled endpoint that speaks the plain Postgres wire protocol, over `sslmode=verify-full`. The shop's own `dist/main.js`, started on a laptop with `DATABASE_URL` pointed at that endpoint, sold a key: create → `LIMIT3` → simulate → `delivered`, 2.41 s over three polls, and the rows read back over the direct endpoint were the same rows the local database would hold — one delivery, one `req_…_a_1` claim, one redemption, `LIMIT3.used_count 1`. The seed was run twice and the second run changed nothing it was not allowed to change.
>
> Three things carry the slice, and each is a decision about *which endpoint owns which fact*. **The pooled endpoint is PgBouncer in transaction mode, and the codebase was audited for it rather than trusted to it** — one grep, quoted in `packages/db/src/client.ts`, whose only code-line hit is a `SET LOCAL` that dies with its transaction; every guarantee the shop makes is taken inside `BEGIN … COMMIT` on one checked-out connection, which is exactly the unit the pooler pins to one backend. **Migrations and the seed go to the direct endpoint from an operator's shell and never from a build** — `DATABASE_URL=<neon-direct> pnpm db:deploy`, all pending migrations in one transaction, a seed that is safe to re-run but is not a reset, and a variable that wins because `scripts/with-env.ts` layers the real environment last. **The driver did not change** — the plan since Phase 1 had been to swap `pg` for Neon's WebSocket driver at deployment; the swap was refused, because a Vercel Node function can open a TCP socket and because the two measurements the whole argument rests on — architecture §7's four-process table and `client.ts`'s named-versus-unnamed parse — were made with *this* driver and would otherwise be true only on a laptop.
>
> Reading the delivered work found one thing that matters and three that are worth a line each. `pnpm race webhooks` against the **one** local instance failed, twice out of twice, and the failure is architecture §7's single-process warning made visible by latency rather than a defect in the pooler: fifty webhooks were stored in about two seconds, then fifty continuations queued in Node on the process's one connection at ~30 ms per round trip instead of ~5, the supplier stub in the same process waited on the same pool and hit its 2 000 ms deadline, and the polls waited past `connectionTimeoutMillis` and answered `500`. The guarantees held — one key per order, both runs, with the timeout trap occurring organically and handled as designed — and the check could not finish. Beside it: the script's cleanup raced the still-running continuation and left one orphan claim and one supplier-ledger row per run; one idle `game-shop` connection stayed in `pg_stat_activity` after everything was closed, which is PgBouncer's retained backend and not a leak; and `sslmode=require`, the spelling Neon's console offers, is a spelling `pg` will stop verifying in its next major version.

## 2. The words this document uses

- **The direct endpoint** — the host that is a Postgres backend, one session per connection, everything a session can hold. Migrations, the seed and every `psql` read-back go here. It is never in a function's environment.
- **The pooled endpoint** — the host with `-pooler` in its name: PgBouncer in transaction mode in front of the same database. The function's `DATABASE_URL`, and the local instance's in this slice. It speaks the ordinary Postgres wire protocol, which is why the driver did not have to change.
- **Transaction mode** — the pooler's rule for lending backends: a client gets a server connection when it sends its first statement and keeps it until that statement completes or, inside `BEGIN`, until `COMMIT` or `ROLLBACK`; then the backend goes back into the pooler's pool and the client's next statement may land on a different one.
- **Session state** — anything Postgres keeps on the backend between statements rather than in a table: a `SET` variable, an advisory lock, a `LISTEN` subscription, a named prepared statement, a cursor held open, a temporary table. Through transaction mode it silently lands on the wrong backend later, which is why the audit exists.
- **The pinned unit** — the span during which a client is guaranteed one backend: a transaction. `client.ts`'s `transaction()` checks out one connection for `BEGIN … COMMIT`, so the two coincide by construction.
- **The audit grep** — the one command in `client.ts`'s header that lists every session-state construct and searches the tree for it. Its only code-line hit is the demo reset's `SET LOCAL`.
- **`sslmode=verify-full`** — encrypt, verify the server's certificate chain against a trust store, *and* check that the certificate names the host connected to. `require` in `pg` today means the same thing with a warning; in pg 9 it will mean "encrypt and check nothing".
- **The trust store** — where a client looks for the root certificates it will believe. Node ships its own; libpq looks in `~/.postgresql/root.crt` unless told `sslrootcert=system`.
- **`db:deploy`** — `pnpm run db:migrate && pnpm run db:seed`, the local `db:setup` minus its `db:up`. Run with an exported `DATABASE_URL` naming the direct endpoint; the export wins because `scripts/with-env.ts` layers `.env.example`, then `.env`, then the real environment.
- **Idempotent** — safe to run again against a database that already holds the fixture *and* live state on top of it: definition rows are rewritten from the fixture, state the shop or the supplier wrote is not touched. Not the same as a reset, which is Slice 3's endpoint.
- **A continuation** — the work a webhook schedules after answering `200`: process the stored event, which means one transaction to claim the order for issuance, an HTTP call to the supplier, and one more transaction to record the answer.
- **Starvation** — what §5 measured: one process's single connection with more transactions queued for it, in Node, than the latency to the database lets it serve before the process's own deadlines fire. The database is idle; the queue is in the shop.
- **K** — the number of distinct `x-instance-id` values the runner saw. Against the one local instance it was 1, which the harness turns into a FAIL by design.

## 3. One purchase, from a laptop through the pooler

The path the verify task's purchase took, because it is the same path a function invocation will take from the second hop on, and because each hop is where one of this slice's decisions is visible.

**Before any request: the pool.** `dist/main.js` starts with `DATABASE_URL` naming the pooled endpoint and `sslmode=verify-full`. Nothing connects yet — `getDatabaseClient()` is lazy — and `GET /api/health` answered in 7.7 ms without opening a connection, which is why Slice 4's warm-up uses the catalogue and not health. The first `GET /api/products` took 270 ms: the pool's first checkout dialled the pooled endpoint over TCP, completed a TLS handshake that Node verified against its own root store with no `ssl` option in the pool config, sent the startup packet — the database name, the user, and `application_name: game-shop` — and ran the one `SELECT`. The pooler lent a backend for the length of that statement and took it back. The warm round trip afterwards was 35 ms, against roughly 5 on Docker: Frankfurt from the operator's desk, and the reason §5 happened.

**The purchase.** `POST /api/orders` — one `INSERT … SELECT … ON CONFLICT (client_request_id) DO NOTHING … RETURNING` through the pool's one connection; the pooler pins a backend for that statement and returns it. `POST /api/orders/:orderId/promo` with `LIMIT3` — `transaction()` checks the connection out, sends `BEGIN`, and from that byte until `COMMIT` every statement the redemption issues goes to the same backend: the order's row lock, the reads, then `UPDATE promo_codes … WHERE used_count < max_uses RETURNING`, `INSERT INTO promo_redemptions … ON CONFLICT (order_id) DO NOTHING`, and the order's new amount under `WHERE status = 'created'`. The amount became `96 750`. `POST /api/payments/:orderId/simulate` — the shop posts a webhook to itself at `/api/webhooks/payment`; the receiver stores the event in one statement, `INSERT … ON CONFLICT (event_id) DO NOTHING`, and answers `200`; and the continuation runs: one short transaction that takes the event under `FOR UPDATE SKIP LOCKED`, moves the order `created → paid` and claims it `paid → delivering` under its row lock; then, *outside* any transaction, an HTTP call to the supplier stub, which in the same process claims a key with `FOR UPDATE SKIP LOCKED` in a transaction of its own; then one more transaction to write the delivery and mark the order `delivered`. Three polls of `GET /api/orders/:id`, 2.41 s in all, and the body carried the key and the promo.

**The read-back.** With the local instance still running, `psql` on the direct endpoint — a plain session, nothing pooled — showed one order, one delivery, one `supplier_keys` row claimed by `req_…_a_1`, one `promo_redemptions` row, `LIMIT3.used_count = 1`. Two doors, one memory: the shop wrote through PgBouncer and the operator read through a backend, and the rows agreed with what the local Compose database holds after the same purchase. That agreement is the entire content of "nothing about the shop's behaviour changes between local and live" at the database layer, and it is the thing a hosted database makes checkable by someone who is not on the laptop.

**What the same path looks like from a function.** Identical from the pool's first checkout onward. The differences are all before it — the environment comes from the platform instead of `with-env.ts`, and the process is one invocation's instance rather than a long-lived server — and one after it: the supplier stub is a *second* invocation with its own pool, not a route in the same process sharing the same one connection. §5 is what that last difference costs when it is absent.

## 4. The five decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision.

### 4.1 A pooled endpoint in transaction mode, and why the codebase survives it

**What the pooler does to a connection.** A client that connects to the pooled endpoint is talking to PgBouncer, not to Postgres. PgBouncer keeps a small number of real backend connections open and lends one to a client only while the client needs it: for a statement sent outside a transaction, for the length of that statement; for `BEGIN`, until the matching `COMMIT` or `ROLLBACK`. Between those spans the client's connection is a socket to the pooler and nothing else — the backend it just used is serving someone else. That is what lets fifty single-connection instances share far fewer than fifty backends, and it is the reason the function's `DATABASE_URL` names this host and not the direct one.

**What that breaks.** Anything Postgres remembers on a backend between statements. `SET application_name` or `SET search_path` at session level applies to whichever backend happened to be lent and evaporates for the next statement; `set_config(…, false)` likewise. A session-level advisory lock (`pg_advisory_lock`) is held by a backend the client no longer has. `LISTEN` subscribes a backend, and the `NOTIFY` arrives on a connection nobody is reading. A named prepared statement — `PREPARE p1 AS …` followed later by `EXECUTE p1` — is the classic one: the later statement reaches a backend that has never heard of `p1`, and `client.ts` quotes the exact error, `prepared statement "p1" does not exist`. A cursor declared outside a transaction or `WITH HOLD` is gone when its backend is. Newer PgBouncer versions can track protocol-level prepared statements on the client's behalf; the codebase does not depend on that, and the argument below does not need it.

**Why this codebase survives it — the audit.** `client.ts`'s header carries the command, quoted here as the file quotes it:

```
grep -rnE "SET LOCAL|SET SESSION|search_path|set_config|pg_advisory|LISTEN|NOTIFY|\.prepare\(" \
  apps packages scripts --include='*.ts'
```

Run again for this document, with `dist/` excluded: one code line matches — `apps/api/src/demo/demo-reset.service.ts:218`, `await tx.execute(sql\`SET LOCAL lock_timeout = '5s'\`)`. Every other hit is a comment: `.prepare(` in the four places that forbid it, `LISTEN` as `LISTENER` and `LISTENS` in `apps/web` DOM-event headers, and the header's own bullet list. There is no advisory lock, no `LISTEN`, no cursor, no session-level `SET`, no `search_path`, and no Drizzle query finished with `.prepare("…")` — which is the one call that would make node-postgres send a *named* parse; every other Drizzle call sends the unnamed statement, Parse/Bind/Execute in one round trip, nothing retained on the backend.

**Why the transaction is the pinned unit and that is enough.** `transaction()` checks one client out of the pool, sends `BEGIN`, runs the callback's statements on that client, and sends `COMMIT` or `ROLLBACK` — the comment above it lists exactly those lines. The pooler pins a backend for exactly that span. So every row lock the shop takes — `SELECT … FOR UPDATE` on the order, `FOR UPDATE SKIP LOCKED` on the inbox and on the supplier's key — is taken and released on one backend, and every status-guarded `UPDATE` that follows a lock runs where the lock is. A statement outside a transaction is self-contained by construction: `INSERT … ON CONFLICT DO NOTHING RETURNING` neither needs nor assumes anything from the statement before it. Nothing in the shop reads a fact in one statement and relies on the *backend* — rather than a table — still holding it in the next.

**`application_name` survives; `pg_prepared_statements` does not.** PgBouncer keeps `application_name` in the parameter set it received at the client's startup and applies it to whichever backend it lends, so `pg_stat_activity` on the direct endpoint still shows `game-shop`, `game-shop-seed` and the race scripts as themselves — the verify task saw the one retained connection under that name (§5.3). The header's other audit, `SELECT count(*) FROM pg_prepared_statements` reading `0` after traffic, is a session-local view: through the pooler an auditor never gets the application's session, so that check is run locally or on the direct endpoint, and the header says so.

**The one `SET LOCAL`, and why it is safe.** Slice 3's demo reset opens its transaction with `SET LOCAL lock_timeout = '5s'`. `LOCAL` scopes the setting to the transaction: it is discarded at `COMMIT` or `ROLLBACK`, which is before the pooler takes the backend back, so no later borrower inherits a five-second lock timeout. A `SET SESSION` in the same place would outlive the transaction on a backend the reset no longer holds, and would then apply to whichever request borrowed that backend next — a request that has no idea it is running under someone else's timeout. That is why the audit lists `SET SESSION` and why the header says the reset must never use it. The reset has not yet run through the pooler; Slice 5 will be its first time, and R9's remedy is written down before it is needed.

**The obvious alternative.** Session mode — a pooler that lends a backend for the client's whole connection — or the direct endpoint itself. Everything works, nothing needs auditing.

**What goes wrong with the alternative.** The arithmetic in `client.ts`: connections held ≈ `max` × live instances. Fifty concurrent webhooks are fifty instances, each holding one connection for as long as its pool keeps it — ten seconds of `idleTimeoutMillis` on a running process, and indefinitely on a frozen instance whose timer cannot fire (R14) — and in session mode, or on the direct endpoint, each of those is a backend, plus the operator's `psql`, the seed, PgBouncer's own retained backends. `max_connections` on this compute is 112. It would fit, most days; it is the kind of margin that becomes a flaky race script rather than an error message, and transaction mode removes the question instead of answering it.

### 4.2 The same driver, and not the serverless one

**What.** `drizzle-orm/node-postgres` over `pg@8.23.0`, locally and live. `client.ts`, `migrate.ts` and the seed use it; `Database` is an alias so that a driver change *could* be one line, and Phase 6 decided not to make it. The architecture's §2 bullets say so with the inline marker.

**The obvious alternative — and the plan until this slice.** `@neondatabase/serverless`, the driver Neon ships for runtimes that cannot open a TCP socket: the same protocol tunnelled over a WebSocket, with a `Pool` that mirrors node-postgres' API. `client.ts`'s header had a section called "PHASE 6 — SWAPPING IN NEON", and architecture §2 said "a serverless driver that supports real transactions" was one of the reasons Neon was chosen.

**What goes wrong with the alternative.** Two of the project's load-bearing measurements would become assumptions at the moment they matter. Architecture §7's table — the key claim weakened to an unlocked read-then-write hands out 20 distinct codes in one process and **9** in four — was measured with *this* pool and *this* `max: 1`; it is the measurement that justifies the harness, the runner's external mode and the README's sentence. And the prepared-statement argument in `client.ts` — that Drizzle passes `name: undefined` and node-postgres therefore uses the unnamed parse — is a statement about *this* driver's wire behaviour. Swap the driver at the deployment boundary and both stay true on the laptop and merely plausible in production, which is the opposite of what the deployment is for. The alternative's one genuine advantage, a WebSocket where TCP is unavailable, does not apply: `apps/api` is a Vercel *Node* function — the Node runtime with Fluid Compute off, not the Edge runtime — and a socket to the pooled endpoint's port is an ordinary thing for it to open. The tech spec's §2.3 records it as the user's decision; the two comments elsewhere that had anticipated the swap (`supplier-key-claim.service.ts`, `orders.service.ts`) now say "Phase 6 weighed a swap … and kept `pg`", and the one walkthrough sentence that still says the swap happens is listed in §5.4.

**The architecture's sentence, corrected.** §2's "Hosted instance" used to end "…and a serverless driver that supports real transactions". It now says the pooled endpoint "speaks the plain Postgres wire protocol — so the same `pg` driver runs locally against the Compose container and in production against Neon, and only `DATABASE_URL` differs", and keeps the old wording as history in the amendment. The property that was always the important one is the protocol, not the driver.

### 4.3 `sslmode=verify-full`

**What.** Every Neon URL in this project ends in `?sslmode=verify-full`, and `.env.example`'s comment says why in the spelling `pg` needs. No `ssl` option is passed to the pool; Node's root store holds the chain.

**What `require` really does in `pg` today.** `pg-connection-string@2.14.0` — the parser `pg` uses for a URL — treats `sslmode=require` as an alias of `verify-full`: the certificate chain *is* verified and the hostname *is* checked. But it says so out loud, a `SECURITY WARNING` on stderr, once per process. In a long-lived server that is one line at boot. In a function it is one line per cold start, in the function log, forever, and a log line that says "warning" about TLS on every cold instance is the kind of thing a reviewer reads as a misconfiguration. Worse, the warning is a notice of a change: in pg 9, `require` adopts libpq's meaning — encrypted, but the server's certificate no longer checked — so a URL that verifies today stops verifying on a dependency bump with no code change. `verify-full` is what is meant, it is what the parser does silently, and the verify task confirmed the `db:deploy` run printed no `sslmode` warning with it. Neon's console appends `channel_binding=require` to the URLs it offers; `pg` neither implements nor rejects the parameter, so it may stay or go, and the task reports it was ignored.

**libpq versus Node's trust store.** The same URL behaved differently in two clients, and the difference is where each looks for root certificates. `psql`, which is libpq, needed `sslrootcert=system` appended to reach the direct endpoint under `verify-full`: libpq's default root file is `~/.postgresql/root.crt`, which does not exist on a fresh machine, and `system` tells it to use the operating system's store instead. `pg` in Node needed nothing, because Node's `tls` ships its own root store and node-postgres hands the connection to it. Neither client was wrong; they have different defaults for the same question, and the pool config needs no `ssl` block precisely because Node's default answers it.

**`pg_stat_ssl` versus `\conninfo`.** On the direct endpoint, `SELECT ssl FROM pg_stat_ssl WHERE pid = pg_backend_pid()` reports `f`. That is not an unencrypted connection: Neon's proxy terminates TLS at its edge and connects to the backend over its own network, so the backend genuinely sees a plaintext connection from the proxy. `\conninfo` in the same `psql` session reports the *client's* side — `TLSv1.3` — which is the fact that matters to the operator. The two views describe two different hops, and reading the first as "TLS is off" would be the wrong lesson.

**The obvious alternative.** `sslmode=require` as the console offers it, or a pinned CA passed as `ssl: { ca }`.

**What goes wrong with the alternative.** `require`: a warning per cold start now and no verification later, §4.3 above. A pinned CA: a certificate file in the tree, or in an environment variable, that has to be rotated when Neon rotates its chain, and a failure mode — every connection refused after a rotation — that looks like an outage and is a stale file. The public root Neon's chain terminates in is already in Node's store; pinning it would replace a maintained trust store with a copy that nobody maintains.

### 4.4 Migrations go to the direct endpoint from a laptop, never from a build

**What.** `DATABASE_URL=<neon-direct> pnpm db:deploy`, typed by an operator, with the URL exported for that command in the session shell. `db:deploy` is `pnpm run db:migrate && pnpm run db:seed`; both go through `scripts/with-env.ts`, which layers `.env.example`, then `.env`, then the real process environment — so the export wins, nothing in `.env` has to change to point one command at the Neon project, and nothing about the project ever lands in a file. `migrate.ts` opens a single `pg.Client`, not the pool — one connection, one operator, one run — and hands it to drizzle's migrator.

**"All pending, in one transaction."** The migrator does not wrap each file separately. Drizzle's pg dialect opens `session.transaction(...)` once and loops every pending file inside it — each file's statements, then its `drizzle.__drizzle_migrations` insert — so a failure anywhere in a run leaves neither DDL nor journal rows behind from *any* file of that run (drizzle-orm 0.45.2, `pg-core/dialect.js`, `migrate()` at line 44, the transaction at line 60). `migrate.ts` used to say "each file in a transaction"; that was the doc fix the tech spec named, and the comment now states the real boundary and the one condition it depends on: no migration here uses `CREATE INDEX CONCURRENTLY`, which cannot run inside a transaction block. The first run against the Neon project printed `migrate: applied 7 migration(s); 7 total`, the second `no pending migrations`.

**Why never from a build.** Three reasons, in `migrate.ts`'s header. Every preview deploy would run DDL on every pull request, against whatever database the preview's environment names — and R5 is the case where that is the production database. The build would depend on a cold compute being awake and would have to hold the database secret, when a build has no database and should have none. And the seed is idempotent but not inert: a fixture that lowers a code's `max_uses` under a live `used_count` trips `promo_codes_used_count_range` (`23514`) and aborts the whole seed transaction — which is a human's decision about a demo that has been used, not a deploy failure for a bot to retry.

**Why the direct endpoint and not the pooled one.** The migrator *would* work through PgBouncer — one transaction, nothing session-bound, no `CONCURRENTLY` — and `migrate.ts` says so. It uses the direct host anyway for three smaller reasons: an operator's single connection has no pooling problem for PgBouncer to solve; the `psql` read-back that follows (`\d`, `SHOW max_connections`) is a plain session on the direct host regardless; and keeping DDL off the endpoint the function shares with fifty instances is one less thing to reason about during a demo.

**The obvious alternative.** A `vercel-build` hook or a CI step that runs `db:migrate` on every deploy, so the schema can never lag the code.

**What goes wrong with the alternative.** The three reasons above, and one more: forgetting is loud. A function that boots against a database one migration behind builds its container fine — `GET /api/health` is `200`, because it opens no connection — and fails on the first statement that needs the missing column or constraint, with the Postgres error naming it. That is a mistake an operator sees on the first `curl` and fixes by running the command; a preview that ran DDL against the wrong database is a mistake nobody sees until the demo is different. `db:deploy` before `vercel --prod` is the ordering, and the runbook says so.

### 4.5 The seed is idempotent but not a reset

**What.** `pnpm db:seed` loads twelve products, four promo codes, fifty keys and two behaviour rows in one transaction, with a different `ON CONFLICT` shape per table because each table holds a different mix of definition and state. It is safe to run against a database that already holds the fixture and live orders on top of it. Run twice against the Neon project: `0 inserted, 12 updated … 4 updated … 50 already present … 2 already present`, with `sum(used_count)` and the unclaimed count unchanged between the runs.

**What it never writes.** `promo_codes.used_count` — the counter I7 guards; the seed's `DO UPDATE` names `kind`, `value`, `currency`, `max_uses` and stops, and its own report line says "never written by this script". `supplier_keys.claimed_by_request_id` and `claimed_at` — `ON CONFLICT (code) DO NOTHING`, so an existing key row is untouchable: a `DO UPDATE` here, even one that only set the definition columns, would be a way for a routine re-seed to resell a key a delivered order is holding. `supplier_behaviour` — `DO NOTHING` again, because the row carries a knob a reviewer may have armed moments ago. And no order, event, delivery, attempt or redemption — the seed does not know those tables exist.

**Why it is not a reset, and why that is the right shape.** "No new rows" is not "nothing changed": the catalogue and the promo definitions are rewritten from the fixtures on every run, which is how a drifted price or limit gets corrected, and the three state columns are what is genuinely untouched. A script that also zeroed counters and released claims would be the seed and the reset in one file, and the one place a routine `pnpm dev:stack` — which runs the seed every time — could silently undo a demo in progress. Slice 3's `POST /api/admin/demo/reset` is the operator's tool for that: one transaction, every order's lock first, the five deletes in FK order, the counters and the claims and the knobs, behind the admin token, answering with what moved. The seed loads; the reset erases; and the one collision left between them — a lowered `max_uses` under a live count — aborts loudly rather than choosing.

**The obvious alternative.** `TRUNCATE … CASCADE` and reload. Simpler, always consistent, and what most seed scripts do.

**What goes wrong with the alternative.** It runs on every `pnpm dev:stack` and on every `db:deploy`, so every developer restart and every schema change would erase the shop's memory — which on the Neon project is the demo the reviewer is looking at, and functional spec §2.1's last criterion is that the orders are still there the next day.

## 5. Findings

### 5.1 One local process at WAN latency starves — the slice's finding

**What was run.** With the one local instance still up against the pooled endpoint, `RACE_BASE_URLS=http://localhost:3000 … RACE_DATABASE_URL=$NEON_DIRECT_URL pnpm race webhooks`. The task line expected it to pass with the single-instance warning printed. It failed, twice out of twice. Then `pnpm race harness` against the same target: one backend pid, `K = 1`, FAIL — as designed for one target.

**The mechanism, in plain words.** The webhook check sends fifty distinct reports of one payment at once. Each `POST /api/webhooks/payment` stores its event in one statement — `INSERT … ON CONFLICT (event_id) DO NOTHING` — and answers `200`; through the pool's one connection at ~30 ms per round trip, all fifty were stored in about two seconds — fine. Each of the fifty then schedules a continuation, and every continuation begins with a transaction: check the connection out, `BEGIN`, the event under `FOR UPDATE SKIP LOCKED`, `SELECT … FOR UPDATE` on the order, the guarded `UPDATE`, `COMMIT`. On Docker at ~5 ms a round trip those fifty transactions drain in well under a second. At ~30 ms they are fifty short transactions queued *in Node* for one connection, one after another — median wait about 10 s, the longest about 18 s. Exactly one of them matches the guarded update, and that one then calls the supplier over HTTP. Locally the supplier stub is a route in the *same process*, and its key claim is a transaction of its own — which now joins the same queue, behind the continuations that have not yet had their turn to discover they lost. The issuance client's deadline is `SUPPLIER_TIMEOUT_MS`, 2 000 ms by default, and it fired first: `issuance: UNKNOWN outcome — the request is outstanding; the same id must be re-asked, never another supplier`. Meanwhile the check's polls of `GET /api/orders/:id` were also queued for that connection, and `connectionTimeoutMillis` — which bounds time spent waiting for a free client as well as the handshake — is 10 s; the polls that waited longer got `500`, and the check reported them.

**Why the guarantees still held.** Two things the database was asked to guarantee, and both did. One key per order, in both runs, read back on the direct endpoint. And the timeout trap — the scenario Phase 3 built the probe for — occurred organically: the supplier's claim committed *after* the shop's deadline, so a key was on the supplier's ledger under a request id the shop had given up waiting on; the ladder re-asked the same supplier with the byte-identical `request_id`, the supplier's `supplier_requests.request_id UNIQUE` row answered with the code it had already issued instead of cutting a second one, and the order settled `delivered` about 11 s later with one delivery. Nothing about that path was exercised by a knob; the latency armed it.

**Why this is architecture §7 and not a pooler defect.** The pooler never refused a connection, never misrouted a statement, never lost a lock; every statement ran on the backend that held its transaction, which is the only thing §4.1 asks of it. The queue was in the shop's process, in its own pool, before any byte reached the pooler. §7's rule says exactly this: within one process a transaction holds the only connection for the whole of `BEGIN … COMMIT` and a second concurrent claim queues in Node before a byte reaches Postgres — a single-instance run measures the connection pool, not the constraint. On Docker that serialisation is invisible because it costs microseconds; at Frankfurt's latency it costs enough to cross the process's own deadlines, and the same shape that made a broken claim look correct in one process now makes a correct one look broken. The harness said the same thing in its own vocabulary: one backend pid, one instance id, FAIL.

**What shape the checks are for.** Two, and the runner's README now says so in a paragraph of its own. Four local instances on Docker Postgres — four processes, four pools, four connections, latency in microseconds — which is `pnpm race`. And the deployed shop, where every request is its own process with its own `max: 1` pool and the supplier stub is a second invocation with a pool of its own, so no continuation ever waits behind another and no claim ever waits behind a continuation. One local instance against a hosted database is neither: it has the deployment's latency and the laptop's process count, and it is the one combination that pays for both.

**What Slice 5 must therefore show.** Against the live address: `K ≥ 2` from the runner's instance-id half, the fifty webhooks answered `200`, the order `delivered` with one key, no `500` on any poll, and a wall-clock that does not carry a 10 s median queue — because there is no queue to carry. If the live run shows the numbers of this section, the reading is that requests are sharing a process (Fluid Compute on, R3), not that Neon is slow.

### 5.2 The cleanup raced the continuation

The check's cleanup ran when the check decided it had failed, which was while the winning continuation was still in flight — waiting on the pool, then re-asking the supplier. The cleanup deleted the order's rows and released the claims it could derive from the order; the continuation then completed and committed a claim and a `supplier_requests` row for an order that no longer existed. One orphan claim and one ledger row per run, cleaned by hand through the same statements. Two things are worth naming. The supplier's tables are separate from the shop's on purpose — no FK from `supplier_requests` to `orders` — so the orphan is the boundary doing its job, not a consistency failure. And the cleanup's correctness assumes the check's work is over when the check says so, which is true in the two supported shapes and false in this one; it is a symptom of §5.1, not a second bug.

### 5.3 One idle `game-shop` connection after everything was closed

After the instance was killed by port and the cleanup's client had ended, `pg_stat_activity` on the direct endpoint still listed one idle connection with `application_name = game-shop`. That is PgBouncer's backend, not the shop's: the pooler keeps server connections open after the client that used them has gone, and it labels each with the last client's startup parameters — which is the same mechanism that makes `application_name` useful through the pooler in the first place. `client.ts`'s `pool.on("error")` comment anticipates the mirror image, the pooler dropping *its* side of an idle connection. Nothing to fix; something to know before reading `pg_stat_activity` as a leak detector on the pooled endpoint.

## 6. Role among the key points

The assignment's subject is a shop whose correctness under concurrency is enforced by the database — unique constraints, row locks, guarded updates — and not by anything a process remembers. Every earlier phase argued that claim by running the code against a Postgres in Docker and reading the rows. Phase 6's sentence turns the argument into evidence a stranger can gather: run the checks against a public address where every request is a separate process, and if they pass, memory could not have been the reason. That sentence needs a Postgres the stranger's fifty processes can reach, holding the schema whose constraints *are* the guarantees. This slice is that Postgres.

Its specific contribution is narrower than "it works on Neon", and better. The same driver, the same `max: 1`, the same `transaction()` and the same statements — audited for the one property a pooler adds, session-lessness — wrote a purchase through the endpoint the function will use, and a `psql` session on the other endpoint read the rows the local database would hold. The seed put the fifty keys and the four codes there with the same script the local baseline assertions depend on, and put them there idempotently, so the reviewer's database and the developer's database are the same fixture. "Correctness lives in Postgres" is now a claim about a Postgres that is not on the author's machine, which is the first time it has been testable from outside — and §5 is that testability already saying something: one process against it is not enough, and the runner knows.

## 7. What a reviewer might challenge

- **Why not Neon's serverless driver — it is what Neon recommends for serverless.** It is what Neon recommends for runtimes that cannot open TCP, and a Vercel Node function can. Adopting it would have left architecture §7's four-process table and `client.ts`'s prepared-statement argument true on a laptop and assumed in production. One driver keeps both measurements about the thing that is actually running. §4.2.
- **Why not `SERIALIZABLE` through a pooler, where you cannot see which backend you are on?** The isolation level is per transaction and the pooler pins a backend per transaction, so `SERIALIZABLE` would work through it — and it would still be the wrong tool. The project's guarantees are constraints and explicit locks that a reader can see in the SQL; `SERIALIZABLE` moves them into a retry-on-conflict loop nobody can audit. Transaction mode changes nothing about that argument, and `READ COMMITTED` stays.
- **A 0.25 CU compute that scales to zero — is that not just slow?** It is the smallest compute Neon offers and it is the right size: the shop's transactions are a handful of indexed statements each, and the fifty-webhook check is fifty short transactions, not a workload. The cost of scale-to-zero is R4's — the first request after idle pays the compute's resume plus the function's cold start — and Slice 4's warm-up and the README's "the first request may take a few seconds" are the mitigation. The number this slice did *not* measure is that resume from inside a function; §9.
- **Why not run migrations in CI, where they cannot be forgotten?** §4.4: preview deploys would run DDL per pull request against whatever the preview's environment names (R5); a build would hold the database secret and depend on a cold compute; and the seed can legitimately refuse — a lowered `max_uses` under a live count — which is a person's decision, not a pipeline's. The migrator is idempotent and additive, so the failure mode of forgetting is loud and fixable by running it, not silent.
- **Why `verify-full` and not a pinned CA — a pin is stricter.** A pin is a copy of a certificate that Neon will rotate on its own schedule, and a rotation turns the pin into an outage that looks like Neon being down. `verify-full` against Node's maintained root store checks the chain and the hostname today and after the rotation. The stricter thing is the one that stays correct without a human remembering it.
- **The one-instance webhook check failed. Is the pooled endpoint too slow for the shop?** No — the same run stored fifty events in about two seconds and settled a purchase in 2.41 s. What failed was one process serialising fifty continuations plus the supplier's claim on one connection at 30 ms a round trip, which is the shape §7 says never to measure with. The deployed shape has no such queue. §5.1.
- **Then why keep `max: 1` if it is what starved?** Because raising it in one process changes the configuration under test — §7's last sentence — and because in the deployed shape there is nothing to raise it *for*: an instance serves one request at a time and issues its statements sequentially. `max: 1` is a correctness constraint derived from the deployment, and the local instance against a WAN database is the one shape where the deployment's constraint meets the laptop's process count.

## 8. Interview questions this answers

**"Walk me through what a pooled endpoint in transaction mode does to your connection."**
PgBouncer lends a real backend for one statement, or for `BEGIN … COMMIT`, and takes it back. Between those spans the connection is a socket to the pooler and the backend is serving someone else. Anything Postgres keeps on a backend between statements — a session `SET`, an advisory lock, a `LISTEN`, a named prepared statement, an open cursor — lands on the wrong backend later. This codebase has none of those: one grep in `client.ts` lists them and its only code hit is a `SET LOCAL` that dies with its transaction. Every lock and guarded update runs inside `transaction()`, which is one checked-out connection for `BEGIN … COMMIT` — exactly the span the pooler pins.

**"Why did you keep `pg` instead of Neon's driver?"**
Because TCP is available in a Vercel Node function, and because the two measurements the design rests on — the four-process `max: 1` table and the unnamed-parse argument — were made with `pg`. One driver keeps them true where it matters.

**"What is wrong with `sslmode=require`?"**
In `pg` today it verifies and warns once per process — once per cold start in a function log. In pg 9 it will encrypt and verify nothing, on a dependency bump with no code change. `verify-full` is what is meant and is the spelling the parser accepts silently.

**"Your `pg_stat_ssl` says `ssl = f`. Are you connecting in plaintext?"**
No. Neon's proxy terminates TLS; the backend sees the proxy, not me. `\conninfo` on the same session shows `TLSv1.3`, which is the client's hop. Two views, two hops.

**"Where do migrations run and why?"**
From an operator's shell, `DATABASE_URL=<neon-direct> pnpm db:deploy`, all pending files in one transaction, never from a build: previews would run DDL per pull request, a build would hold the secret and depend on a cold compute, and the seed can refuse for a reason that needs a person.

**"Is the seed safe to run against the live shop?"**
Yes, and it is not a reset. It rewrites the catalogue and the promo definitions from the fixtures and never writes `used_count`, a key's claim, or a supplier knob; run twice against Neon it inserted nothing and changed no state column. The reset is a separate endpoint behind the admin token.

**"You pointed one local instance at Neon and the webhook check failed. What did you learn?"**
That architecture §7's warning about single-process runs is not only about false passes: at 30 ms a round trip, fifty continuations on one connection queue for ten seconds median, the in-process supplier waits behind them and times out, the polls wait past `connectionTimeoutMillis`. One key per order still — the timeout trap fired organically and the same-id re-ask recovered it. The checks are for four local processes on Docker or for the deployed shop; the README now says so.

**"How would you tell a pooler problem from a process problem on the live run?"**
By K and by the timing. `K ≥ 2` with the fifty webhooks settling in seconds is the deployed shape working. `K = 1`, or a settle time that carries a ten-second queue, is requests sharing a process — Fluid Compute on — not the pooler.

**"What did the second `db:deploy` prove?"**
That the migrator finds nothing to do and the seed changes nothing it is forbidden to change: `no pending migrations`, `0 inserted`, `50 already present`, `sum(used_count)` and the unclaimed count identical before and after.
