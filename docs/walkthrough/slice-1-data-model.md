# Slice 1 — The data model, and why every constraint ships before any code touches it

> Written for the author to read and re-explain from memory. Companion to `context/product/architecture.md` §3 and §3.1.
> Slice 8 consolidates this and the other slice walkthroughs into the phase-level document.

## 1. What is actually in the database

Seven tables. Five belong to the shop, two belong to the simulated supplier. The promo tables (`promo_codes`, `promo_redemptions`) are Phase 5 and are not in this migration.

**The shop's five:**

- **`products`** — the twelve supplied catalogue items. `sku` UNIQUE is the shop's public handle. Prices are `price_minor` — integer kopecks. There is no floating-point column anywhere in this schema.
- **`orders`** — one row per purchase attempt, plus the state machine that carries it: `created → paid → delivering → delivered`, with branches to `payment_failed` and `out_of_stock`. The id is `ord_` + ULID, **generated by the application, not by a sequence**. That is not a style choice: a webhook may quote an order id before the row exists, and a sequence cannot produce an id that hasn't been inserted yet.
- **`payment_events`** — the durable webhook inbox, which is also the work queue. The endpoint's shape is receive → persist → acknowledge → process. `processed_at IS NULL` means "pending work", and that predicate is literally the queue.
- **`issuance_attempts`** — one row per supplier call. The ledger the Phase 3 retry policy reasons over. The distinction it exists to record is `failed` (definite — try the other supplier with a *new* request id) versus `unknown` (a timeout — retry *the same* supplier with *the same* request id, because it may already have issued a code).
- **`deliveries`** — the issued key bound to an order. One row here is the shop's entire definition of "this shopper has been given a key".

**The supplier's two:**

- **`supplier_keys`** — the fifty codes. `claimed_by_request_id` NULL means unclaimed; once set it never changes. There is no "unclaim" — restocking is adding rows.
- **`supplier_requests`** — `request_id → code`. The supplier's own idempotency ledger.

The division is by *who owns the truth*. `orders` and `deliveries` are what the shop knows. `payment_events` is what a payment provider told us — stored verbatim, believed conditionally. `supplier_keys` is what a third party has, which we can only learn about over HTTP.

## 2. Why the supplier tables are separate

**Interview question: "You control both sides of this integration — why make it hard on yourself?"**

The obvious move is to treat `supplier_keys` as the shop's inventory table: 50 rows, `SELECT` one, mark it used, done. One query instead of an HTTP round trip, and transactional with the delivery insert.

Here is what breaks. The entire Phase 3 trap is: *the supplier call times out and we do not know whether a key was issued.* If `supplier_keys` is our own table inside our own transaction, that state is **unreachable**. Either the transaction committed or it didn't; we always know. So the timeout scenario cannot be built, the same-`request_id` retry rule has nothing to protect against, the fallback-to-supplier-B decision becomes trivial, and the "never fall through while an attempt is `unknown`" rule is unmotivated. You would have deleted the hardest requirement in the assignment by accident.

The rule is enforced at the module level: `supplier.ts` is never imported by shop code, the tables are never joined, and the shop's only knowledge of a key is what came back across the HTTP boundary. They share a database purely so `docker compose up` runs the whole demonstration. **If shop code ever imports that file, that is the bug.**

## 3. Why every constraint shipped in migration 0000

**Interview question: "Isn't `client_request_id` dead weight? Nothing sends that header yet."**

A unique index is not "code that runs later". It is a **statement about what rows may exist**, and it is retroactive — it applies the moment it exists, to every writer, including writers that don't exist yet.

Tested rather than asserted. Twenty concurrent sessions, all inserting an order with the same `Idempotency-Key`, against the real `orders` table, with no application code involved:

```sql
INSERT INTO orders (id, client_request_id, sku, amount_minor, currency, status)
VALUES ($1, $2, $3, $4, $5, 'created')
ON CONFLICT (client_request_id) DO NOTHING
RETURNING *;
-- 0 rows => another request won the race; read that order back and return it with 200
```

```
session 1  -> ord_demo_1
session 3  -> ZERO ROWS (read the winner back, return 200)
session 20 -> ZERO ROWS
... 18 more losers ...

 id         | client_request_id | status
------------+-------------------+---------
 ord_demo_1 | idem-demo-key     | created
(1 row)
```

One row. Phase 2's job is not to *build* idempotency — it is to send the header and handle the zero-row case. The guarantee is already standing.

The alternative — adding constraints as the code that needs them arrives — means every later migration adds a constraint to a table **that already has rows in it**, so each one needs a backfill plan and a "what if the existing data violates this" conversation. Worse, it makes correctness look like a feature that was bolted on.

Constraints are named explicitly (`orders_client_request_id_key`, not Drizzle's default), so a Postgres error points straight at the invariant that just refused to be broken.

## 4. The one deliberate absence: no FK on `payment_events.order_id`

**Interview question: "You have a FK on `deliveries.order_id` but not on `payment_events.order_id`. Which one is the mistake?"**

Neither. The asymmetry is the design.

A payment webhook can legitimately arrive before its order row is committed — the client's `POST /api/orders` and the provider's webhook are separate connections in separate processes, with no ordering guarantee between them. A `deliveries` row cannot arrive early, because it can only ever be written by code that has already read and locked the order.

Storing an event for an order that doesn't exist:

```
  event_id   |        order_id        | processed_at
 evt_early_1 | ord_does_not_exist_yet |
(1 row)
```

Stored, `processed_at` NULL, drained later. The same insert a second time — the provider's redelivery:

```
 event_id
----------
(0 rows)
INSERT 0 0
```

Zero rows means "already seen": acknowledge 200 and stop. Winning the insert *is* what "first sight" means; nobody reads first.

The same early write against a table that does have the FK:

```
ERROR:  insert or update on table "deliveries" violates foreign key constraint
        "deliveries_order_id_orders_id_fk"
DETAIL:  Key (order_id)=(ord_does_not_exist_yet) is not present in table "orders".
```

That is what a "helpful" reviewer adding `REFERENCES orders(id)` to `payment_events.order_id` would cause. Trace it: the webhook endpoint raises, returns 500, **the provider retries on 5xx**, and now you have retry storms caused by an event that was merely a few milliseconds early. A normal path converted into a self-inflicted incident, and the assignment's "webhook before order" scenario broken outright.

Both the schema file and the migration carry a boxed DO NOT FIX THIS comment. The FKs on `deliveries` and `issuance_attempts` sit ten lines away so nobody can read the omission as forgetfulness.

## 5. Constraints, not application checks — the 20-session experiment

**Interview question: "Why not just check whether the order was already delivered?"**

The implementation the brief specifically names as the thing candidates get wrong:

```ts
if (!alreadyDelivered) { deliver() }
```

Twenty concurrent Postgres sessions, released simultaneously by a clock barrier, all processing the same `paid` event for order `ord_race`, against a mirror of `deliveries` with the unique constraint removed. Each counts existing deliveries, waits 200ms (the supplier call), and if the count was zero, claims a key and inserts.

```
--- ARM A: 20 concurrent sessions, application check, NO unique constraint ---
 delivery_rows_for_ord_race | distinct_keys_handed_out
                         20 |                       20
 keys_claimed
           20
```

**Twenty keys handed out for one order.** The exact sequence: all twenty run `SELECT count(*) ... WHERE order_id = 'ord_race'` before any of them has inserted. Under READ COMMITTED each sees a snapshot from before the others wrote, so all twenty read zero. All twenty conclude "not delivered yet". All twenty call the supplier. All twenty insert. Every session's check was correct, and the outcome is still catastrophic. No amount of care in writing that `if` fixes it, because the gap between reading and writing is where the other nineteen sessions live. Moving the check inside a transaction doesn't help — READ COMMITTED readers don't block each other, and nothing here is locked.

Same twenty sessions against the shipped table:

```sql
INSERT INTO deliveries (order_id, code, provider, request_id)
VALUES ($1, $2, $3, $4)
ON CONFLICT (order_id) DO NOTHING
RETURNING *;
-- 0 rows => this order already has a delivery; keep the existing one, do NOT issue again
```

```
 delivery_rows_for_ord_race        keys_claimed
                          1                  20
```

One delivery row. One winner, nineteen losers, and **the losers find out by being told zero rows** rather than by asking a question whose answer expires. `ON CONFLICT DO NOTHING` is not the guarantee — the unique index is; the `ON CONFLICT` only keeps the nineteen losers from raising.

But look at the second number — **twenty keys still burned**. That is the honest limit of a constraint on its own, and it is worth saying aloud because it shows you know where each mechanism stops. The unique index guarantees the *shopper* gets one key. It does not stop twenty workers from calling the supplier, because by the time the constraint speaks, the money is already spent.

That is what I4 is for:

```sql
SELECT * FROM orders WHERE id = $1 FOR UPDATE;

UPDATE orders SET status = 'delivering', updated_at = now()
WHERE id = $1 AND status = 'paid'
RETURNING *;
-- 0 rows => someone else already advanced it; this worker does nothing
```

```
 delivery_rows    keys_claimed    final_order_status
             1                1             delivered
```

One delivery, **one key**, nineteen workers that never reached the supplier. The lock serialises the workers; the status guard makes the transition idempotent; the unique index is the backstop that holds even if both were written wrongly. Three layers, each doing one job.

The pool claim, the one place Phase 1 genuinely races — twenty concurrent requests against fifteen remaining keys:

```sql
UPDATE supplier_keys
SET claimed_by_request_id = $1, claimed_at = now()
WHERE code = (
  SELECT code FROM supplier_keys
  WHERE claimed_by_request_id IS NULL
  ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING code;
-- 0 rows => pool exhausted => out_of_stock
```

```
 keys_in_pool | claimed | distinct_claimants | still_unclaimed
           15 |      15 |                 15 |               0
```

Fifteen keys, fifteen *distinct* claimants, five sessions cleanly told `out_of_stock`. Nobody blocked — `SKIP LOCKED` means a session that finds the first candidate locked moves to the next instead of queueing behind it. One statement, so there is no read-then-write window at all.

**A precision a sharp interviewer will probe:** what stops a key going to two requests is *structural* — the row has one `claimed_by_request_id` column, so it can only name one claimant. What `UNIQUE (claimed_by_request_id)` adds is the other direction: one request can never end up holding two keys. That is the constraint that catches a retried claim, and the reason a Phase 3 timeout retry cannot quietly drain the pool.

This is also why isolation stays `READ COMMITTED`. `SERIALIZABLE` would also be correct, but it hides the guarantee inside an invisible retry-on-conflict loop you cannot point at. Explicit constraints and locks are cheaper and **defensible out loud**.

## 6. Where this sits in the assignment

The brief claims a typical tutorial shop will fail the concurrency and recovery checks. It fails them because it stores a `delivered` boolean and guards it with an `if`.

| Scenario | Status after Slice 1 | What Phases 2–3 still add |
|---|---|---|
| **50 parallel webhooks → one key** | Mechanism proven at 20 sessions: one delivery, one key. | The webhook handler, `FOR UPDATE`, and the issuance module. |
| **Replayed `event_id`** | Settled by `event_id` PRIMARY KEY. | The handler treating 0 rows as "acknowledge and stop". |
| **Webhook before its order** | Settled by the *absence* of the FK. | The drain triggers — `waitUntil`, order creation, status poll, admin sweep. |
| **Empty pool → restock → recovery** | Half-won: `out_of_stock` is a real state; the claim returns 0 rows on an empty pool. | The `delivering → out_of_stock` transition, admin list, manual retry. |
| **Concurrent promo redemption** | Not started — Phase 5 tables. | `UPDATE ... WHERE used_count < max_uses RETURNING` and UNIQUE (`promo_id`, `order_id`). |

**The schema decides what is possible, the phases decide what happens.** Three of the five scenarios are already impossible to fail at the storage layer; the remaining work is wiring, not correctness. That is the sentence to lead with if the reviewer asks why the first slice — a page listing twelve products — shipped a migration containing constraints that nothing calls.

One deployment note that makes the argument land harder: on Vercel the API runs as serverless functions, so concurrent requests arrive in **separate processes**. Any correctness leaning on an in-process mutex or a single Node instance would break there. Passing the 50-webhook scenario against the deployed URL is direct evidence the guarantees live in Postgres, not in application memory.
