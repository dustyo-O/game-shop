# Phase 5 · Slice 4 — The shopper enters a code on the order page

> A shopper on an order that is waiting for payment now sees a field above the two payment buttons, types a code, presses Enter, and within one tick of the page's own refresh loop the page shows «LIMIT3 — скидка 322,50 ₽» under «Сумма 967,50 ₽ (было 1290 ₽)» — the field gone, the address bar unchanged, nothing reloaded. Reload by hand, and the same row is there; pay, and «Ключ выдан» arrives with the row still under the amount. What exists after this slice is the storefront's half of the feature: a feature slice with one form and six Russian strings, an order entity that can read a promo off the wire and put a code on an order, a «Промокод» row painted from the order and not from the status, a repaint rule that has learned an order can change without its status moving, and six browser tests written to the technical spec's table — run: six green, and every one shown able to fail.
>
> Three things carry the slice, and each one is about *who is allowed to decide something*. **The page shows a price it never computed.** `967,50 ₽` is `formatPrice(96750)`, and `96750` is the `amount_minor` the server put in the order view; `322,50 ₽` and `1290 ₽` are two more server numbers, `discount_minor` and `list_amount_minor`; there is no subtraction, no percentage and no rounding anywhere in the page, and a `grep` says so. **The form refreshes through the poll instead of painting its own response.** `applyPromo` hands back the repriced order, and the form throws it away and calls `onOrderMayHaveChanged()`, because the content region has one writer and a second one would race it. **The repaint memo compares `promoCode`.** The poll skips repaints of an order that has not changed, and "changed" was, until this slice, *status or key* — a code applied to a `created` order moves neither, and a memo that does not know about the promo would swallow the one read that carries it, silently, with everything green.
>
> Reading the delivered work found two sentences the code has moved past, one piece of context worth having, and one finding the e2e's own RED turned up: the memo's doc comment still calls everything but three fields "fixed at creation" one paragraph before saying the amount moves; R10's reload URL is written as `/order/ord_x?` in five places when the field is `name="code"` and the browser would append `code=…`; the promo form is the app's *second* `<form>`, not its first — the operator's token form from Phase 3 is the precedent, and it keeps the `required` this one refuses; and the technical spec names no inversion for the reload test, while the one nearest to hand — T5's status gate on the row — *passes* that test rather than failing it, because a reloaded order never leaves `created`, so the e2e had to find the inversion that isolates what a reload actually proves. None of the sentences was edited, because an acceptance suite was running against the API and another agent held the e2e file while this was written.

## 2. The words this document uses

- **The order view** — the JSON `GET /api/orders/:id` answers. Since Slice 2 it carries `amount_minor` (the amount to pay, in kopecks, *as the column now holds it*) and `promo`, which is `null` or `{ code, discount_minor, list_amount_minor }`. `POST /api/orders/:id/promo` answers with the *same shape* on success — the order as the shop holds it after the code went on.
- **The content region** — `.order__content`, the one `div` the order page owns. Everything under the «Заказ» heading is its children, and it is replaced wholesale, never patched.
- **The poll** — `pages/order/model/poll.ts`: read the order, wait a second, read again, until the order is terminal. The next read is chained off the *end* of the previous one, so there is never more than one read in flight.
- **In flight** — a request that has been sent and not yet answered. The poll allows exactly one; a `POST` from the form is a second request on the wire, but not a second *read*.
- **`refreshNow`** — the poll's "read now rather than after the interval". If a read is in flight it is *remembered* and run the moment that read lands; it never starts a second concurrent one. This is the property §4.2 rests on.
- **The memo** — `rendered: RenderedOrder | null` in `order-page.ts`, and the comparison at the top of `showOrder`: if the last painted order has the same `status`, the same `code` and the same `promoCode` as the one just read, return without touching the region.
- **One writer** — `showOrder` is the only function that calls `content.replaceChildren` with an order in hand. The form, the payment controls and the recovery notice hand it elements; they do not place them.
- **A refusal, on the page** — one of the typed errors `applyPromo` throws for a non-2xx answer: `OrderNotFoundError` (404), `PromoCodeUnknownError` (422), `PromoCodeExhaustedError` (409 `exhausted`), `PromoNotApplicableError(reason)` (any other 409). Anything else — a 500, a `TypeError` from `fetch`, a 200 whose body is not an order — is not a refusal but a failure, and gets the generic sentence.
- **The promo row** — `<dt>Промокод</dt><dd data-promo-code="LIMIT3" data-discount-minor="32250">LIMIT3 — скидка 322,50 ₽</dd>`. One `dd`, because it is one fact.
- **The list-amount span** — `<span class="order-details__list-amount" data-list-amount-minor="129000">(было 1290 ₽)</span>`, appended inside the «Сумма» `dd` after the amount and a space.
- **Inert by construction** — Phase 4's term: a control that does nothing because the markup gives it nothing to do (`<button type="button">` with no handler, an `<input>` with no `<form>` around it), as opposed to *inert by cancellation* — a control whose default action a listener suppresses. The storefront is the first kind throughout; §3.2 is about why the promo form is neither.
- **Kopecks** — every amount on the wire and in `Order` is an integer of minor units, typed `MinorUnits` from `@game-shop/contracts` so `96750` cannot be mistaken for roubles. `formatPrice` is the one place it becomes «967,50 ₽», at the moment of display.

## 3. One code, from the field to the row

The smoke test run against `pnpm dev` earlier today, followed line by line through the page. The order is `ord_01M2GFX0M02G4QCVW4AAJR3S0Q`, a `created` order for `KEY-CS2-PRIME` at `129000` kopecks.

**The first paint.** The page is built synchronously with «Загрузка заказа…» in the region, and the poll's first read lands a moment later: `fetchOrder` → `toOrder` → `showOrder`. The memo is `null`, so it paints. `renderOrderDetails(order)` builds the `<dl>` — Товар, Сумма `1290 ₽`, Статус «Ожидает оплаты», Номер заказа — with no promo row, because `order.promo` is `null`. `renderOrderRecoveryNotice(order)` returns `null` for a `created` order. `promo.render(order)` returns the form, because the status is `created` and `promo` is `null`. `payment.render(order)` returns the two buttons. `replaceChildren` places the four in that order, with the `null` filtered out: details, form, buttons. The form is above the buttons because it is *earlier in the array*, and that is the whole of functional spec §2.2's first criterion.

**What the page sends.** The shopper types ` limit3 ` — spaces and lower case — and presses Enter. The browser's implicit submission finds the form's one `type="submit"` button and fires `submit`; the handler's first line is `event.preventDefault()`, and its second starts `send`. `send` trims the value to `limit3` and finds it non-empty, so it removes any previous error line, sets `input.readOnly = true` and `button.disabled = true`, and calls `applyPromo(orderId, "limit3")`. That is `postJson("/api/orders/ord_…/promo", { code: "limit3" })`, and the request body is exactly `{"code":"limit3"}`. Trimmed, not upper-cased — the normalisation is the shop's, and the code the shop stores comes back on the order. There is no amount in the body, and no field of the request type that could hold one.

**What comes back.** The API runs Slice 2's transaction and answers `200` with the order view, read after `COMMIT`: `amount_minor: 96750`, `promo: { code: "LIMIT3", discount_minor: 32250, list_amount_minor: 129000 }`, `status: "created"`, `code: null`. `toOrder` parses it — `readMinor` brands `96750`; `readPromo` checks `code` is a non-empty string and brands the two figures — and the parse succeeding is the success check: a `200` whose body is not an order would have thrown here. The parsed `Order` is then *discarded*. The form does not read `amountMinor` off it, does not build a row, does not touch the page. It calls `options.onOrderMayHaveChanged()`, which is `poll.refreshNow()`, and leaves itself busy.

**The refresh.** Two cases, and both end the same way. If no read is in flight, `refreshNow` cancels the pending wait and reads now. If one *is* in flight — the poll reads once a second, so this is common — the refresh is remembered, the in-flight read lands first, and the refresh runs the instant it has. An in-flight read that left the browser before the transaction committed comes back with `promo: null`; `showOrder` compares it to the memo — `created === created`, `null === null`, `null === null` — and returns without painting. Then the refresh reads the committed view, `showOrder` finds `promoCode` is `"LIMIT3"` where the memo has `null`, and paints: `renderOrderDetails` now builds Сумма as `967,50 ₽ ` followed by the span `(было 1290 ₽)`, then the row `LIMIT3 — скидка 322,50 ₽`, then Статус, then Номер; `promo.render(order)` returns `null` because `order.promo` is set; `payment.render(order)` returns fresh buttons. One `replaceChildren`: the form is gone, the row is there, the amount has changed. If instead the in-flight read left *after* the commit, it carries the promo itself, paints the row, and the remembered refresh reads the same view and is suppressed by the memo. Either way: **exactly one repaint, whichever read carries the news first.**

The page's URL is what it was, and a `window` global set before the submit is still there afterwards — no navigation happened. That is what `docs/screenshots/005-slice4-task2-promo-applied.png` shows: «Сумма 967,50 ₽ (было 1290 ₽)», «Промокод LIMIT3 — скидка 322,50 ₽», «Статус Ожидает оплаты», the order id, and the two payment buttons with no field above them.

**The three sentences.** `nope` on a fresh order: the API answers `422`, `applyPromo` throws `PromoCodeUnknownError("nope")`, `messageFor` returns «Такого промокода нет», `showMessage` appends `<p class="promo-form__error" role="alert">` inside the form, and `setBusy(false)` makes the field writable again with `nope` still in it and focus where it was. An exhausted code: `409 { reason: "exhausted" }` → `PromoCodeExhaustedError` → «Промокод больше не действует», the same way. A shop that did not answer, or answered `500`, or answered `200` with something that is not an order: «Не удалось применить промокод. Проверьте соединение и попробуйте ещё раз.» — the one sentence that invites a retry, because it is the one case where a retry is right. All three live in one place, the `text` table at the top of `promo-form.ts`, beside `placeholder: "Промокод"`, `apply: "Применить"` and `notFound` — the same «Заказ не найден. Проверьте адрес страницы.» every other feature on the page uses for a `404`. The Russian-labels unit test reads that table out of the source file and asserts six entries, every one Cyrillic, the three refusals distinct from one another, `notFound` identical to the page's.

And the fourth outcome has no sentence: `PromoNotApplicableError` — `not_awaiting_payment` or `another_code_applied` — means the order moved under this tab, paid or given a code somewhere else, and the form was drawn from a view that is no longer true. The truthful response is not a sentence about the code; it is `onOrderMayHaveChanged()`, after which the page paints what is actually there.

**An empty field** — empty, or a row of spaces — trims to `""` and `send` returns before it touches anything: no request, no message, no busy state. Functional spec §2.2's fifth criterion, done in the handler rather than by the browser, for the reason the next section gives.

### 3.1 Why the input has no `required`

The browser's own answer to an empty required field is a validation bubble — «Please fill out this field» — drawn by the browser, in the browser's language, in a style the page does not control. Spec 001 §2.8 says every text a shopper reads is Russian, and functional spec 005 §2.7 restates it for this feature by name: the field, the button, the three messages. A `required` attribute would put the one English sentence on the order page, and it would be the sentence a shopper meets first. So the attribute is absent, the handler trims and checks, and an empty submit is silent by design — the spec's *"the field simply stays as it is"* is exactly what a handler that returns early does. The Russian-labels test has a negative case for it: it reads the source and asserts the input's attribute list carries no `required`, so the attribute cannot be added back as a well-meant "improvement" without a test saying why not.

The operator's token form from Phase 3 (`features/present-admin-token`) *does* use `required`, and its header says why: it "lets the browser refuse an empty submit without this file having to word a message for it". Spec 001 §2.8's last line extends the Russian rule to the operator's view, so that is a Phase 3 inconsistency this slice did not create and did not touch; it is in §8 as something a reviewer will notice.

### 3.2 Why a real `<form>`, when the storefront has none

Phase 4 built the storefront with zero `<a>` and zero `<form>` elements, asserted in a browser by `layout.spec.ts`, and its walkthrough argues the rule: a *decorative* control wrapped in a `<form>` whose only listener cancels the submit is a control pretending to be wired, and it holds only as long as the listener does — lose it, and Enter in the search field navigates to `/?q=…`. With no `<form>`, Enter in a bare input is a keystroke; there is no default action to lose. The search field and «Ввести промокод» on the storefront are decorative, so they got no form.

This field is the opposite case, and the rule's own reasoning says so. It is *wired*: the `submit` handler is where the work happens, and `preventDefault()` is a line inside it rather than the point of it. The `<form>` is what gives Enter a meaning — implicit submission is the browser's, not this file's; a bare `<input>` with a keydown listener for Enter would be re-implementing it, worse — and what gives the button a `type="submit"` a screen reader announces as one. Losing the handler here would not leave a control quietly pretending to work; it would leave one that visibly does not — the browser would `GET` the form and reload the page (R10), and the e2e's `window` marker exists to catch precisely that. `layout.spec.ts`'s zero-`<form>` assertion runs on `/` only, and this form is on `/order/:id`.

Two details keep the form from reaching anything it should not. The payment buttons are `type="button"`, and they are *siblings* of the form in the content region, never children of it — `order-page.ts` composes four separate nodes — so implicit submission finds the form's own submit button and nothing else. And the promo form is not the app's first `<form>`: the operator's token form is one too, for the same reason (it does something), and its header makes the same point about `preventDefault` being load-bearing — there, because a `GET` submission would put a credential in the URL.

### 3.3 `readOnly`, not `disabled`, on the field

The shopper who pressed Enter has focus in the field. Setting `disabled` on a focused element drops focus to `body`: the focus ring vanishes, a screen reader loses its place, and when the request fails and the field comes back the shopper is nowhere. `readOnly` freezes the value for the length of the request and keeps focus where it was, so a failure lands its sentence under a field the shopper is still in. The button is `disabled` because that is what it should be — a disabled button dispatches no click, so a second Enter during an open request sends nothing. That is a guarantee about this tab and this form; the limit itself is held by one conditional `UPDATE` in the database that has never heard of the button.

## 4. The three decisions the task names

Each in the same shape: what was built, the more obvious alternative, and what goes wrong without the decision.

### 4.1 The page shows a price it never computed

**What.** Three numbers appear on the page after a code is applied, and every one is a server value passed through `formatPrice` and nothing else. «967,50 ₽» is `formatPrice(order.amountMinor)`, and `amountMinor` is the wire's `amount_minor` — `orders.amount_minor` as Slice 2's `applyDiscount` wrote it, the column the payment simulator will read when the shopper pays. «322,50 ₽» is `formatPrice(order.promo.discountMinor)`, the ledger's `discount_minor`. «1290 ₽» is `formatPrice(order.promo.listAmountMinor)`, the ledger's `list_amount_minor`. `formatPrice` divides kopecks by 100 and spells the result with a Russian comma; it is arithmetic of *units*, not of *price*, and it is the same function the catalogue has used since Phase 1.

The page does not subtract. `discountMinor` is on the wire as its own field rather than derived on the page as `listAmountMinor − amountMinor`, and `order.ts`'s comment on the interface says why: *a derived figure would be the first number in this storefront that the server did not decide*. `order-details.ts`'s `renderAmountValue` says the same from the other side — *this function subtracts nothing, and it must not: the page is the one place in the storefront that never decides a price*. A `grep` across `order-details.ts`, `promo-form.ts` and `order-page.ts` for any of the three amount fields adjacent to `+`, `−`, `×` or `/` finds nothing. And the request the page sends is `{ code }` — Slice 2's parser reads that key and no other, and the type on the API side is *a code and nothing else*.

**The obvious alternative.** Compute it on the page. The page already has the list price; a `percent` code with `value: 25` is one multiplication away from the discounted total, and the page could show `967,50 ₽` the instant the shopper presses Enter, before any request, then send `{ code }` — or `{ code, amount }` — for the server to record. Or a smaller version: keep the server's `amount_minor` but derive the discount on the page from the two figures it already has.

**What goes wrong with the alternative.** Four things, in increasing order of how quietly they happen.

*The page would have to know the definition.* To multiply, the page needs `kind` and `value`, and Slice 2's wire deliberately does not carry them — `promo` is `code`, `discount_minor`, `list_amount_minor`, and *no `kind`, no `value`, no percentage: the page is handed the applied kopecks and nothing it could recompute a price from*. Giving the page the definition is the first step toward the page sending a number, and the whole argument of functional spec §2.3 is that it never does. With nothing to compute from, there is nothing to tamper with, and the page and `curl` are the same client.

*Two calculators drift.* The server's rule is fixed by Slice 1's unit file: multiply the integer kopecks first, divide by 100 last, round half up — so 25 % of 9 999 kopecks is 2 500. A page working in roubles from a formatted string starts from a float and a rule of its own; the two agree on every seeded amount for a 1 290 ₽ order and disagree on the case the unit file pinned to tell rounding modes apart. The number the shopper agreed to and the number on the webhook would come from different code, and the ledger's `CHECK (discount_minor <= list_amount_minor)` and the identity `list = amount + discount` are enforced on the server's numbers, not the page's. A page that shows one figure while the column holds another is the drift functional spec §2.3's last criterion forbids, arrived at from the front.

*The clamp.* `GG500` is 500 ₽ off. On a 300 ₽ order the server's `computeDiscount` records a discount of `30000` and an amount to pay of `0`. A page subtracting `50000` from `30000` shows «−200 ₽», or must re-implement `Math.min` — a second copy of `computeDiscount`, in a second language, to be kept in step forever.

*Optimistic paint lies for the length of a refusal.* A page that paints `967,50 ₽` on Enter and then hears `409 exhausted` has to paint `1290 ₽` back, and for the round trip in between it showed a shopper a price they will not get. Under the race Slice 3 proves, seventeen of twenty shoppers would see the discount appear and vanish. The shop's answer is the only answer, so the page waits for it.

The derived-discount version fails on the last two alone — the clamp makes `list − amount` the whole list price rather than the code's face value, which is correct, but only because the *server* clamped; a page that derived it would be reproducing a server decision it cannot see, and the day the identity stops being a subtraction the page is wrong.

### 4.2 The form refreshes through the poll instead of painting its own response

**What.** On success, `send` calls `options.onOrderMayHaveChanged()` — which the page wires to `poll.refreshNow()` — and does not use the `Order` that `applyPromo` returned. The poll's next read goes through `showOrder`, the memo notices `promoCode` has changed, and one `replaceChildren` paints the row, the new «Сумма» and no form. The form is left in its busy state until that replacement throws it away; it never re-enables itself after a success. `refreshNow` is the same callback the payment controls use, and it has the property §2 names: if a read is in flight, the refresh is remembered and runs the instant that read lands, never concurrently with it.

**The obvious alternative.** Paint from the response. `applyPromo` returns the repriced order — the form has `order.amountMinor` and `order.promo` in hand the moment the `200` lands — so call `renderOrderDetails(order)` and swap it in, hide the form, and skip a round trip. It is faster by one read, and it is how most single-page apps do it.

**What goes wrong with the alternative.** The content region would have two writers, and the page already has a loop reading the order once a second.

*Two `Order` snapshots race.* The poll's read that was in flight when the `POST` succeeded may have left the browser before the transaction committed. It comes back with `promo: null` a few milliseconds after the form painted the row. Now either `showOrder`'s memo has been told about the form's paint — in which case the form has to reach into the page's private state — or it has not, and the memo compares the stale read to what *it* last painted, finds no change, and does nothing, leaving the page correct by luck; or worse, a later read carrying the promo compares against the memo's stale `promoCode: null`, sees a change, and repaints the region a second time. A shopper would see the row appear, and then flash as the same row is rebuilt under them. The one-writer rule with `refreshNow`'s no-overlap guarantee turns all of that into a fixed sequence: stale read lands, suppressed; refresh reads the committed view, painted once. §3 walked through both orderings, and both produce exactly one repaint.

*The `PromoNotApplicableError` case has no response to paint.* When the answer is `409 not_awaiting_payment` or `409 another_code_applied`, the form has nothing in hand but a reason string, and the only right move is *re-read the order and let the page decide what to show* — the paid status, or the other code's row, and no form. If the success path painted from its response and the refusal path refreshed through the poll, the feature would have two ways of updating the screen for two outcomes of one request. One path for every outcome that may have changed the order is simpler and is what shipped: success and not-applicable both call `onOrderMayHaveChanged()`; only the refusals that leave the order untouched — unknown, exhausted, not found, failed — show a sentence and leave the page alone.

*Who removes the form.* The form is removed by the poll's repaint, not by the form itself, and this is the consequence of the rule rather than a separate decision. `render(order)` returns `null` once `order.promo` is set, so the next paint simply does not include it. If the form hid itself on success and then re-enabled its controls "to be safe", there would be a live field on screen for the length of one read whose next Enter sends a second code to an order that already has one — a `409 another_code_applied` the shopper would have been invited to cause. Left busy and then discarded, the field cannot be used again by construction.

The returned `Order` still matters: parsing it is how the form knows the `200` meant what it said. An unparseable body is a failure with the generic sentence, not a silent success followed by a refresh that shows nothing.

### 4.3 What the repaint memo's `promoCode` protects against

**What.** `RenderedOrder` in `order-page.ts` is `{ status, code, promoCode }`, and `showOrder` begins by comparing the order it was handed to the last one it painted: if all three are equal, it returns without touching the region. `promoCode` is `order.promo?.code ?? null` — the one field of the promo that identifies it. The amount is deliberately *not* a fourth field: `orders.amount_minor` changes after creation only when a promo is applied, so one witness is enough and a second could only ever agree with the first.

**Why there is a memo at all.** A `created` order is read once a second while the shopper decides. Without the memo, every read would replace the content region — wiping the disabled state of a button whose request is still open, the Russian sentence under it, the focus ring of anyone navigating by keyboard, and, since this slice, the half-typed code in the promo field — once a second, forever. So the memo is what lets a shopper type `limi` and have it still be there when the next read lands. It is *also*, through `promoCode`, what notices the moment the code has been applied. Two faces of one comparison: it must suppress the reads that carry nothing new and admit the one that does.

**The obvious alternative** is not an alternative anyone would choose; it is the field being forgotten. `RenderedOrder { status, code }` was correct for four phases, and a reviewer adding the promo would naturally touch the entity, the feature and the page's `replaceChildren` and consider the page done. Nothing fails to compile. Nothing logs. The form works, the request works, the server works.

**What goes wrong.** The technical spec's §2.4 names the sequence and the doc comment on `RenderedOrder` repeats it, because it is the one failure in this slice that produces no evidence of itself. The `POST` succeeds; the refresh reads the order back with `promo` set; `showOrder` compares `created === created` and `null === null` and returns early. The form stays disabled — it was left busy on purpose, waiting for a repaint that will now never come. The amount stays at the list price. No «Промокод» row appears. A second Enter does nothing, because the button is disabled. The shopper who applied a code sees *nothing happen* — no error, no change, a button that stopped responding — until something *else* moves the status: they pay, the read after the webhook carries `paid`, the memo admits it, and the row and the discounted amount appear alongside «Оплачен, готовим ключ», a minute after they were earned. Or they reload, at which point `mountApp` builds the page from nothing, the memo starts `null`, and everything is right — which is why a manual check that reloads between "apply" and "look" proves nothing. The server was correct throughout, the webhook carried `96750`, and every API test stayed green.

That is why the e2e's T1 is the guard and its planned RED is exactly this field. T1 applies the code by Enter and asserts the row *appears* — `toHaveText("LIMIT3 — скидка 322,50 ₽")` on `.order-details__value--promo` — without reloading, and then asserts the URL is unchanged **and** a `window` global set before the submit is still present. The two halves are two different bugs: the marker (R10) proves the row did not appear *because of* an accidental reload; the row's presence proves the memo admitted the read. Drop `promoCode` from `RenderedOrder`, from the object literal `showOrder` builds and from the comparison, and T1's `toHaveText` times out with the row absent — and that is what happened. The header of `promo.spec.ts` records the run: `Expected: "LIMIT3 — скидка 322,50 ₽"` / `Error: element(s) not found`, on `promoRowSelector`, after the full 10 000 ms. The field restored, six green. A test that asks for the row *by name* is the only kind that can see this failure; a test that checks the request succeeded, or reads the amount back from the API, sees a working system.

## 5. `HttpError.body` and the typed refusals

The transport and the entity divide the work of a refusal along the line that was already there for a success. `getJson` and `postJson` return `unknown` — the header of `http.ts` has said since Phase 1 that a generic `getJson<T>()` is *a type assertion wearing a nicer hat* — and the slice that knows the endpoint narrows. This slice applies the same rule to the *failed* response. `HttpError` gains `readonly body: unknown`, filled by `readBody(response)`, and `readBody` is total: it tries `response.json()` and answers `null` on any rejection — a body that is not JSON, an empty body, a stream aborted mid-read — with a bare `catch` that binds nothing because there is no branch in which it should do anything else. `new HttpError` occurs at two sites, both in `http.ts`; four consumer files branch on `instanceof HttpError` and `.status`; one reads `.body`, and it is `applyPromo`.

Why `readBody` must never throw is R11, and it is not a hypothetical. Every failed read of the order page's poll passes through `getJson`. If a non-JSON `404` — a proxy's HTML page, say — made `readBody` throw, the `HttpError` would never be constructed; `fetchOrder`'s `instanceof HttpError && error.status === 404` would be skipped; the page would fall through to the generic path; and «Заказ не найден. Проверьте адрес страницы.» would become «Не удалось загрузить заказ…» — a final answer misreported as a temporary one. The same for the payment simulator's `404`/`502`, the admin list's `401`/`503`, the operator's retry. One exception leaking from one function would change the class of every consumer's refusals at once. The existing 404 acceptance test and the unit case *«409 with a non-JSON body → PromoNotApplicableError('unknown') — readBody never throws (R11)»* are the two guards from the two sides.

The narrowing lives in `order-api.ts`, in `readReason(body)`: an object with a non-empty string `reason` yields it, anything else yields `null`, and it does not throw — a refusal with an unreadable body is still a refusal, and the status is the fact that matters first. `applyPromo` maps in a fixed order: `404` → `OrderNotFoundError`, the same class `fetchOrder` throws because *there is no order with this id* is one fact whichever endpoint reports it; `422` → `PromoCodeUnknownError(code)`; `409` → read the reason, `"exhausted"` → `PromoCodeExhaustedError`, anything else including `null` → `PromoNotApplicableError(reason ?? "unknown")`; and any other status is rethrown as it came, because a `500` is not a promo verdict. The `409` is classified as *some* promo refusal before its reason is read, so a `409` whose body was lost in transit cannot fall through to the generic sentence — which invites a retry of something the server has already refused.

Which of the four gets a sentence, and why, is `messageFor` in the feature:

| Error | Status | The shopper reads | Why |
| --- | --- | --- | --- |
| `PromoCodeUnknownError` | 422 | «Такого промокода нет» | The shopper can act: check the spelling. The field stays editable with their text in it. |
| `PromoCodeExhaustedError` | 409 `exhausted` | «Промокод больше не действует» | The code exists and this order could take it; its uses are spent. Trying again fails identically, and the sentence says so. This is the fifth scenario's refusal with a face on it. |
| `OrderNotFoundError` | 404 | «Заказ не найден. Проверьте адрес страницы.» | The page's own sentence for the same situation. |
| `PromoNotApplicableError` | 409, any other reason | *nothing* — `onOrderMayHaveChanged()` | The order moved under this tab. A sentence about the code answers the wrong question; the re-read paints the truth. |
| anything else | — | «Не удалось применить промокод. Проверьте соединение и попробуйте ещё раз.» | The shop did not answer, or answered nonsense. A retry is right. |

`PromoCodeExhaustedError` is its own class rather than a reason on `PromoNotApplicableError` for a reason the entity's comment gives: it is *the refusal spec 005 exists to prove*, and a check that could only say "the second order got a generic conflict" would prove less than one that says the second order was told the code is spent.

## 8. What a reviewer might challenge

- **A `<form>`, on a codebase whose front page has none.** The storefront's rule is about *decorative* controls: a form whose only listener cancels is a control pretending to be wired. This control does something, and the `<form>` is what makes Enter mean «Применить» without re-implementing implicit submission by hand. The buttons below it are `type="button"` siblings, never children. The precedent is the operator's token form, which is a `<form>` for the same reason. §3.2.
- **A button and an input with a click handler would be simpler.** It would lose Enter, or re-implement it with a `keydown` listener that has to know about IME composition, `Enter` versus `NumpadEnter`, and a screen reader's announcement of a submit control. The browser already does all of that for a `<form>`.
- **No optimistic UI.** The page could show `967,50 ₽` on Enter and correct itself on a refusal. It does not, because the shop's price is the only price, seventeen of twenty shoppers in the race would see a discount appear and vanish, and the page would need the definition to compute from — which is the first step toward the page sending a number. §4.1.
- **No "remove code" or "change code".** Functional spec §2.2: one code per order, and it cannot be removed or replaced. A use is spent at apply time (§2.4's last criterion — an abandoned order does not return a use), so "remove" would have to un-spend a use, which is a second transaction on the hot row and a reservation semantics the brief did not ask for. Once applied, the entity's row stands where the field was. §4.2's last paragraph is why the field cannot even be re-used by accident.
- **The storefront's «Ввести промокод» is still inert.** It belongs to the Steam top-up block, which is not a purchase — functional spec §2.2 says so outright. Wiring it would mean inventing what a Steam top-up promo does; `inert-controls.spec.ts`'s test for it is unchanged and is part of the verify task's checklist.
- **`readOnly` on the field rather than `disabled`.** `disabled` on a focused element drops focus to `body`; `readOnly` keeps the shopper in the field so a failure's sentence lands where they are. The button *is* `disabled`, because a disabled button dispatching no click is the guarantee wanted there. §3.3.
- **`applyPromo` in the entity, not the feature.** It parses its response with the entity's private `toOrder`, and the entity's `api` segment is documented as holding every request that reads or writes the order. The feature owns what a shopper's press *does* with the request — the busy state, the four sentences, the refresh — and imports the function from the entity's index. A feature reaching for `toOrder` directly would be a feature reaching past a public API.
- **The functional spec's example wording.** §2.2's second criterion gives «Промокод LIMIT3: −322,50 ₽», «Сумма: 967,50 ₽» *as an example*; the technical spec's §2.4 table fixes what shipped — «LIMIT3 — скидка 322,50 ₽» and «967,50 ₽ (было 1290 ₽)». The shipped form carries the same three facts plus the list price the spec's own third criterion asks for. Not a discrepancy, but a reviewer comparing the two documents will ask.
- **The operator's form keeps `required`.** Spec 001 §2.8's last line extends the Russian rule to the operator's view, and the token form's browser bubble would be English. This slice refused `required` for the shopper's field and did not touch Phase 3's; it is an inconsistency worth a line in whichever phase next opens that file.
- **The amount is not in the memo.** It changes only when the promo does, and the memo compares the promo's code. If a future phase gives `orders.amount_minor` a second post-creation writer, the memo needs a fourth field that day; the doc comment records why there is not one now.

## 9. Interview questions this answers

**"Where does the page get `967,50 ₽` from?"**
From the server, and from nowhere else. The order view carries `amount_minor: 96750`, and the page runs it through `formatPrice`, which divides by 100 and spells the comma. The discount and the list price are two more server fields, `discount_minor` and `list_amount_minor`, formatted the same way. The page does not subtract, multiply or round anything — a `grep` for an amount field beside an operator finds nothing — and the wire deliberately carries no `kind` or `value` it could compute from. The request it sends is `{ code }`. So the number on screen is the number in `orders.amount_minor`, which is the number the payment simulator reads when the shopper pays, and there is one calculator in the system.

**"Why not compute the discount on the page? It's one multiplication."**
Because then there are two calculators, and they will disagree on the first input that separates them — the server rounds integer kopecks half-up, a page working in roubles from a float will not always; a fixed-sum code larger than the price needs the server's clamp reproduced or the page shows a negative amount; and to multiply at all the page needs the code's definition, which is the first step toward a page that sends a number. The functional spec's §1 puts the cost in one line: a shop that lets the page say the price sells a 3 490 ₽ key for 1 ₽ to anyone who edits a request. The page shows the shop's figure and has nothing to edit.

**"The form gets the repriced order back from the server. Why doesn't it just show it?"**
Because the page already has a loop reading the order once a second, and the content region has one writer — `showOrder`, fed by that loop, with a memo that skips reads that changed nothing. A second writer means two snapshots of the order racing for the same region: a read that left before the transaction committed lands after the form's paint with `promo: null`, and either the form has to reach into the page's memo or the next read that *does* carry the promo repaints a row that is already there. So the form discards the response and calls `onOrderMayHaveChanged()`, which is `poll.refreshNow()`; that queues behind an in-flight read rather than overlapping it, the stale read lands first and is suppressed, and the refresh paints the row, the new amount and no form in one replacement. The response still matters — parsing it is how the form knows the `200` meant what it said.

**"What happens if you forget `promoCode` in the memo?"**
Nothing you can see, which is the problem. The `POST` succeeds, the refresh reads the promo back, the memo compares `created === created` and `null === null` and returns early. The form stays disabled — it was left busy waiting for a repaint — the amount stays at the list price, no row appears, and the shopper who applied a code sees nothing happen with no error anywhere. It stays that way until the status moves — they pay, and the row appears next to «Оплачен» — or they reload, at which point everything is right, so a manual check that reloads proves nothing. The server was correct the whole time and every API test is green. The only test that can see it is one that asks for the row by name without reloading, and that is the e2e's first test; dropping the field is its planned RED.

**"Why a `<form>`? The storefront was built with none, on purpose."**
The storefront's rule is about decorative controls: a `<form>` whose only listener cancels the submit is a control pretending to be wired, and it holds only as long as the listener does. This field is wired — the handler is where the work happens and `preventDefault` is one line inside it — and the `<form>` is what makes Enter mean «Применить» without re-implementing implicit submission. The payment buttons are `type="button"` siblings, so Enter cannot reach them. The operator's token form is the precedent. And if the `preventDefault` were ever lost the failure would be visible — a reload — which is what the e2e's `window` marker catches.

**"Why is there no `required` on the input?"**
Because the browser's bubble for it is «Please fill out this field», in the browser's language, and spec 001 §2.8 says every text a shopper reads is Russian. The handler trims and returns early on empty, so an empty submit sends nothing and says nothing — which is exactly what the functional spec asks for. A unit test reads the source and asserts the attribute is absent, so it cannot come back as a well-meant improvement.

**"What does the page do with a `409`?"**
Reads the reason. `exhausted` is its own error class and its own sentence — «Промокод больше не действует» — because it is the refusal this phase exists to prove, and a shopper can understand it without knowing anything about the order. Every other `409` — `not_awaiting_payment`, `another_code_applied`, or a `409` whose body was unreadable — is `PromoNotApplicableError`, and it gets *no* sentence: both reasons mean the order moved under this tab, so the form asks the poll to re-read, and the page paints what is actually there. A `409` is classified as a promo refusal before its reason is read, so a lost body can never fall through to the generic sentence that invites a retry.

**"Why is `HttpError.body` `unknown`, and why does `readBody` swallow everything?"**
`unknown` for the same reason `getJson` returns `unknown`: the transport does not know which endpoint answered, and a typed body there would be a type assertion nothing checked; the entity that knows `{ reason }` is the shape narrows it with `readReason`. `readBody` never throws because every failed read of the order page's poll passes through it, and one exception leaking from it would skip the `instanceof HttpError` in four consumer files at once — a non-JSON `404` would turn «Заказ не найден» into «Не удалось загрузить заказ». The unit case with an HTML `409` body is that guard from the promo side: `readBody` yields `null`, `readReason` yields `null`, and the caller still gets a typed refusal.

**"Which part of the assignment's sentence is this slice?"**
«Скидку считает сервер», from the page's side. Slice 2 showed the server's arithmetic has no parameter a request could reach; this slice shows the page has no arithmetic a shopper could see or edit. The sentence is only true when it holds at both ends. And the limit's half gets a human face here: the reviewer's race shows `17 × 409 exhausted`; a shopper on the fourth order reads «Промокод больше не действует».

## 11. The two sentences

The standing requirement asks that each slice's question be answerable unaided, in two sentences, before any code is opened. For this slice — the price the page never computed, the refresh through the poll, and what `promoCode` protects:

> The page sends one string — `{ code }` — and every number it shows afterwards, `967,50 ₽`, `322,50 ₽` and `(было 1290 ₽)`, is formatted from kopecks the server returned in the order view, so the figure on screen is the figure the webhook will carry and there is no arithmetic on the page for a shopper to edit or for rounding to drift in. The form does not paint the response it gets back; it asks the poll to re-read the order, so the one function that writes the content region paints the row, the new amount and the form's disappearance in one replacement — which is why the repaint memo must compare `promoCode`: without it, a `created` order that gained a code looks unchanged to the memo, and the applied code never appears until something else moves the status.
