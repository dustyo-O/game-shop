# Game Shop — магазин цифровых товаров (тестовое задание)

Рабочий срез магазина игровых ключей, построенный вокруг одного утверждения: **оплаченный заказ всегда получает ровно один ключ** — сколько бы раз платёжный сервис ни повторил вебхук, сколько бы раз покупатель ни нажал Купить, в каком бы порядке ни пришли события и завис ли поставщик посреди выдачи.

**Стек.** pnpm-монорепозиторий: API на NestJS 11 (в деплое — одна serverless-функция), витрина на Vite + vanilla TypeScript (статика), Drizzle ORM + Postgres 16; хостинг — Vercel (`fra1`) + Neon (`eu-central-1`).

## 1. Живая витрина и исходники

- **Витрина:** https://game-shop-ochre.vercel.app
- **Исходники:** https://github.com/dustyo-O/game-shop

Всё, что описано ниже, кроме раздела «Запуск локально», можно проделать, не клонируя репозиторий: витрина, страница заказа, операторский вид и запуск гонок против живого магазина работают с любой машины. Магазин — демонстрационный: реальных покупателей нет, оплата имитируется двумя кнопками на странице заказа — «Оплатить успешно» и «Оплата не прошла».

Что попробовать руками: нажать Купить на карточке → страница `/order/ord_…` со статусом «Ожидает оплаты» → ввести `LIMIT3` и нажать «Применить» (цена пересчитается на сервере) → «Оплатить успешно» → через несколько секунд «Ключ выдан» и сам ключ. Операторский вид — `/admin/recovery` — показывает оплаченные, но не выданные заказы и кнопку повтора; он открывается по токену:

> **Токен демо-стенда:** `1e568c9c17abcb8cc8e334937956ea14` — это `ADMIN_TOKEN` *только живого демо*, опубликованный намеренно (см. раздел 5). Он не совпадает с локальным значением по умолчанию из `.env.example` и ничего, кроме демо-операций на магазине без покупателей, не открывает.

## 2. Запуск локально

Нужны: **Node ≥ 22.18** (и < 23 — `engines` в `package.json`), **pnpm 10** (`corepack enable` подхватит `pnpm@10.18.0` из поля `packageManager`), **Docker** с Compose (в контейнере живёт только Postgres 16, порт `5433`; API и витрина запускаются из исходников — так же, как они деплоятся).

```sh
pnpm install     # ставит зависимости и собирает packages/* (хук prepare)
pnpm db:setup    # docker compose up --wait, миграции, сид: 12 товаров, 50 ключей, 4 промокода
pnpm dev         # витрина http://localhost:5173, API http://localhost:3000
```

Что должно быть видно: `curl http://localhost:3000/api/health` отвечает `{"status":"ok",…,"runtime":"node","supplier_timeout_ms":2000}`; на `http://localhost:5173` — витрина с баннером, меню «Каталог», блоком пополнения Steam и рядом карточек; Купить ведёт на страницу заказа, «Оплатить успешно» — к «Ключ выдан». Настраивать ничего не нужно: `scripts/with-env.ts` подкладывает `.env.example` как базовые значения под каждую `pnpm`-команду; `.env` создаётся только если что-то надо переопределить.

Проверки (одна общая база — запускать по очереди, не параллельно):

```sh
pnpm test        # Vitest: API — 17 файлов / 144 теста (в т. ч. гонки в 4 процессах), витрина — 6 / 69
pnpm --filter @game-shop/web exec playwright install chromium   # один раз, ~276 МБ
pnpm test:e2e    # Playwright: 10 файлов / 65 тестов, поднимает свои серверы на 5101/5102
pnpm race        # девять состязательных проверок против четырёх локальных процессов → 9/9
```

## 3. Как воспроизвести гонки

### Локально

`pnpm race` собирает API, поднимает **четыре настоящих процесса** `node dist/main.js` (порты 4601–4604, у каждого пул из одного соединения — форма serverless), гоняет девять проверок по кругу между ними и гасит их. Четыре — не украшение: в одном процессе пул `max: 1` выстраивает конкурентные запросы в очередь ещё в Node, и клейм ключа *вообще без блокировок* раздал 20 разных ключей из 20, а в четырёх процессах тот же сломанный код — только 9 из 20 (`context/product/architecture.md` §7); одиночный процесс измеряет пул, а не ограничение. `pnpm race --list` — список, `pnpm race webhooks same-event` — только названные.

| Проверка | Что доказывает |
| --- | --- |
| `harness` | Процессы действительно разные: локально — по `pid` в `pg_stat_activity`, снаружи — по заголовку `x-instance-id` (≥ 2 разных на 8 параллельных `GET /api/health`) |
| `webhooks` | 50 **разных** событий `paid` для одного заказа одновременно → заказ `delivered`, один ключ (I3, I4) |
| `same-event` | 20 одновременных доставок **одного** `event_id` → `stored=1, duplicate=19`, ничего не повторилось (I2) |
| `before-order` | Вебхук `paid` пришёл до создания заказа → сохранён, не потерян; заказ создаётся на другом инстансе и доходит до `delivered` |
| `create-order` | 20 одновременных Купить с одним `Idempotency-Key` → один заказ; новый ключ → новый заказ (I1) |
| `promo` | 20 одновременных `LIMIT3` → ровно `3 × 200` и `17 × 409 exhausted`; 10 `ONCEONLY` → 1 и 9; ни одного 5xx (I7, I8) |
| `recover-out-of-stock` | Пул осушен → заказ `out_of_stock`, не падение; после пополнения повтор → `delivered` с ровно одним ключом, второй повтор → 409 |
| `recover-refusal` | Поставщик A отказал → B выдал под **новым** `request_id`; один ключ |
| `recover-timeout` | A завис *после* клейма ключа → попытка `unknown`, а не `failed`; повторный запрос к **тому же** A с **тем же** `request_id` возвращает тот же код; B не спрашивают (I5) |

### Против живого магазина

```sh
RACE_BASE_URLS=https://game-shop-ochre.vercel.app ADMIN_TOKEN=1e568c9c17abcb8cc8e334937956ea14 RACE_DEMO_RESET=1 pnpm race
```

В этом режиме раннер ничего не собирает и не запускает — инстансы поставляет платформа. У проверяющего нет доступа к базе, поэтому каждая проверка, которая заглядывает в Postgres (одна строка `deliveries`, один заклеймленный ключ, `used_count = 3`…), печатается как **`SKIP` с названием утверждения — и никогда не засчитывается как пройденная**; HTTP-половина (статусы, `stored`/`duplicate`, `delivered`, тело ответа) проверяется по-настоящему. Проверки оставляют на стенде заказы; `RACE_DEMO_RESET=1` в конце вызывает `POST /api/admin/demo/reset` и печатает, что снято, а `RACE_BASE_URLS=… ADMIN_TOKEN=… pnpm demo:reset` делает то же отдельной командой. Полное описание режима, ручек и того, какие утверждения требуют базы, — в `scripts/race/README.md`.

Если стенд простаивал, первый прогон может закончиться `8/9`: падает только `harness` — `all 8 answers came from one instance — re-run, or check that Fluid Compute is off` — потому что восемь миллисекундных `/api/health` успел обслужить единственный проснувшийся инстанс, тогда как рабочие проверки того же прогона отвечают из десятков процессов. Это холодная платформа, а не магазин: повторите команду — по тёплому стенду `harness` проходит (так выглядела и первая из пяти попыток автора, см. ниже). Заказов `harness` не создаёт, так что сбрасывать стенд между попытками не нужно.

## 4. Как гарантирована единственная выдача

Ни одна гарантия не держится на «сначала проверить, потом сделать» в коде приложения и ни одна — на блокировке в памяти процесса; каждую решает Postgres одним оператором. **Выдача — это выигранный `INSERT`:** у `deliveries.order_id` есть `UNIQUE`, так что из двух воркеров, одновременно увидевших «ключа ещё нет», строку вставит ровно один (`INSERT … ON CONFLICT (order_id) DO NOTHING RETURNING`). Чтобы к поставщику вообще ходил один воркер, заказ продвигается под блокировкой строки — `SELECT … FROM orders WHERE id = $1 FOR UPDATE` — и переходом с охраной статуса `UPDATE orders SET status = 'delivering' WHERE id = $1 AND status = 'paid'`: `0 rows` значит «кто-то уже продвинул, ничего не делать». Ключ из пула забирается `UPDATE supplier_keys SET claimed_by_request_id = $1 WHERE code = (SELECT code … WHERE claimed_by_request_id IS NULL … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING code`, а `claimed_by_request_id UNIQUE` не даст продать один ключ дважды даже при проигранной гонке. Вебхуки складываются во входящую очередь `payment_events` с `event_id PRIMARY KEY` через `INSERT … ON CONFLICT (event_id) DO NOTHING`: выигранная вставка — «первое появление» и обязанность обработать, проигранная — повтор, `200` и ничего больше; событие для ещё не созданного заказа лежит в очереди (внешнего ключа нет) и разбирается, когда заказ появится. Таймаут поставщика — это `unknown`, а не `failed`: магазин переспрашивает **того же** поставщика с **тем же** `request_id` (он детерминирован: `req_{order_id}_{provider}_{attempt}`), и ledger поставщика возвращает уже выданный код; ко второму поставщику никогда не идут, пока хоть одна попытка `unknown`. Лимит промокода — одна условная операция без чтения: `UPDATE promo_codes SET used_count = used_count + 1 WHERE id = $1 AND used_count < max_uses RETURNING *`, `0 rows` — «исчерпан». Каждый оператор в форме, которую реально выполняет Postgres, с комментарием, что означают 0 и 1 строк, — `context/product/architecture.md` §3; длинное объяснение всей цепочки — `docs/walkthrough/phases-1-to-5.md`.

## 5. Ключевые решения и компромиссы

- **Входящая очередь в Postgres, а не брокер.** Событие и изменение состояния коммитятся в одной транзакции, воркеры разбирают очередь через `FOR UPDATE SKIP LOCKED`. *Цена:* это не очередь общего назначения — без dead-letter, без бэкпрешера; при реальной нагрузке её заменила бы настоящая очередь.
- **Serverless для доказательства, а не для удобства.** Долгоживущий процесс позволил бы блокировке в памяти незаметно прикрыть отсутствующую гарантию в базе; раздельные процессы не позволяют. *Цена:* холодные старты — измерено 1,81 с инициализации платформы + 29 мс Nest на холодном инстансе, 2,38 с на холодный вызов самого себя (симулятор оплаты), ~0,15 с на тёплом; Neon засыпает через пять минут простоя, и первый запрос после этого стоит ~0,8 с. Поэтому живой профиль иной, чем локальный: `SUPPLIER_TIMEOUT_MS=5000` (локальные 2000 приняли бы здорового холодного поставщика за `unknown`), `SUPPLIER_MAX_PROBES_PER_REQUEST=2` (худший случай 20 000 мс) под `maxDuration: 60` в `vercel.json`; Fluid Compute выключен, иначе один инстанс обслуживал бы много запросов и доказательство рассыпалось бы.
- **`READ COMMITTED` плюс явные блокировки, а не `SERIALIZABLE`.** Каждая гарантия видна как конкретный оператор и `UNIQUE`. *Цена:* многословнее; `SERIALIZABLE` спрятал бы то же самое в логику повторов транзакций.
- **Без подписи вебхуков.** Задание её не требует. *Цена:* в продакшене `POST /api/webhooks/payment` не аутентифицирован и нуждался бы в HMAC.
- **Демо-ручки на живом магазине:** `POST /api/admin/demo/reset` (одна транзакция: блокировка всех заказов, шесть `DELETE`, счётчики промокодов в ноль, все ключи освобождены), `POST /internal/suppliers/keys/{drain,restock}` (осушить пул под меткой прогона и вернуть ровно то, что осушили — для `recover-out-of-stock`), `ALLOW_CLIENT_SUPPLIED_ORDER_ID=true` (иначе `before-order` не поставить: id заказа нужно знать заранее) и **опубликованный токен**. Это безопасно только потому, что у магазина нет покупателей: худшее, что позволяет токен, отменяет сброс. *Цена:* деплой заведомо не продакшен-формы — флаг id, дренаж пула и сброс в настоящем магазине включать нельзя, и код говорит это при каждом старте.
- **Без Vercel Cron.** На Hobby-плане он срабатывает примерно раз в сутки — как страховка бесполезен. Вместо него четыре слоя обработки: `waitUntil` после ответа на вебхук, дренаж при создании заказа, дренаж при опросе статуса, и `POST /api/admin/payment-events/sweep` оператором. *Цена:* застрявший заказ, до которого никто не дошёл, ждёт опроса или оператора, а не таймера.
- **Окно «применить промокод vs оплатить» задокументировано, а не закрыто.** Симулятор читает сумму заказа без блокировки и затем шлёт вебхук; код, применённый к заказу `created` в эти миллисекунды, ляжет на платёж по полной цене, потому что обработчик суммы не сравнивает. Честное исправление названо — сравнивать `payment_events.amount_minor` с `orders.amount_minor` под блокировкой заказа и отправлять несовпадение в `payment_failed`, — но оно меняет платёжный путь и суммы в 50-вебхучной гонке; `context/product/architecture.md` §9.
- **Сознательно не сделано:** снятие или замена применённого промокода, лимиты на покупателя и сроки действия кодов, свой домен, мониторинг и алерты, CI и автодеплой (деплой — ручной шаг из зафиксированного дерева), Playwright против живого адреса (пять взаимодействий и покупка на живом стенде пройдены вручную — `docs/screenshots/006-live-*.png`).

## 6. Две карты

**Пять состязательных сценариев задания → проверка → тест, который её охраняет.** Проверка запускается по имени (локально `pnpm race <проверка>`, против стенда — с `RACE_BASE_URLS` и `ADMIN_TOKEN` из раздела 3); тест — в `pnpm test`.

| Сценарий из задания | `pnpm race …` | Охраняющий тест |
| --- | --- | --- |
| 50 параллельных вебхуков `paid` для одного заказа → ровно один факт выдачи, ровно один ключ списан | `webhooks` | `apps/api/test/concurrency/fifty-webhooks-one-order.test.ts`; блокировка заказа отдельно — `order-lock-race.test.ts` |
| Повторный вебхук с тем же `event_id` ничего не меняет | `same-event` | `apps/api/test/acceptance/single-issuance-under-races.test.ts`, блок §2.2 |
| Вебхук пришёл до создания заказа или не по порядку — без потери и без дубля | `before-order` | `apps/api/test/acceptance/single-issuance-under-races.test.ts`, блок §2.3 |
